# Backups

Teme backs up its own database and media with **restic**, to places the administrator chooses, on a schedule, and checks that each backup can be read back (I-355 onward; slice 1.12). Slice 1.12a built the seam the rest stands on: the records, the permission, the settings, the lock, and the two programs found, checked and driven. 1.12c sets backups up and holds the keys: the recovery and machine keys, and the places backups are kept. 1.12d makes the backups: the run, its checks and copies, what's kept and pruned, and the nightly schedule. 1.12e proves they can be read and restored, and tells the administrators when they can't. The screen is *Tools › Backups*, below; the part that restores adds its own section here when it merges.

## The two programs

Teme runs two programs it doesn't ship: **restic**, which stores encrypted, deduplicated snapshots, and **PostgreSQL's `pg_dump` and `pg_restore`**, which make and read the database's copy (I-2400).

- **Where they are** (`config/teme.php`'s `backups` block): `TEME_RESTIC_BINARY`, `restic` by default, and `TEME_POSTGRES_BINDIR`, empty by default. A value holding a slash or a backslash is a path, used as given; a bare name is looked up on the PATH, as a shell would, with `PATHEXT` on Windows. An empty PostgreSQL folder means `pg_dump` and `pg_restore` are each looked up on the PATH; a folder means both are in it. Windows paths in `.env` go in **single quotes**, since a double-quoted value reads `\r` or `\U` as an escape.
- **The versions Teme accepts** (I-366): restic **0.19.1 or later**, the version it is tested with; `pg_dump` and `pg_restore` from **PostgreSQL 18 or later, and no older than the database server**, and both the same version.
- **`php artisan teme:backup:tools`** says where each program is, its version beside the server's, and in words what's wrong; it exits 1 when anything is. It reads and changes nothing. 1.13's `teme:deploy` runs it before it backs up (I-377).
- **restic's cache** is `storage/app/restic-cache` (`TEME_RESTIC_CACHE`); an empty value runs restic with `--no-cache`.

## Running restic

`Restic::run()` starts one process per call through Laravel's `Process`:

- **An argument list, never a shell string**, with `--json`, the cache flag and the repository's `-o` options first, then the caller's command. Each call has a time limit, an hour unless the caller says.
- **Secrets only in the child's environment:** `RESTIC_REPOSITORY` and `RESTIC_PASSWORD` (and `RESTIC_FROM_*` for a copy), the place's `AWS_*` variables, and the caller's own, such as PostgreSQL's for a dump. A key added with `key add` goes on standard input. **Every `RESTIC_*`, `AWS_*` and `PG*` variable Teme itself was started with is removed** first (`ChildEnvironment`), so a stray `RESTIC_PASSWORD_FILE` or `AWS_PROFILE` on the server can't change what restic opens. `RESTIC_PROGRESS_FPS` is `0.1`, since with `--json` restic otherwise prints its progress many times a second for a whole backup.
- **`ResticRepository`** holds its key privately, shows only its location when dumped, and refuses to be serialized.
- **Exit codes in words** (restic 0.19.1's table): 0 succeeded; 1 failed; 2 crashed; **3, incomplete, is a failure** (a backup that couldn't read some files has a hole); 10 no repository; 11 locked; 12 wrong key; 130 cancelled; any other status failed. Teme adds two of its own: timed out, and not started. People read `ResticResult::sentence()`.
- **restic's own words** (`ResticResult::detail()`, for the log and the operator's terminal) are its `exit_error` message from standard error, or the last line, at most 1,000 characters, with **every secret of the call replaced by `[hidden]`**. A secret is the repository's key, the standard input, or the value of a variable whose name holds `PASSWORD`, `SECRET`, `TOKEN` or `KEY`; a host, user, port, database name or region stays readable.

## The database's copy

`PostgresTools` points `pg_dump` and `pg_restore` at a database through PostgreSQL's own variables (`PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`, `PGSSLMODE`), from Teme's connection or one given, with `PGAPPNAME=teme-backup` and `--no-password`, so a wrong password fails at once. A connection naming several hosts is refused.

- **The dump** (I-357) is `--format=custom --statistics`, with `--snapshot` when a transaction exported one, so the copy is the database exactly as that transaction sees it.
- **It reaches restic through restic's own `--stdin-from-command`:** restic runs `pg_dump` as its child and stores its output as one file, `teme.dump` (no leading slash, which restic on Windows can't dump). Nothing is written to disk on the way, and restic makes no snapshot when `pg_dump` fails.
- **Tables kept as structure only** (`BackupTables::STRUCTURE_ONLY`; I-261, I-534): `cache`, `cache_locks`, `sessions`, `jobs`, `job_batches`, `failed_jobs`, and the page cache's `page_cache_tags`, `page_cache_purges`, `page_cache_cdn_purges`, `page_cache_files` and `page_cache_cdn_addresses`. Their definitions are dumped, never their rows. `tracked_jobs` looks like a queue table but is data a restore needs, so it's named in `BackupTables::KEPT_DESPITE_NAME`. A test lists every table and requires each that looks like a cache, a session, a queue or a lock to be in one list or the other, so a new one is a decision, never an accident.

## The lock

**One backup at a time, across the web, the queue worker, the scheduler and `teme:deploy`** (I-358): `BackupLock` holds a session-level PostgreSQL advisory lock on `hashtext('teme.backup')`, which `cache:clear` never empties.

- It's held on **a connection of its own**, `teme_backup_lock`, made when the lock is taken. `during($work)` takes it without waiting, refuses with `BackupAlreadyRunning` while another session holds it, runs the work, then lets go with `pg_advisory_unlock_all()` and closes the connection. The unlock comes first because a closed session's locks go only when its server process ends, which another session can see a moment late. Closing still lets go when the work broke the session, and a process that dies takes its locks with it.
- `isHeld()` takes the shared lock on the default connection for an instant and lets go, so asking never holds anything. A media file deletion asks it, and waits while a backup, a prune or a check runs (*The schedule*).
- `stillMine()` is true only while this process took the lock with `during()` and the lock's own session still has it in `pg_locks`; it's false on any connection error, as when the database restarted under a run (I-2866).

## The records

Three tables, every ID a lower-case ULID, every rule a check constraint (a fourth, `backup_alerts`, is in *The verdict and the alerts*):

- **`backup_destinations`**, the places: a name, a `kind` (`folder`, `s3` or `sftp`) with the keys its `location` needs, whether it's `off_server` (every kind but `folder`), restic's `repository_id`, a `state` (`ready`, `failing` with its `last_error`, or `removed`), when it last answered, and who added or removed it. **`credentials`** are encrypted JSON (`encryptString()`, never `serialize()`, rule 4), required for every kind but a folder, cleared when a place is removed, and never in `toArray()` or `toJson()`.
- **`backup_runs`**, one row for each backup, copy, check, read-back, test restore, prune or restore: its `state` (`running`, `finished` or `failed`), what started it (`schedule`, `person`, `deploy` or `command`, with the person's ID only for a person), its place, its parent run, restic's `snapshot_id`, its `figures` (a JSON object) and its message.
- **`backup_keys`**, restic's keys for each place: the `machine` key Teme's own runs use and the people's `recovery` keys, by restic's key ID, with a label, and who added or removed each.

## The permission and the settings

- **`backups.manage`**, administrators only (I-364), added by an add-only migration and `RoleSeeder`. Where a screen lists permissions, its label is "Manage backups".
- **The `backups` settings group** (I-361) is changed on its own screen only, never on a Settings page: `hour` (`00:00` to `23:00`, `02:00` by default), `keep_daily` (7), `keep_weekly` (4), `keep_monthly` (12), and `machine_key`, a secret a server may supply as `TEME_BACKUP_MACHINE_KEY`. The group is **sensitive**: keeping fewer backups removes some, so every change is in the security log, and the Operations that change it ask for the password again.
- **The security log's backup types** are all registered: `backup.set_up`, `backup.destination_added`, `backup.destination_changed`, `backup.destination_removed`, `backup.recovery_key_added`, `backup.recovery_key_replaced`, `backup.recovery_key_checked`, `backup.restore_started` and `backup.restore_ended`.

## Setting up

`php artisan teme:backup:setup` (and the setup page on Tools › Backups) runs **`SetUpBackups`** (I-2401): it makes the first place's repository with `init`, opened by the machine key, adds a new recovery key to it, and returns that key once.

- **The recovery key** (I-2817): 32 characters of Crockford's base 32 (no I, L, O or U), 160 bits from `random_int()`, shown as eight groups of four joined by hyphens. **That printed form, hyphens included, is restic's password**, so plain restic and the paper alone open the backups. Typed into Teme (`RecoveryKey::fromTyped()`), a key is read in any case, spaces and hyphens ignored, `O` read as `0` and `I` and `L` as `1`. Teme keeps no copy.
- **Keys stay inside objects that hide them** (I-2818): `RecoveryKey`, `SftpKeyPair` and `NewPlace` show `[hidden]` to `var_dump()` and `print_r()` and refuse to be serialized, so none reaches a session, a queue or a cache by accident. A parameter that carries a key as a string is `#[SensitiveParameter]`, so a stack trace leaves it out.
- **Typed back, kept nowhere** (I-2819): showing a key asks for two of its groups, at positions chosen at random. The Operation returns a `RecoveryKeyChallenge`: the purpose, the label, the positions, the new key's restic ID at each place, and an HMAC-SHA256 under `APP_KEY` of all of them and the two groups. It holds no part of the key. The caller keeps it (the command in memory, 1.12h in the session) and hands it to **`ConfirmRecoveryKey`** with the typed groups. The command allows three tries.
- **Pending until typed back** (I-2820): a shown key's `backup_keys` rows are written at once as pending, `removed_at` equal to `added_at`. `ConfirmRecoveryKey` sets `removed_at` back to null. It refuses when the key is no longer pending at exactly the places in use.
- **The machine key** (I-2824): 64 hexadecimal characters from `random_bytes(32)`, made by the first setup when the server supplies no `TEME_BACKUP_MACHINE_KEY`, and written through `SettingsWriter` as the `backups` group's `machine_key` secret: encrypted in `settings.secrets`, and logged as a sensitive change without its value. It is the first key of every repository Teme makes, opens every place for Teme's own work, and is never shown. `BackupKeys::machineKey()` reads it.
- **Where setup stands** (I-2821): `BackupSetup::isFinished()` is true once a recovery key in use is recorded on a place in use. Until then nothing backs up, and every key and place Operation but `SetUpBackups`, `ConfirmRecoveryKey`, `TestBackupDestination` and `RemoveBackupDestination` refuses with "Finish setting backups up first." Setup run again on an unfinished setup keeps its place, sweeps the key nobody saw, and shows a new one. To start again somewhere else, a person removes the unfinished place, which only an unfinished setup allows.

## Keys

Each place holds restic keys, recorded in `backup_keys` by restic's key ID (I-359): **the machine key**, labelled "Machine key", and **the recovery keys** people hold. One recovery key has a different restic ID at each place; the rows that share a label are one key (I-2830). A label is at most 100 characters and unique, whatever its case, among the recovery keys in use; setup's is "Recovery key" unless the person names it. A new key reaches restic only on `key add`'s standard input.

- **Add** (`AddRecoveryKey`): a new key under a new label, added to every place in use, shown once and typed back as at setup.
- **Extend** (`ExtendRecoveryKey`, I-2402): the holder types their recovery key once, and Teme adds it, under its recorded label, to every place in use it doesn't open yet. A key that opens a place but isn't one of the site's recorded recovery keys is refused.
- **Replace** (`ReplaceRecoveryKey`): a new key under the same label, added to every place in use and shown once. **The old key goes only once the new one is confirmed:** `ConfirmRecoveryKey` marks the old key's rows removed in its transaction, and removes the old restic keys **after the commit** (`DB::afterCommit()`), so nothing that fails there can leave the places without a recovery key. A place that doesn't answer then keeps the old key and is named; the next sweep removes it.
- **Check** (`CheckRecoveryKey`): says which places a typed key opens, and its label. It keeps nothing of the key and writes only `backup.recovery_key_checked`; it's an Operation because it asks for the password again and writes that entry.
- **One key change at a time** (I-2839): `SetUpBackups`, `ConfirmRecoveryKey`, `AddBackupDestination`, `AddRecoveryKey`, `ExtendRecoveryKey` and `ReplaceRecoveryKey` first take `pg_advisory_xact_lock(hashtext('teme.backup-keys'))`, held to the end of their transaction, then read again what their validation decided. So two first setups can't each make a machine key, and a sweep can't remove a key a confirmation is recording.
- **The sweep** (I-2822): before Teme adds a key to a place, it lists the place's keys and removes each whose row there is marked removed: a key shown and never typed back, or a replaced key whose removal failed. **A key Teme has no record of is never touched**: the database isn't the whole truth about a repository's keys (a restored older database, a second install, a key an operator added with restic by hand). The key that opened the place is never removed.
- **Who may** (I-2823): a person who holds `backups.manage`, or the operator at the server; everyone else is refused with "Only an administrator manages backups." Every key and place Operation asks for the password again (`RequiresElevation`).
- **`php artisan teme:backup:key {check|add|extend|replace} {label?}`** runs them as the operator. It refuses to run without a person at the terminal, asks for a key with hidden input, never as an option or argument, and asks for the two groups straight after showing a key (I-2836).
- **The security log** (I-2835): `backup.set_up`, `backup.destination_added`, `…_changed` (with the fields changed) and `…_removed`, `backup.recovery_key_added` (a confirmed setup or add, and an extend), `backup.recovery_key_replaced` and `backup.recovery_key_checked`. Places, kinds, labels and counts only; never a key.

## Places

A place is described as a `NewPlace`, and its `problems()` say in words what can't be used before anything runs (I-360, I-2825). Three kinds:

- **A folder** on this server: an absolute path of at most 500 characters. **It's refused inside the public folder**, where it would be served, **or inside the root of any `local` disk** in `config/filesystems.php`, where the media is kept, checked as written and through any link (`realpath()`), since a deploy's symlink can lead into `public/`. A folder that already holds a repository is refused. The folder offered first is `storage/app/backups` (`BackupSetup::suggestedFolder()`). It's the only kind that isn't `off_server`.
- **S3-compatible storage**: an `https://` endpoint, a bucket, an optional folder in it and an optional region, an access key ID and a secret access key. The keys are kept in `credentials` and reach restic only as `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_DEFAULT_REGION`.
- **An SFTP server** (I-2403, I-2827): a host, a port (22 by default), a user, a folder, **an Ed25519 key pair Teme makes for the place** with sodium (`SftpKeyPair`), and **the host key a person confirmed**. The person adds the public half to the server's `authorized_keys`; the private half, in OpenSSH's own format, is kept in `credentials`. `SshKeyscan` reads the server's host key (`ssh-keyscan -T 10`), preferring Ed25519, and the person confirms its fingerprint (`SHA256:…`, as `ssh-keygen -l` prints it) before the place is added or moved to another server. The location keeps the host key and its fingerprint, both public. Every field that reaches SSH's configuration is checked against a pattern that can't hold a space, a quote or a line break.

**SFTP's files live for one call** (I-2826). `PlaceRepositories::during()` makes a folder of its own under the system's temporary folder (mode `0700`) and writes in it each SFTP place's private key (`0600`), a `known_hosts` with one line per place, and an `ssh_config` with one `Host teme-{place id}` block per place (`StrictHostKeyChecking yes`, `BatchMode yes`, no passwords). Every SFTP repository in the call carries the same `-o sftp.args=-F '{folder}/ssh_config'`, so two SFTP places open together. Each file is removed by its name in a `finally`, and by a shutdown function if PHP stops first. **A changed host key fails the call**, and the place turns failing at its next run or test. `ssh` and `ssh-keyscan` must be on the server's `PATH`. restic reads one set of `AWS_*` variables for both sides of a call, so two S3 places with different keys never open together (`PlaceRepositories::canOpenTogether()`).

- **Adding** (`AddBackupDestination`, I-2402, I-2829): the person types a recovery key once. Teme opens a place in use with it, refuses a wrong key before making anything, and requires it to be a recorded recovery key there. The new repository is made with `init --copy-chunker-params`, **its chunker parameters copied from a folder place, else from the oldest place restic can open beside it**, so data splits alike at every place (I-2828); when none can, it's refused, asking for a folder first. The machine key and the typed key lock the new place, and Teme forgets the typed key. It names the other recovery keys that don't open the place yet, for their holders to extend.
- **Changing** (`ChangeBackupDestination`, I-2832): the name, or the address and credentials of the same kind; never the kind. A new address is opened with the machine key and refused unless restic answers with the repository ID recorded for the place. An SFTP place keeps its key pair; a new server needs its fingerprint confirmed.
- **Testing** (`TestBackupDestination`, I-2831): `cat config` with the machine key. The place turns `ready`, or `failing` with the sentence in `last_error`; `last_answered_at` moves only when restic reached it. A folder also reports the room left on its disk; for S3 and SFTP Teme can't tell, and says so.
- **Removing** (`RemoveBackupDestination`, I-2833): `state` `removed`, `credentials` and `last_error` cleared. Its backups stay where they are, and its key rows stay as history. Once setup is finished, the only place in use can't be removed.
- Calls a person waits for stop after 60 seconds (`PlaceRepositories::ANSWER_SECONDS`), `init` after 600 (I-2837). A failed call becomes a sentence on `place` through `PlaceFailure`, and restic's own words, secrets hidden, go to the log at `warning` (I-2834).
- **`php artisan teme:backup:destinations {list|add|change|test|remove} {place?}`** runs them as the operator; `add` and `change` need a person at the terminal.

## The run

**`BackupSite::run()`** backs the site up (I-358). `teme:backup:run` and `teme:backup:due` call it inline, and 1.13's `teme:deploy` will. **It isn't an Operation:** a backup lasts minutes to hours, too long for one transaction. Every row it writes goes through two short Operations (I-2842): **`StartBackupRun`**, one `running` row (its kind, what started it, who, its place, its parent), and **`EndBackupRun`**, its state, figures, snapshot and message and each place's state, each in its own transaction. So a run is seen while it works and recorded however it ends. Both accept the operator or a holder of `backups.manage`, and ask no password: a backup reveals and destroys nothing (I-2843).

- **The lock covers the whole run** (I-2844): taken before the run's row is written, let go after the last check. While another session holds it, `BackupAlreadyRunning` is thrown and nothing is written. Before each step the run asks `stillMine()`; when the lock is lost, the run ends failed ("The backup lock was lost, so this stopped: another backup or prune may have started beside it.") and nothing more goes to restic (I-2866).
- **Refused, writing nothing:** the lock held, the actor, backups not set up. **Failed, with the run recorded and its sentence:** `teme:backup:tools`' problems, a media disk that isn't a folder on this server, no machine key, no place, no place answering, or a part not written (I-2853).
- **Which place** (I-2852): the places in use, oldest first; the first that opens with the machine key and answers `cat config` with its recorded repository ID takes the backup. Each that doesn't is recorded failing.
- **One moment of the database** (I-2847): `DatabaseMoment::open()` opens a session of its own, `teme_backup_moment`, begins a `REPEATABLE READ, READ ONLY` transaction and exports its snapshot. In it Teme reads PostgreSQL's version, the newest migration, every table's rows but the structure-only tables', and every media row. **The same snapshot feeds `pg_dump --snapshot=…`**, and the moment stays open until restic's `backup --stdin-from-command` has the whole dump. So the dump, the media list and the manifest describe one instant.
- **The media, as folders** (I-2848, I-2404): `MediaInventory` reads every media row the moment sees, trashed ones too, and checks each original and every variant on its disk by its recorded path (`is_file()`), never by listing. **restic then backs up the two disks' folders**, so each snapshot keeps two paths, not one per file, and finds last night's as its parent. A file a row names that isn't there is a hole: the run still writes all four parts, and fails, naming the first such file and how many. So does restic's exit 3 on the media. A file with no row is a harmless extra.
- **The `APP_KEY`** (I-2850): `app-key.json`, the key and its previous keys, **given to restic on standard input only**. Never in the manifest, a log, a figure, an argument or a file on disk.
- **Four snapshots, the manifest last** (I-2851): `teme-database` (`teme.dump`), `teme-media`, `teme-app-key` and `teme-manifest` (`manifest.json`), each with **`--host teme`** and the tags `teme`, `teme-run:{run id}` and its part. A run is complete exactly when its manifest is there. The host is fixed: a container's name changes with every deployment, and the site's domain on a move. Teme never touches a snapshot without the `teme` tag.
- **The manifest, format 1** (I-2849, I-2405): the run, when, and Teme's version; PostgreSQL's version and major, the newest migration and how many have run, and every table's rows; the media's counts and bytes, its two folders as this server has them and as restic writes them inside the snapshot, every original's ID, disk, path, bytes and SHA-256, and the missing files (at most 1,000 named); the active theme's code and version, as the dumped settings name it; and every installed package's version but development ones. No secret, and no code.
- **The check after every backup** (I-2858): at the place that took it, and at each it's copied to, a `check` run under the backup: the run's four parts are there, the manifest reads back equal to the one written, and `restic check` finds nothing wrong.
- **Copies** (I-2859): then every other place in use gets a `copy` run under the backup: asked to answer, then `restic copy --host teme --tag teme` from a place that holds the backup and can be opened beside it, a folder first. It copies whatever of Teme's the place lacks, so one that was down catches up. Then it's checked. One place failing doesn't stop the others, and a copy or a check that fails fails its own run, never the backup (I-2854).
- **What a run records** (I-2855): a backup's `figures` are `seconds`, `database_bytes`, `media_files`, `media_bytes`, `missing_files`, `bytes_added`, `tables` and `rows`, and its `snapshot_id` is its manifest's. A copy or a check records `seconds`. Each place's state follows what the run saw there, as a test of it does (I-2846). Messages never hold a secret; restic's own words go to the log.
- **Runs a dead process left** (I-2845): `StartBackupRun`, starting a whole backup or prune, first ends as failed every backup or prune still `running`, and every step under one, with "This stopped before it finished: the process running it ended." It refuses with a `LogicException` unless this process holds the lock (`stillMine()`), so no caller ends a live run. A restore's runs are never touched, and a check's are ended by the next check, not by a backup's start (*Verification*).
- **`php artisan teme:backup:run`** (I-2865): one backup now, as the operator, `started_by` `command`. It prints each step, then the outcome, and exits 1 when the backup, a copy or a check failed, backups aren't set up, or another backup runs.
- **Time limits** (I-2856): 60 seconds for a place to answer, 12 hours for a backup, a copy or a prune.

## What's kept and pruned

- **Teme chooses the runs to keep, by the settings' own words** (I-2860), not restic's `--keep-*`, which treats a run's four snapshots as four groups and overlaps the tiers. `KeptRuns::choose()` takes a place's complete runs, newest first, and keeps the newest of each of the last `keep_daily` days that have one; then, from the runs before those, the newest of each of `keep_weekly` ISO weeks; then, from the runs before those, the newest of each of `keep_monthly` months. Days, weeks and months are the site's time zone's.
- **Everything else tagged `teme` is forgotten by ID**, `restic forget` a hundred snapshot IDs at a time: incomplete runs and stray tagged snapshots too. A snapshot without the tag is never touched.
- **`PruneBackups`** (I-2861) runs under the backup lock, so never beside a backup: a whole `prune` run, and at each place in use a `prune` run (list, forget, `restic prune`, with `runs_kept`, `runs_forgotten` and `snapshots_forgotten`) and a `check` run straight after. One place failing doesn't stop the others; a lost lock stops it before the next place.

## Verification

**`VerifyBackups`** proves the backups can be read and restored (I-362). Like a backup, it isn't an Operation: a check lasts minutes to hours, so every row it writes goes through `StartBackupRun` and `EndBackupRun` (I-2951). `readBack()` and `testRestore()` first ask who is running them (the operator or a holder of `backups.manage`), then whether backups are set up, then whether a restore has left the places paused, all before anything is written. Neither asks for a password: a check reveals and destroys nothing.

- **Under the backup lock, one thing at a time** (I-2952): a check takes `BackupLock::during()` before its first row and asks `stillMine()` before each step. So a check never runs beside a backup, a prune, a restore or another check. restic's prune takes an exclusive lock and would stop a read-back half way, and a prune could forget the snapshot a test restore is reading.
- **Left by a dead process** (I-2953): a check starts by ending as failed every `read-back` and `test-restore` run, and every step of one, still `running`, with the sweep's words. It refuses with a `LogicException` unless this process holds the lock. It touches no other kind: a backup's and a prune's are `StartBackupRun`'s to end, a restore's are the restore's.
- **The read-back** (I-2954): a whole `read-back` run, and under it a `read-back` step at each place in use, oldest first. A step asks the place to answer, then runs **`restic check --read-data-subset={n}/7`**. **`n` is the seventh after the one this place last read back successfully** (1 first, and 1 after 7), taken from its newest finished step's `figures.subset`. So any seven good nights read all of a place's data once, and a seventh that failed is read again the next night, never skipped for a week. restic's exit 1 is damage, said in words that name the seventh; any other failure is restic's sentence. The place turns `failing` or `ready` by what was seen, and one place failing doesn't stop the others.
- **The test restore** (I-2955, I-362) is one whole `test-restore` run, ended with the place it read from and the tested backup's manifest snapshot. In order:
  1. the spare database opened;
  2. the newest finished whole backup found in `backup_runs`;
  3. the first place in use that answers and holds all four of its snapshots;
  4. its manifest read;
  5. room checked under `storage/app/verify` for the dump, against the backup's own `figures.database_bytes`;
  6. the dump fetched into a private work folder with `restic dump --target`, never through PHP's memory;
  7. the spare database emptied, and `pg_restore` run into it, all or nothing;
  8. the dump removed at once;
  9. every table's rows counted, but the structure-only tables', and compared with the manifest's, with the newest migration;
  10. 50 originals chosen at random (all, when there are fewer) fetched one at a time and their SHA-256 compared with the manifest's, each file removed as soon as it is hashed.

  Then the work folder is removed and the spare database emptied again, whatever happened. Any difference fails the run: the message names the first and counts the rest, and the log lists them all. Its `figures` are `backup_run`, `tables`, `rows`, `differences`, `media_files`, `media_wrong` and `seconds`.
- **The spare database** (I-2956, I-2406) is a database the site's account owns and nothing else uses, named by **`TEME_VERIFY_DATABASE`**; `TEME_VERIFY_DB_HOST`, `_PORT`, `_USERNAME` and `_PASSWORD` default to the site's own `DB_*`. `SpareDatabase` is the only code that ever empties a database, and it opens it after three guards: its name ends in `_verify` and holds only letters, digits, dots, hyphens and underscores (checked before connecting, since it reaches `pg_restore --dbname`); it isn't the site's database by configuration (the same name, host and port); and it isn't the site's database by what the two servers answer (the database's name and OID and the server's start time, equal on both sessions only when they are one database). It works on a session of its own, `teme_verify_session`, which is also entered in the configuration so Laravel can reconnect it by name. Emptying drops every extension but `plpgsql`, then `DROP SCHEMA public CASCADE` and `CREATE SCHEMA public`, which the database's owner may do without being a superuser. `pg_restore` runs through `PostgresTools` with `--single-transaction --no-owner --no-privileges --no-comments --no-publications --no-subscriptions --no-security-labels --no-tablespaces`, so what comes back is as Teme's own role, nothing more. The password never reaches an argument, a log line or a message. **Without a spare database the test restore isn't due, and the verdict is amber** (*The verdict and the alerts*).
- **The work folder** (`VerifyFiles`) is `storage/app/verify/{ulid}`, mode `0700`: each file removed by its known name, then the folder, never by listing it.
- **What's due** (I-2957) is in *The schedule*.
- **While the places are paused** (I-2965), no check is due and `VerifyBackups` refuses with the pause's words: a copy of the site reading back the old site's places would take restic's locks there.
- **Time limits** (I-2964): 60 seconds for a place to answer; 12 hours (`BackupSite::WORK_SECONDS`) for a read-back, for fetching the dump and for `pg_restore`; restic's default hour for the manifest and for each media file.
- **`php artisan teme:backup:verify {--read-back} {--test-restore}`** (I-2963) runs them as the operator, `started_by` `command`; with neither option it runs both. It prints each step, then "Read-back: done." or "Read-back failed: …", and the same for the test restore. Without a spare database it says the test restore is skipped, which fails the command only when the test restore was all it was asked for. It exits 1 when a check failed, backups aren't set up, the places are paused, or another backup or check runs.

## The verdict and the alerts

**`BackupStatus::verdict()`** says in one `BackupVerdict` how the backups stand (I-2958, I-2409). The banner, the alert email and 1.12h's page all read it, so the three always agree. It reads the backup tables, two settings and the configuration in at most four statements, through their indexes, and never asks restic.

- **Red, and nothing else, when backups aren't set up:** no recovery key on a place in use.
- **Red, and emailed** (`alerting`): the newest ended backup failed, or recorded missing files; a copy or a check under it failed; **no backup has started since the hour's latest time two hours ago** (`GRACE_HOURS`), counted only once backups were set up before then, so a dead scheduler shows two hours after the hour; the newest ended prune, read-back or test restore failed. The newest of each kind decides, so a success clears an older failure.
- **Red, not emailed:** the places are paused after a restore. While paused, no backup is counted overdue. A pause is a choice a person makes, not a failure.
- **Amber** (`cautions`): no backup has finished yet, and none is overdue or failed; every place in use is on this server (I-355); no spare database is named (I-2406).
- **Green:** none of these. `level()` is `error`, `warning` or null; `problems` are told in order, and `lastGoodBackup` is the newest finished backup's end.

**The banner** (`BackupsSafe`, I-2959, I-221) is a Status check shown to holders of `backups.manage`. Red is an `error` banner at priority 90 with the first problem, below an unusable theme's 100 and above every warning. Amber is a `warning` at priority 20 with the first caution, below the page cache's and the represented person's and above search's: amber is a lasting state, not news. Its action, "See the backups", leads to Tools › Backups.

**The alert rules** (I-2960, I-2409): every administrator is emailed at once when backups fail, at most once a day while they keep failing, and once when they work again.

- **`RaiseBackupAlert`** runs at the start of every minute in `teme:backup:due`, even while the lock is held so a failure is told without waiting for a long check, and again after the work. A failure is one of the verdict's `alerting` sentences, and each is told on its own. Within the current run of alerts (those since the newest `fixed`) it writes, in this order: **`failing`**, listing the failures no alert has told yet, even if another was told a minute ago; else **`reminder`**, listing those last told 24 hours ago or more; else **`fixed`**, when no failure is left, the verdict isn't red, and the run has an alert; else nothing. A reminder waits a minute behind a new failure.
- **One decision at a time:** the Operation takes `pg_advisory_xact_lock(hashtext('teme.backup.alert'))` before it reads the newest alert, so two schedulers or two overlapping minutes send one email. It writes the row, then queues the email **after commit** (rule 6), so a mail server that's down loses one email and never sends one every minute. A failure in the alert is reported and never stops a backup.
- **Who gets it** (I-2961): every account that holds `backups.manage`, verified and not suspended, read when `SendBackupAlertEmails` runs. No setting turns it off: a backup is a guarantee. The job runs once (`$tries = 1`), so a failure part way never emails anyone twice.
- **`backup_alerts`** (I-2962) holds one row for each decision: a ULID, `kind` (`failing`, `reminder` or `fixed`), `problems` (a JSONB list of the sentences emailed, empty exactly for `fixed`) and `raised_at`, indexed on `raised_at DESC`. Check constraints hold the kinds and the list's shape. Only `RaiseBackupAlert` writes it. It is data, so a backup keeps it.
- **The email** (`BackupAlertNotice`, I-2967) says what failed in the verdict's own sentences, the newest good backup, what to run at the server (`php artisan teme:backup:run` and `teme:backup:verify`), and when the next email comes; the fixed kind says backups work again and since when they had failed. Place names and the site's title are escaped for Markdown (`MailText::inline()`). Its button, "See the backups", leads to Tools › Backups.
- A dead scheduler sends no email, since nothing runs `teme:backup:due`; the banner turns red two hours after the hour (I-2520).

## The schedule

- **`teme:backup:due`** runs every minute (`withoutOverlapping(10)`, `onOneServer()`), as the operator (I-2862). While the backup lock is held it does nothing. Otherwise it starts, inline:
  - **the nightly backup**, when backups are set up and no backup has started since the latest time the `hour` setting came in the site's time zone (today's, or yesterday's before the hour). A failed or abandoned backup counts as that night's, so a crashing backup isn't started again every minute. A server off at the hour backs up when it's back, and a changed hour applies at once;
  - **the weekly prune**, when that night's backup has started and no prune has in the last seven days;
  - **the nightly read-back** (I-2957), when backups are set up and nothing is paused, that night's backup has started, and no read-back has since;
  - **the weekly test restore**, when a spare database is named (I-2406), backups are set up and nothing is paused, that night's backup has started, and no test restore has in seven days.
  A failed or abandoned check counts as that night's or that week's, so one that crashes isn't started again every minute. It exits 1 when what it started failed. It catches only `BackupAlreadyRunning`; any other refusal is an error the scheduler's log shows. **It also raises the backups' alert** at the start of every minute and after its work, even while the lock is held (*The verdict and the alerts*).
- **A media file deletion waits for a backup or a check** (I-2864, I-2868, I-2952): `DeleteMediaFiles` asks `BackupLock::isHeld()` first, and while a backup, a prune or a check holds the lock it releases itself for 60 seconds and deletes nothing. It waits up to a day, and waiting never spends one of its five tries (`$maxExceptions`). On its last wait it queues a fresh copy of itself, so **a deletion is never lost**. **`VariantMaker::discard()` goes through it too** (I-2867), so a variant replaced mid-backup, by a new file or a moved focal point, stays until the backup ends. The nightly read-back and the weekly test restore hold the lock too, so a deletion also waits an hour or so a night while the backups are checked, well inside its day. On the `sync` queue Laravel drops a released job; production's queue isn't `sync`.

## Tools › Backups

**Tools › Backups** (`tools.backups.index`) is where an administrator sets backups up and looks after them (I-364). Its controllers are in `App\Http\Admin\Tools\Backups`, behind `can:backups.manage`, and call the Operations above; none writes a table itself. The screen reads `backup_destinations`, `backup_runs` and `backup_keys` and never asks restic (`BackupsScreen`). Dates and "what's kept" are put into words on the server (`BackupWords`), so the screen, the banner and the email say the same thing. The Tools hub lists it first, with the `archive` icon (I-2989), and `/admin/settings/backups` leads to it.

- **The verdict leads** (I-2409, I-2977). The lead is the first of these that holds: backups aren't set up (a panel with *Set up backups*); set up, but the recovery key was never typed back ("Backups aren’t set up yet: the recovery key shown for {place} wasn’t typed back.", with *Show a new recovery key* and *Remove {place} and start again*, I-2994); the places are paused (below); otherwise `BackupStatus::verdict()` through `BackupsScreen::verdictLine()`. **Red** leads with the first problem and lists the other problems, then the cautions. **Amber** leads with the first caution. Both are the verdict's own sentences, word for word. **Green** is the screen's own: "Backed up {when}, on this server and off it, and checked." A level is an icon and words, never a colour alone.
- **Under the lead**, in the same block: a backup or prune that is running (read from the `running` rows, never from the lock), the newest backup's figures, and "Next backup {when}. {Kept}" with *Change*. **Back up now** (1.12i, I-361, I-3170) is the header's button and a line in the same block: it puts a backup in line as a tracked job (`RequestBackup`), which `teme:backup:due` starts within a minute as whoever asked (`RunDueBackups`); the line follows it step by step, with Cancel, and Tools › Jobs shows it with Retry. A site with no backup yet can use it, or run `php artisan teme:backup:run` at the server.
- **The hour and what's kept sit beside the next backup** (I-2981, I-2982). *Change* opens the hour, a select of the 24 hours, and the three counts inside the sentence they make: "Keep a backup from each of the last [7] days, then one from each of [4] weeks before them, and one from each of [12] months before those." **`ChangeBackupSchedule`** saves them. It checks each value by the group's own rules and writes through `SettingsWriter` against the version the form was opened on, so a change made by someone else meanwhile is refused. The group is sensitive, so the change is logged.
- **The places** (I-2983), oldest first: the name, the kind and address (never a credential), the state as an icon and a word, the newest backup there, when it last answered, its `last_error`, and the recovery keys it doesn't open yet. Each has **Test**, **Change**, **Remove** and **What it holds**; **Add a place** sits under the list. Under them, **the latest checks** (I-2984): the newest finished run of each check kind at each place, as a sentence.
- **What a place holds is asked for, not stored** (I-2986). Nothing records it, and the screen must not run restic when it opens. **`PlaceStorage::measure()`** opens the place with the machine key and runs `restic stats --mode raw-data` (60 seconds). It writes nothing, so it is a query and asks no password; its route allows six a minute.
- **The password is asked first, where a secret will be typed** (I-2974). The pages that take a key or a credential (`set-up`, `sftp`, `places/new`, `places/{place}/edit`, `keys/new`) pass through **`RequireFreshPassword`**. It sends the person to Fortify's password page, and back, when the confirmation is older than `security.elevation_minutes`: the window the Operations use, not Fortify's own. So a refused form never asks twice. The short forms (Test, Remove, the hour, Replace, Add my key) post as they are, and a lapsed confirmation meets the admin's usual answer. An SFTP place's first step asks through `Elevation::ensure()` before `ssh-keyscan` runs or a key pair is made. Typed-back groups and *Check my recovery key* answer 423 instead, and the page asks for the password in place, posting it to Fortify's `password.confirm.store`, so a key shown once is never lost by leaving the page.
- **A recovery key reaches the browser once** (I-2975). `SetUpBackups`, `AddRecoveryKey` and `ReplaceRecoveryKey` return a `ShownRecoveryKey`, and **`RecoveryKeyPage::show()`** answers that same POST with the page `tools/backups/recovery-key`. The page's props carry `RecoveryKey::groups()` and nothing else of the key. They never pass through a redirect, the session, a flash, the cache or a log. The response is `Cache-Control: no-store, private` and calls `Inertia::encryptHistory()`, so the browser's history keeps the props only under a key held in `sessionStorage`. Confirming the key calls `Inertia::clearHistory()`, which throws that key away. There is no *Copy* button, since a clipboard keeps what it is given; the page offers *Print this key*, a sheet drawn for paper.
- **Only over HTTPS** (I-2995). History encryption needs a secure context. So before any Operation that makes a key, `RecoveryKeyPage::ensureSecure()` refuses a plain connection, unless the host is `localhost`, `127.0.0.1` or `[::1]`. A key page that threw would leave a key shown to nobody.
- **The challenge waits in the session, and nothing else of the key does** (I-2976, I-2996). The session's `backups.challenge` holds the `RecoveryKeyChallenge` as an array: no part of the key. The key page sends back a `challengeId`, the first 16 hexadecimal characters of the SHA-256 of the challenge's pending map, with the two groups; `key/confirm` (ten a minute) refuses groups typed for another key. When the screen opens and the challenge is still pending at every place, it offers the two group fields ("If you wrote {label} down, type groups {a} and {b} to finish."), so a person who closed the tab need not start again. Otherwise it drops the challenge.
- **Refused forms keep no secret** (I-2980). `dontFlash` in `bootstrap/app.php` lists `recovery_key`, `groups`, `access_key_id`, `secret_access_key` and `private_key`, so a refused form puts none back in the session's old input.
- **An SFTP place takes two steps** (I-2979). The first reads the server's host key and makes the key pair (a changed place keeps its own). **`SftpSteps`** keeps one entry in the session, `backups.sftp`: the fields, the host key and fingerprint, the public key, and the private key **encrypted under `APP_KEY`**, since sessions are stored rows. The entry never reaches a page; the page gets the public key and the fingerprint. The second step shows both, and its POST rebuilds the `NewPlace` and calls the Operation. The entry goes when the Operation succeeds, on *Start again*, when another place form is sent, and after 60 minutes ("That step has expired. Start again.").
- **The request waits for restic** (I-2978). Setting up, adding or changing a place, a key change and Test run restic inside the request, with `set_time_limit(0)` and `ignore_user_abort(true)` (`WaitsForRestic`). They can't be queued: every key and place Operation asks for the password, a queued job has none, and a `NewPlace` or `RecoveryKey` refuses to be serialized. Nothing streams progress, since the Operations make their restic calls inside one transaction. A request that gives up loses nothing: each Operation either committed or wrote nothing, and a key shown to nobody stays pending, to be swept by the next setup or key change.
- **The keys' actions.** *Check my recovery key* runs `CheckRecoveryKey` and answers JSON: the key's label and the places it opens and doesn't. *Add another key* asks for a label (`keys/new`), then shows the new key as at setup. *Replace*, beside each label, shows a new key under the same label; the old one stays until two groups of the new one are typed back. *Add my key to new places* appears only while a label misses a place, and runs `ExtendRecoveryKey`. The same key page serves all of them.
- **The pause after a restore** (I-363, I-2990). While any place is paused, `BackupsScreen::setupState()` answers `paused`, the screen draws no verdict, and the lead is red: "Backups are paused since this site was restored, until someone says whether this server is now the site." Under it are **This server is now the site** and **This is a copy: remove these backup places**, each after a confirmation that says what it does. `RestoredSiteController` passes the answer to `ConfirmRestoredSite`, which asks the password. This replaces the verdict's "At the server, php artisan teme:backup:restored says which."; the banner and the email keep that sentence. A paused place reads "Paused since the restore". *Change*, *Add a place* and the key buttons are hidden, since their Operations refuse; *Test*, *Remove* and *What it holds* stay.
- **Restoring is a line, not a control** (I-2988): the screen's last section says to run `php artisan teme:backup:restore` at the server.

## What it costs

Measured by 1.12z on a 4-vCPU cloud container, 40,000 images in 240,000 files and 200,000 items, every file at a tenth of its size (`docs/benchmarks/v0.1.0-rc.12-backup.md`, I-367):

- **A first backup** took 61.4 s and a nightly one 56.3 s, under 165 MB of PHP memory; the media step took 26.8 s for 2.6 GB, so about 270 s at full size (26.3 GB) on that machine, plus whatever a place off the server's link adds.
- **The weekly test restore** took 123.5 s; **a full restore onto an empty server**, with a new `APP_KEY` and address, 120.9 s from start to end, its re-encryption 0.7 s of it.
- **Spare disk:** a backup needs none (the dump streams into restic); the test restore needs room for the dump (about 150 MB here) and a spare database the size of the site's (2.9 GB here); a restore needs room for the dump and the media.

## Testing

**The tests run the real restic, `pg_dump` and `pg_restore`, and fail rather than skip without them** (I-2400): a backup test that skipped would pass a gate that proved nothing. Every place tests run has them: a developer's computer through its two `.env` lines, the cloud containers through `scripts/cloud-setup.sh`, and CI through its own step. `TemporaryRepository` makes a real repository in a fresh temporary folder. `ScriptedRestic` stands in only for what restic can't be made to do on demand: exit statuses 2, 3 and 130, and a timeout.

## For later parts

- **A restore (1.12f) leaves every place it brings back paused until a person confirms this server is now the site**, so an old server and a restored one never both write into one place under `--host teme`.
- **The installation (1.13) makes the spare database** (I-2406): any name ending `_verify`, made from `TEMPLATE template0` so it holds nothing the site's account can't remove, owned by that account (which needs no right beyond owning it), and named in `TEME_VERIFY_DATABASE`, with `TEME_VERIFY_DB_HOST`, `_PORT`, `_USERNAME` and `_PASSWORD` when it lives elsewhere than `DB_HOST`; a separate server keeps the weekly restore's load off the live one. A site configured by a `DB_URL` alone must name the host. `storage/app/verify` needs room for one copy of the database's dump during the test restore. The scheduler and mail must run for the alert email to be sent.
