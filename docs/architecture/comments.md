# Comments

Readers comment on published posts and pages, and whoever looks after an item's comments approves, holds, marks as spam, trashes, restores and deletes them. Slice 1.8 is built, in eight parts: 1.8a built the storage, submission and moderation, 1.8b the thread and the form, which work with no JavaScript, 1.8b′ core's script for them, 1.8c the Comments screen and its moderation, and 1.8c′ editing, replying, emptying and the keys; 1.8c″ the thread's Edit link, 1.8d Settings › Discussion, the comment emails and erasing commenters' addresses, and 1.8d′ the item's Discussion row, Quick and Bulk Edit's, and the benchmark at study S's scale. The evidence is study S (`docs/studies/comments.md`), and the design is 1.8a's plan (`docs/superpowers/plans/2026-09-30-phase1-slice08a-storage-and-submission.md`, D1 to D17 are I-575 to I-591), 1.8b's (`docs/superpowers/plans/2026-09-30-phase1-slice08b-thread-and-form.md`, D1 to D20 are I-599 to I-618) and 1.8b′'s (`docs/superpowers/plans/2026-10-01-phase1-slice08b2-comments-script.md`, D1 to D19 are I-620 to I-638) and 1.8c's (`docs/superpowers/plans/2026-10-01-phase1-slice08c-comments-screen.md`, D1 to D26 are I-654 to I-679) and 1.8c′'s (`docs/superpowers/plans/2026-10-01-phase1-slice08c2-edit-reply-empty.md`, D1 to D19 are I-728 to I-746) and 1.8d's (`docs/superpowers/plans/2026-10-07-phase1-slice08d-discussion-settings-emails.md`, D1 to D17 are I-773 to I-789) and 1.8d′'s (`docs/superpowers/plans/2026-10-07-phase1-slice08d2-discussion-row-benchmark.md`, D1 to D19 are I-810 to I-828); this document describes the system as built and is what the code is checked against.

## The tables

```
comments       id                    char(26) PRIMARY KEY  -- a ULID made from the moment it was written (D16)
               content_id            char(26)              -- the item; deleting it takes the thread
               parent_id             char(26) NULL         -- the comment it answers
               path                  text COLLATE "C"      -- its ancestors' IDs and its own, each followed by /
               depth                 smallint              -- 1 for a comment that starts a thread
               kind                  varchar(16)           -- comment | pingback | trackback
               status                varchar(32)           -- a key in the statuses registry
               previous_status       varchar(32) NULL      -- where it was before the trash or spam (D10)
               author_name           varchar(255) NULL
               author_email          varchar(254) NULL     -- lower-cased, as it's compared (D9)
               author_url            varchar(200) NULL
               author_user_id        bigint NULL           -- the writer's account; set null when it's deleted
               body                  jsonb NULL            -- the restricted document (I-267)
               commenter_token_hash  char(64) NULL         -- the SHA-256 of the browser's token, never the token
               ip                    inet NULL
               user_agent            varchar(255) NULL
               legacy_id             bigint NULL           -- WordPress's comment ID, on an imported comment
               moderation            jsonb NULL            -- what judged it as it arrived
               status_changed_at     timestamptz(6)        -- when its status last changed, to the microsecond (1.8c′'s D2)
               created_at, updated_at  timestamptz

               INDEX (content_id, path) WHERE status IN ('approved', 'removed')   -- comments_thread: the thread (D2)
               INDEX (content_id, status, id)                                     -- comments_item_status: newest approved, per-item lists
               INDEX (parent_id) WHERE parent_id IS NOT NULL                      -- comments_parent: has it replies?
               INDEX (author_email, content_id) WHERE author_email IS NOT NULL    -- comments_email: duplicates, returning guests
               INDEX (author_user_id) WHERE author_user_id IS NOT NULL            -- comments_user: returning accounts
               UNIQUE (legacy_id) WHERE legacy_id IS NOT NULL                     -- comments_legacy
               INDEX (content_id, path) WHERE depth = 1 AND status IN ('approved', 'removed')  -- comments_conversations: pages (1.8b's D2)
               INDEX (created_at) WHERE ip IS NOT NULL OR user_agent IS NOT NULL   -- comments_addresses: the daily erasure (1.8d′'s D10)

comment_stats  content_id        char(26) PRIMARY KEY  -- the item; deleting it takes the row
               approved_count    integer               -- never below nought
               pending_count     integer               -- never below nought
               thread_count      integer               -- the conversations its pages show (1.8b's D2); never below nought
               last_comment_id   char(26) NULL         -- the item's newest approved comment
               last_comment_at   timestamptz NULL      -- its created_at: both set, or neither
```

- **A thread is one sort (I-272).** A comment's `path` is its ancestors' IDs and its own, each followed by `/`, in the C collation, so `ORDER BY path` is display order with no lock and no counter. Each ID is a lower-cased ULID made from the moment the comment was written (`Str::ulid(now())`, D16), so the oldest comes first and a reply sorts under the comment it answers. `comments_path_check` holds the shape: 27 characters a level, and the last level is the row's own ID.
- **The words are a restricted Tiptap document (I-267), never HTML** (rule 7). Readers type plain text; `CommentText::toDocument()` ends a paragraph at a blank line, keeps every other line break and links the web addresses, reading nothing else as formatting. `CommentDocument::validate()` holds what may be stored: paragraphs and quotes, line breaks, and text that is bold, italic, inline code or a link, at most 2,000 nodes with quotes three deep. The formatting beyond that is there for imported comments (1.11). A link to a page on this site is stored by its item's ID and nothing else (rule 9), and an address on the site that names no item isn't linked; any other link is `http`, `https` or `mailto`.
- **A tombstone keeps its place and nothing else (I-278).** A comment deleted for good while it has replies becomes `removed`: its ID, item, parent, path, depth, kind, times and `legacy_id` stay, so the thread keeps its shape; `comments_tombstone_check` requires its words, its writer's name, email address, website and account, its IP address, browser, token hash, moderation record and remembered status to be null. `comments_words_check` requires every other comment to have words.
- **Pingbacks and trackbacks are never accepted (I-277).** `kind` holds them only so that 1.11 can keep the ones a WordPress site has; `SubmitComment` writes `comment`. The kinds are a closed set with a `CHECK`; statuses are a registry with none (D15).
- **Editorial notes never share this table (I-279).** WordPress 6.9 put its notes in `wp_comments`, and every reader query now has to leave them out; when notes come (I-066) they have a table of their own.
- **Deleting an item for good takes its comments and its counts in one statement.** Both tables cascade from `contents`. `parent_id` and `last_comment_id` take no action on delete, so PostgreSQL checks them at the end of that statement, when the whole thread is gone. Trashing an item changes none of its comments: WordPress rewrites every one to `post-trashed` and back, and Teme leaves a trashed item's comments out by a join where it counts them (1.8c).

## Statuses

`CommentStatusRegistry`, filled once at boot like the other registries (I-566), holds core's five. A key starts with a letter and holds lower-case letters, digits and hyphens, at most 32 characters. Phase 5 opens the registry to plugins, which is why `status` has no `CHECK` (D15), as `contents.type` has none.

| Status | In the thread (`shown`) | A moderator may move a comment there (`settable`) | Deleted for good from it (`deletable`) |
|---|---|---|---|
| `pending` | no | yes | no |
| `approved` | yes | yes | no |
| `spam` | no | yes | yes |
| `trash` | no | yes | yes |
| `removed` | yes, as a tombstone | no | no |

WordPress's `comment_approved` holds `0`, `1`, `spam`, `trash` and `post-trashed`: a 2003 boolean column that later took words. Teme stores words from the start, and has no `post-trashed` (above).

## The counts

`comment_stats` is one row per item that has had a comment (I-273): typed columns, never a key-value table (rule 2), as Drupal's `comment_entity_statistics` is.

- **One seam (D5).** `CommentStats::apply($comment, $before, $after)` is the only place a comment's change of status reaches the counts, called by every comment Operation inside its own transaction, after it writes the comment's row; either side is null for a comment written or deleted. Only `approved` and `pending` are counted: spam, the trash and tombstones count nowhere.
- **The conversations** (1.8b's D2): `thread_count` counts the comments at depth 1 that are approved or a tombstone, moved by the same `apply()`, and by `DeleteCommentPermanently` for each tombstone it deletes, so a page knows how many pages its thread has without a `COUNT`.
- **The last comment** is the item's newest approved comment by ID, so a comment approved late never takes a newer one's place. When the last one leaves `approved`, the newest still approved takes its place, through `comments_item_status`, or none does.
- **A drifted row fails loudly.** The upsert starts a new row at the change, never below nought, because PostgreSQL holds the proposed row to `comment_stats_counts_check` before it finds the conflict (B-348). A row that has drifted from the comments, and that a change would take below nought, is refused by the `CHECK`: the Operation writes nothing, and `teme:counts:rebuild` repairs the row.
- **`teme:counts:rebuild`** recomputes every item's counts, conversations and last comment from the rows beside the other maintained counts (I-141), reports the items that differ, and rewrites `comment_stats` when not run with `--check`. 1.11's importer loads comments with the counts left alone and runs it after (study S §3.2). A fixed comment count purges every page, since a thread's heading and pages show them.

## Where comments are allowed

Three things decide it, the widest first, and the settings decide how a new item starts.

- **The switch.** `modules.comments`, `on` or `off`, in the `modules` settings group (study H), and on by default for new and existing sites (I-574). Off, `SubmitComment` refuses with "Comments are switched off."; stored comments are kept for when it's switched back on, and from 1.8b readers see nothing of them (I-484).
- **The type.** `ContentType::$comments` (D7): null takes none, and `Discussion::Open` or `Discussion::Closed` is how the type's new items start. `ContentTypeRegistry` refuses comments on a type that isn't public, and a Hidden start (I-572): on a new item Closed and Hidden look the same. Posts start Open, pages Closed; regions take none.
- **The item.** `contents.comment_status` (D8), `open`, `closed` or `hidden`, held by `contents_comment_status_check` and cast to `Discussion`. The column keeps the spec's name; WordPress's collides with a comment's own status, and in Teme the two are in different tables. The migration made existing items of a type that starts Open (posts) `open`, and every other item `closed`. After an item is created, `SetDiscussion` alone writes it, for whoever may publish the item (I-571; *One item's Discussion*).

A new item starts as `DiscussionSettings::forNewItem()` says, which `CreateDraft` asks: Open when its type takes comments and `discussion.open_for` names the type, and otherwise Closed.

`SubmitComment` takes a comment only on an item that is published, live, dated now or earlier, of a type that takes comments, Open, and within `discussion.close_after_days` of its date.

## The Discussion settings

A part declares the settings it reads (1.8a's D6): 1.8a the switch and nine in the `discussion` group, 1.8b `ask_website` and `per_page`, and 1.8d `email_moderators`, `email_authors` and `keep_ip_days` (1.8d's D6). `DiscussionSettings::current()` reads them afresh each time. Every page that reads the group carries its tag, `discussion` (1.8b's D6).

| Key | Default | What it does | WordPress's option, which 1.11 maps (D12) |
|---|---|---|---|
| `modules.comments` | `on` | Comments at all | none: a site with comments imports `on` |
| `open_for` | the types that start Open: posts | Which types' new items start Open | `default_comment_status` |
| `signed_in_only` | off | Guests may not comment | `comment_registration` |
| `ask_website` | on | The form asks guests for a website, and one given is kept (I-596) | none: WordPress always asks |
| `close_after_days` | 0, never (0 to 3,650) | Days after an item's date when it stops taking comments | `close_comments_for_old_posts` and `close_comments_days_old` |
| `thread_depth` | 5 (1 to 10) | How deep replies go | `thread_comments_depth`, 1 when `thread_comments` is off |
| `per_page` | 50 (1 to 200) | How many conversations a page of comments holds | `comments_per_page` (1.8b's D12) |
| `hold_all` | off | Every comment waits | `comment_moderation` |
| `approve_returning` | on | A returning writer is approved, a first comment held once (D11) | `comment_previously_approved` |
| `hold_links` | 2 (0 to 100; 0, never) | A comment with this many links waits | `comment_max_links` |
| `hold_list`, `block_list` | empty | A line found in a comment holds it, or sends it to spam (I-573) | `moderation_keys`, `disallowed_keys` |
| `email_moderators` | on | Whoever looks after an item is emailed when a comment on it waits (*The emails*) | `moderation_notify` |
| `email_authors` | on | An item's author is emailed when a comment on it is approved | `comments_notify` |
| `keep_ip_days` | 60 (1 to 365) | Days after a comment arrives when its IP address and browser are erased (I-270) | none: WordPress keeps them for ever |

**Settings › Discussion** (1.8d's D2 to D5, E1, E2) is a screen of its own at `settings.discussion`, behind `settings.discussion.manage`. Both the `discussion` and the `modules` group declare it as their `screen`, so Settings lists a Discussion tab and never a Modules one (I-485), `/admin/settings/modules` leads to it, and the generic `UpdateSettings` refuses both groups. The page has two forms, each saving its own group against the version it was opened on, so neither overwrites the other: the switch first, saved by `SwitchComments`, which checks `settings.modules.manage` and shows read-only to anyone else; then, while comments are on, every Discussion setting in v9's five fieldsets (`DiscussionScreen::FIELDSETS`, which a test holds to the group's settings), saved by `ChangeDiscussionSettings`. That refuses while comments are off ("Comments are switched off."), so the settings the page hides stay as they were. Both Operations check values through `SettingRules::validateValues()`, as `UpdateSettings` does. While comments are off, the Comments screen's page links to the switch for whoever may change it (D15).

## Who looks after an item's comments

`CommentModeration::allows($user, $item)` (I-483, I-570): whoever holds `comments.moderate`, on every item, and whoever may publish the item (`ContentPolicy::publish()`), which gives authors their own posts and contributors nothing. Pages are written by editors and administrators alone since slice 2.1f (I-3313), so a page's comments are looked after by them; an author's older page keeps its author's name and gives that author nothing. A stored type with its own permissions asks its own `publish`, and the comment emails go only to people who hold permissions Spatie can find (`CommentRecipients`). They moderate the item's comments, and their own comments there are approved at once, past the moderator and the rate limit, though not the duplicate check.

`comments.moderate` is held by editors and administrators. It reached existing sites through an add-only migration (I-449) that creates the permission and grants it to those two roles where they exist, never by re-running `RoleSeeder`, which resets the roles it names. There is no permission for authors' own items: publishing is it. `settings.discussion.manage` and `settings.modules.manage` reached administrators the same way in 1.8d, through `2026_10_23_100000_add_discussion_settings_permissions.php` (1.8d's D5, I-685); `RoleSeeder` lists both. From 1.8c, only `comments.moderate` holders see a commenter's IP address and browser (I-270).

## Submitting

`SubmitComment` checks in study S's order, cheapest first (§3.4), and writes nothing when it refuses.

| Step | What | Refusal |
|---|---|---|
| authorize | A guest (no actor) is allowed unless `signed_in_only`; an actor must exist and not be suspended | `AuthorizationException`, before anything else is read or counted |
| validate 1 | The switch is on | "Comments are switched off." |
| validate 2 | The fields, reading nothing: the text, trimmed, 1 to 5,000 characters; a guest's name (1 to 100) and email address (at most 254); a website, `http` or `https` (at most 200); the parent's ID; the browser's token (`^[A-Za-z0-9_-]{22,128}$`); the IP address | on the field |
| validate 3 | The item, one read by its key (above) | "This page takes no comments." or "Comments here are closed." |
| validate 4 | The rate limit, unless the writer looks after the item's comments (D13) | 429, "You've sent several comments in a short time. Try again in a minute." or "…in N minutes." |
| validate 5 | The document: `CommentText::toDocument()`, then `CommentDocument::validate()` | the document's error |
| validate 6 | The comment answered: there, on this item, approved | on `parentId` |
| validate 7 | A guest's name and email address aren't an account's (Drupal) | on `name` or `email` |
| validate 8 | The same words on this item from this email address (WordPress's duplicate check) | "You've already said that here." |
| perform | The comment answered, locked and checked again; where the reply goes; the verdict; the row; the counts, through `CommentStats::apply()` | |

- **The verdict.** Whoever looks after the item's comments is approved at once, recorded as Teme's, with the rule `looks-after`. Anyone else is judged by the moderator (below).
- **The returning-commenter rule** (`ReturningCommenter`, I-275). A signed-in writer returns when their account has an approved comment. A guest returns when an approved comment has the same email address and came from the same browser, whose token only that browser holds. A name and email address alone, which anyone can type, are never enough.
- **The rate limit** (`CommentThrottle`): five comments in ten minutes from one IP address, and five from one email address, counted by Laravel's rate limiter in the cache store as sign-in's are (study S §3.4, Emdash's figure). The email address is a SHA-1 in the key, so no key holds it. It replaces WordPress's flood check (`wp_check_comment_flood()`), which also lets moderators by; the duplicate check lets nobody by.
- **Where a reply goes (I-272).** Under the comment it answers, one level deeper. When that comment is at the deepest level `thread_depth` allows, the reply goes beside it, under its parent; under an imported comment deeper than that, it goes at the deepest level, under its ancestor there. So a new reply is never deeper than `thread_depth`, and a depth of 1 makes every reply a new thread. The ancestors are read from the answered comment's `path`, with no query.
- **The writer's details (D9).** A signed-in writer's name and email address are their account's, whatever the input says; a guest's are trimmed. Email addresses are lower-cased. The browser's token is kept only as its SHA-256; the browser's user agent is cut to 255 characters; the IP address is kept as `inet`.

## The moderator

A moderator judges each comment that isn't approved at once: `Teme\Contracts\Comments\CommentModerator`, the slot a spam checker such as Akismet takes in phase 5 (I-224). It has a `name()` and one method, `judge(CommentCandidate): ModerationVerdict`. The candidate carries the text, the links counted in it, the writer's name, email address, website and account, the IP address, the browser, whether the writer is returning, and the item's address. The verdict carries a status (`approved`, `pending` or `spam`), a reason and its signals. A status the Operation doesn't know is held, and reported.

**Core's moderator** (`BuiltInModerator`, bound in `CommentServiceProvider`; a plugin binds its own in its place):

1. a line of the block list found in the comment: spam;
2. a line of the hold list: held;
3. at least `hold_links` links: held;
4. `hold_all`: held;
5. `approve_returning` off: approved (D11);
6. a returning writer: approved; anyone else: held once, as a first comment or the first from this browser.

A list line is matched anywhere in WordPress's six fields (the text, the name, the email address, the website, the IP address and the browser), ignoring case (I-573). So the lists a migrated site brings keep catching what they caught, and a line such as `203.0.113.` holds a whole range of addresses. The hold list only holds, and a moderator can undo the block list's spam.

**The moderation record** is kept with the comment, so a moderator sees why it was judged as it was:

```json
{"by": "Teme", "status": "pending", "reason": "Held: the hold list has “casino”, found in the email address.", "signals": {"rule": "hold-list", "match": "casino", "field": "email"}}
```

**Core's moderator judges inside the transaction (D14).** It is local: the settings and one indexed query. Phase 5's slot must not call a network service there: when phase 5 designs the dispatcher, a moderator such as Akismet is judged before the transaction.

## Moderating, and deleting for good

Both Operations authorize through `CommentModeration::allows()` on the comment's item, trashed or not, and refuse a missing actor. Each works under a lock on the comment.

- **`ModerateComment`** moves a comment between `pending`, `approved`, `spam` and `trash` (I-224), or restores it with `ModerateComment::RESTORE`. A tombstone never moves. Moving into the trash or spam remembers where the comment came from in `previous_status` (D10, WordPress's `_wp_trash_meta_status`, a column rather than a meta row), keeping the first place when it moves between the two. Restoring, only from the trash or spam, puts it back there, or in `pending` when it remembers nothing, as an imported one doesn't. Moving it anywhere else forgets it, and asking for the status it has changes nothing.
- **`DeleteCommentPermanently`** deletes a comment in the trash or spam for good (I-278, D3). A comment with any replies, approved or waiting, becomes a tombstone, so a reply approved later never reads as an answer to something else. A comment with none is deleted, and then each tombstone above it left with nothing beneath, one by one up the thread, each locked in turn with the child's lock taken first, so two deletions under one tombstone can't deadlock. It returns `removed` or `deleted`.

## The thread

A theme is given an item's thread as view models (spec §5.9), never the rows. `CommentViews::forItem()` builds a `CommentsView` for one page, holding a tree of `CommentView`s, and `ArticleView::$comments` carries page 1. It gives nothing at all while comments are switched off, the item is Hidden or its type takes none (I-484, I-274), and a preview shows no comments, since they belong to the published item (D20).

- **A page holds conversations (D2).** A conversation is a comment at depth 1, approved or a tombstone, with every reply under it; a page holds `per_page` of them, oldest first. `comment_stats.thread_count` counts them, so a page knows how many pages its thread has without a `COUNT` on a public page (study S §3.11). A page's first conversation is found by position in `comments_conversations`, an index of those first comments alone (an `OFFSET`, bounded by `PathResolver::LAST_PAGE`), and the page is then read as one range of `comments_thread` between two paths (`CommentThreads::page()`). A numbered page's start can't be a key a link carries, since a conversation moves to an earlier page when one before it is taken down.
- **A comment shows only while every comment above it shows (D3).** A reply under a comment that waits, is spam or is in the trash is hidden with it, and comes back when that comment is restored or becomes a tombstone, as WordPress's threaded query does. `approved_count` still counts it, as WordPress's `comment_count` does.
- **The heading counts every approved comment, pings included (D4);** tombstones aren't counted.
- **Each place is a comment, a tombstone or a ping.** A tombstone keeps its place with nothing personal in it (I-278); a ping is one line (I-277); one imported from WordPress keeps its old anchor, `#comment-{legacy_id}`. The story's own author is marked "Author", known from the account, never from a name a guest can type (I-597). A reply says whom it answers, and the default theme shows that line once the indent stops, after three steps on a phone and four on a wider screen (I-595). A reply at the depth limit is stored under the parent of the comment it answers, so "In reply to" names that one (D11; keeping both is parked, I-598).
- **Nothing personal but a name and a website (D19).** The thread's query never selects an email address, an IP address, a browser, a token's hash or a moderation record.
- **Core draws the words** (`CommentBody`, I-267): paragraphs, quotes, line breaks, bold, italic, code and links, every word escaped. A link to another site is `rel="ugc nofollow"`, one to an item here is given its address now (rule 9), and only `http`, `https` and `mailto` addresses are ever drawn as links. The picture is the writer's initials on one of eight hues made from their name (`CommentPicture`, I-269), never a photo from another service.
- **Times are absolute,** on the site's clock, in Carbon's `LLL` for the item's language (D17): a relative time can't live in a stored page.
- **What a thread costs:** four statements whatever its size (the counts, the item's address, where the page starts, and the page), three on an article, which has read its address already, and one more for each item its comments link to. An item that shows none costs none once the request has read the settings.

## Addresses

- **Page 1 is the item itself,** at `#comments`; a later page is `{item}/comments/page/{n}/` (I-272), a stored page of its own, drawn through the theme's `templates.comments`, or core's plain page when the theme has none, never the theme's `index` (D10). Page 1's own address redirects to the item, a page past the last answers 404, and an old address redirects to the item's new one. A term called "comments" keeps its archive's pages: the rule answers only an address that names an item.
- **`/_teme/comment/{id}`** is a comment's own address: a 302 to the page its conversation is on, at `#comment-{id}`, found with one count over `comments_conversations`, and `no-store`, since that page moves when an earlier conversation is taken down.
- **`/_teme/comment/{id}/reply`** is Reply without JavaScript (I-594): the comment answered above a form of its own, never stored or indexed. It says beforehand when a reply at the deepest level will go at the end of its conversation (D11).
- **All of them answer 404 while comments are switched off,** and the comment addresses do for a comment no reader sees. WordPress's `/slug/comment-page-N/` addresses are 1.11's, which knows whether WordPress's paging came across (D12).

## The form and posting

**The form is core's component,** `<x-teme::comment-form>`, which a theme places and styles. Its fields and their names, the honeypot, the privacy line and every `data-teme-*` hook are core's, so no theme can lose one. It posts the item's address, `path`, never its ID (D9). The parts that need core's script, saving details, the signed-in name, the reply line and Cancel, are drawn `hidden`, and core's script shows them (*Core's script*).

- **The honeypot is a field named `subject`,** labelled "Leave this empty" (D8). No browser's autofill knows it, and bots fill it; `teme.core` keeps it off-screen with `!important` in every theme. A filled one is answered as held, and nothing reaches `SubmitComment` or its rate limit.
- **The privacy line** says what is kept and for how long: as many days as `keep_ip_days` holds, 60 by default, study S's figure (D13). `CommentFormView::$keepIpDays` is required, so every construction passes the setting, and a page that reads the `discussion` group already carries its tag, so changing the setting removes it (1.8d′). Its link waits for the site's privacy page (issue #32, I-611).
- **Where only signed-in people may comment** (D16), a browser without the sign-in marker gets a line in the form's place, and `SubmitComment` still refuses a guest.

**Posting is `POST /_teme/comments`,** outside the public group, behind `GuardCommentPost`, core's forgery rule (D7), since Laravel's compares tokens only in a session:

1. a `Sec-Fetch-Site` other than `same-origin` is refused, `same-site` too, as Laravel refuses it;
2. with no Fetch Metadata, an `Origin` other than the site's (`app.url`'s, or the request's own), `null` included, is refused;
3. a browser with no sign-in marker then posts as a guest, with no session read and no cookie set: it carries no identity to forge;
4. a marked browser has the reader group's session middleware run for this request alone, with its checks, and, signed in, must say the form is its own or send the session's token as `_token`, which core's script fills (*Core's script*). A marked browser with neither Fetch Metadata nor JavaScript can't comment, and is told so.

**Each outcome answers with a page of its own** (I-593), drawn through the theme's `templates.respond` in core's words, with `Cache-Control: no-store, private` and `noindex, nofollow` (D18). Posted and waiting answer 200, a waiting page covering held, spam and a filled honeypot alike (I-592). A form refused or with errors answers 422, the rate limit 429, and the guard and `SubmitComment`'s authorization 403. Every answer keeps what the reader wrote: the posted and waiting pages echo it, the "wasn't posted" page holds it in a read-only field, and a form with errors comes back filled in, what was wrong first. `SubmitComment` refuses in the form's own words (D14), takes a website typed without a scheme as `https://`, and keeps none while the site doesn't ask for one (I-596).

## The emails

Two emails, each a Laravel notification in `PasswordChangedNotice`'s shape (subject, lines, one button, inside Laravel's own layout and its greeting and sign-off, I-790), sent at once by a queued job (1.8d's D7 to D12, E5, E6):

- **"A comment is waiting for approval on “{title}”"** goes to everyone who looks after the item's comments when one arrives `pending` through `SubmitComment`: never for spam, one approved at once, or one a moderator moves back to pending. `CommentRecipients::moderators()` reads the candidates in SQL (holders of `comments.moderate`, holders of both the type's `publish` and `edit.any`, and the item's author) and keeps those `CommentModeration::allows()` passes. It carries the commenter's name, the comment's words, its stored reason, a button to the drawer and how many comments wait on the items the person looks after (`CommentsWaiting::countFor()`).
- **"New comment on “{title}”"** goes to the item's author when a comment on it becomes approved: as it arrives, when `ModerateComment` approves it (never by Restore, which puts back a comment shown before), and when `ReplyToComment` writes a reply. Never for the author's own comment or their own approval, nor once the item isn't published. A button reads it on the site, at `/_teme/comment/{id}`, and an author who looks after the item also gets a link to it in Comments.
- **Who gets one** is read when the job runs, never when it was queued: a verified account, not suspended, not the comment's writer, not the person whose action queued it (the job's `actorId`), and with their preference on. The job also checks again that comments and the email's setting are on, the comment still pending or approved, and its item out of the trash. An Operation queues a job only when it could send, and always after commit (`->afterCommit()`), so a change rolled back emails no one (D16).
- **The jobs** (`SendCommentWaitingEmails`, `SendCommentApprovedEmail`) call no Operation, write nothing and ask for no elevation, so they run under the queue's `DeniedElevation`; each runs once (`$tries = 1`), since a retry would email the first recipients again.
- **Nothing anyone else wrote becomes formatting** (D10): the name, the title and the reason pass through `MailText::inline()`, and the comment's words through `MailText::quote()`, a quoted block escaped for Markdown and then HTML. A comment reading `[Approve](https://evil.example)` arrives as those characters, not a link. The subject is a mail header, never Markdown, and is left as typed.
- **Links are made as the email is sent**, from `config('app.url')`, never stored (D11, rule 9).
- **Neither email carries** an IP address, a browser or an email address, or a one-click action: an emailed address outlives `keep_ip_days`, and a link that acts would act for whoever opens it (E5, E6).
- **The opt-outs** (D12, E7) are two preferences, `notifications.comment_waiting` and `notifications.comment_approved`, on by default. Account › Preferences draws them under "Notifications" (`CommentEmailChoices`): the waiting one to whoever looks after any item's comments, worded for them; the approved one to whoever holds `content.create`; neither while comments are off. While the site's setting is off, its box is disabled and sends nothing, so the person's own choice is kept.

## Commenters' addresses

A comment's IP address and browser are erased `keep_ip_days` after it arrives (I-270; 1.8d's D13), by `created_at`, whatever its status, imported comments on the first run. `teme:comments:erase-addresses` runs daily as the operator and calls `EraseCommentAddresses` a chunk at a time (`--chunk`, 1,000 by default) until a chunk erases fewer than it could; one statement sets both columns to null on rows that still hold either, skipping a row another transaction has locked. Nothing else on the comment changes, not `updated_at`, and no page is purged, since no public page shows an address. It reads `comments_addresses (created_at) WHERE ip IS NOT NULL OR user_agent IS NOT NULL` (1.8d′'s D10), whose condition is the statement's own, so the index holds only the comments that still keep an address, about `keep_ip_days` of arrivals however many comments there are, and no run reads every comment; the benchmark plans the statement and would fail a sequential scan.

The drawer says when (D14), to those who see addresses: under an address, "Erased on {date}, {N} days after it arrived", and "Erased with the IP address" under the browser; once both are gone and `keep_ip_days` have passed, "Erased", with "Kept {N} days, then erased". A reply written in the admin keeps "None: written in the admin", and a ping, which never had either, "None". `CommentDetails` carries `erasesAt` and `keptDays` for it.

## The page cache

Two tags, one of each kind the page cache knows (D5): `comments:{item}`, a list, recorded by every page that draws the item's thread; and `comment:{id}`, a thing, recorded for each comment drawn, tombstones and pings too. A change to a list sets its pages aside, served `STALE` while one request draws each afresh (study S §3.6); a change to a thing removes its pages, never served stale. Every page that reads the Discussion settings carries their tag, `discussion` (D6), so a change to how many conversations a page holds or how deep replies go redraws every thread. 1.8a's Operations tell the page cache through `purgeAfterCommit()`, and it purges after the outermost commit (rule 6):

| Operation | When | Purges | So the pages |
|---|---|---|---|
| `SubmitComment` | the comment is approved at once | `comments:{item}` | showing the thread are set aside |
| | held or spam | nothing | are unchanged: only its writer sees it (*Core's script*) |
| `ModerateComment` | into the thread (approved, restored to approved) | `comments:{item}` | are set aside |
| | out of it (to pending, spam or the trash) | `comments:{item}`, `comment:{id}` | showing it are removed; the thread's others set aside |
| | between statuses no reader sees | nothing | |
| `DeleteCommentPermanently` | a tombstone takes the comment's place | `comments:{item}` | are set aside: the comment was in the trash or spam, so a place appears |
| | tombstones above it go too | `comments:{item}`, `comment:{id}` of each | showing them are removed |
| | the comment alone goes | nothing | never showed it |
| `RebuildCounts` | it fixes a comment count | `*` | are all removed |

## Core's script

With JavaScript, the comment form keeps what a reader chose to save, shows a signed-in person the name they comment under, shows a reader their own comments that wait, moves under the comment answered when Reply is pressed, and posts without leaving the page. Without it, everything is as 1.8b built it. The script is core's, never the theme's (1.8b′'s plan, D1 to D19).

- **Where it's drawn (D1, D2; amended by 1.8c″'s D3).** It is inline, as 1.7c's session script is, and `<x-teme::thread-script />` pushes it once onto the shell's `teme-core-scripts` stack, drawn right after the session script. The comment form uses the component, and so does a theme that draws a thread with no form: the default theme places it after "Comments are closed.". So a post, a later page of comments, the reply page, an answer page and a closed item that has comments carry it; a closed item with none, a list, the front page and a page that takes no comments don't, and nor does the line shown to guests where only signed-in people may comment. A closed thread's page carries about 4 KB of inline script for readers who will never use it; the benefit is Edit there. It is the same for every reader and names no item, so a stored page stays shared and a content security policy can allow it by its hash. With the session script it stays within 5 KB compressed (study Q §4, I-253), which a test holds. It finds the `data-teme-*` hooks of the default theme's drawing and core's form's own ids, never a theme's classes.
- **One question to `/_teme/session` a page (D3, D4).** The session script keeps its answer as a promise under `document[Symbol.for('teme.reader')]`, and the comments script reads it. The answer gains `name`, the account's name, which `SubmitComment` stores for a signed-in writer whatever the form says. The form then hides its guest fields, shows "You’re signed in, so you’ll comment as …" with the name set as text, and fills its `_token` from the answer's `token`, which `GuardCommentPost` asks of a signed-in browser that sends no Fetch Metadata.
- **The key, and what is saved (D5).** At a browser's first post the script makes 24 random bytes from `crypto.getRandomValues()`, written as base64url (32 characters), and keeps them in local storage as `teme-commenter-key`, whether or not the box is ticked, as the drawn words say. The reader's name, email address and website are kept as `teme-commenter` only while the box is ticked; a post with it unticked forgets them. The key is sent as the form's `token` with every post, a signed-in person's too, and only its SHA-256 is ever stored (`CommenterToken`, which `SubmitComment`'s rule and the pending read share). Where local storage can't be written, the box stays hidden and no key is made: the form posts as it does without the script, and a guest's comment is held, as in 1.8b. A browser that never posts makes no key and asks nothing about its comments.
- **This browser's own comments (D6, D14, D16, D17).** `GET /_teme/comments/pending?path={the item's address}`, with the key in the `X-Teme-Commenter` header, never the address, which lands in logs. It answers `{"comments": [{"id", "parentId", "html"}]}`, `no-store, private`, with no session and no cookie: the comments this key wrote on the item that wait (pending, and spam, which reads as held, I-592), and those approved since a stored page could have been drawn (within `PageCache::lifetime()` plus its render window), at most 20 (`CommentThreads::OWN_LIMIT`), the newest, in path order. The item is found by its address as a post finds it (a current or an old one, never an ID, 1.7c's D11), and a key that isn't one answers `[]` before anything is read. The partial index `comments_token (commenter_token_hash, content_id)` finds them. It is not throttled, as `/_teme/session` isn't, since only a browser that has posted asks, once a page with a thread. Each comment is drawn by the theme's own `partials.comment` from the thread's own view model (`CommentFragments`), `pending` for one that waits, and carries nothing a thread doesn't show: never an email address, an IP address, a browser or a key's hash. The script sends the question with `credentials: 'omit'`.
- **The post's JSON (D8, D9).** `POST /_teme/comments` answers JSON when it is asked for (`Accept: application/json`), beside its pages, with the pages' statuses and `no-store, private`: `{"outcome", "message", "comment", "form"}`. `posted` and `waiting` (held, or spam, or a filled honeypot, which keeps nothing and so has no comment) carry the design pass's status words, "reply" for a reply, and the comment's place; `invalid` and `refused` for a known item carry core's form drawn again as a thread draws it, the reader's words kept and what was wrong first. The script posts by `fetch` only where the page has a thread to put the comment in; on a page of its own (the reply page, an answer page) the form posts the ordinary way. A post the network lost keeps the words and says "Your comment wasn’t sent. Check your connection, then try again." An answer that isn't core's JSON (an error page, a redirect from the guard's session checks, which `redirect: 'manual'` catches) posts the form the ordinary way, so the server's own page answers; the duplicate check keeps a comment from being written twice. The body is sent urlencoded, which every server parses.
- **Where a comment goes (D7, D10).** After a post, where the reader is: a reply at the end of the replies of the comment it's stored under (beside the one answered at the deepest level), a comment at the end of the thread on the page shown, page 1 of several included, though it lives on the last. From the pending endpoint: a reply under its comment wherever that is shown, a comment of its own at the end of the thread only on the item's own page, never one the page has already, and a reply whose comment isn't on the page is left out.
- **The one form moves (D11, D12, D13).** A plain click on Reply (a modifier key or another button opens the reply page as a link) leaves a hidden placeholder where the form was and puts the form inside the comment's `[data-teme-comment]`, before its replies. The heading becomes the Reply link's own words, the label "Your reply", the button "Post reply", and Cancel shows. At the thread's deepest level the line "Replies stop nesting here, so yours will appear at the end of this conversation." shows. Cancel, or Escape with focus in the form, puts it back, with focus on the Reply it came from; Ctrl or Cmd with Enter in the text posts. While posting, the button is `aria-disabled` and the status region says "Posting your comment…"; after it, the text is emptied, a moved form goes home, focus goes to that Reply or stays on the button, and then the status region speaks the answer's words, set a moment after focus moves so a screen reader reads both.
- **What it puts in the page (D18).** Only HTML core's server drew, parsed inert in a `<template>` and moved into place; anything else it shows, the signed-in name, the status words, the Reply link's words, is set as text, and it follows no address an answer gives. Every ID put in a selector goes through `CSS.escape()`. The words reach it through `@json` with Blade's own flags, which keep any word from closing the script.
- **Edit on the thread (1.8c″, D1, D2, D4 to D7).** `/_teme/session` answers `moderate`: the Comments screen's address, `/admin/comments`, when the signed-in person looks after the comments of the item the page's path shows (`CommentModeration::allows()`: whoever holds `comments.moderate`, and whoever may publish the item), else null. It is one string for every item and never names one, so a stored page still carries no ID; the script builds `{moderate}?comment={id}` from the IDs the page already holds as anchors, and uses `moderate` only when it is a path on this site. A later page of an item's comments, `…/comments/page/N`, counts as the item for this answer (`PathResolver::COMMENTS_PAGE`); the "Edit post" link stays as 1.7c built it. The default theme draws `<p data-teme-actions="{Name}">` on every comment that isn't waiting, `hidden` while it holds nothing (Reply is inside it while offered), and none for a waiting comment, a tombstone, a ping or the comment a reply page answers. The script puts the link in that line and shows it, so a closed thread gets Edit and no Reply. **A theme without the hook** gets the link in a `<p>` before the comment's replies, only on a comment whose own Reply is drawn, so a waiting comment, a tombstone and a ping, which a theme's hooks can't otherwise name, get none; the price is that a closed item gets no Edit there until the theme adds the hook. The link says "Edit", and for screen readers " {Name}’s comment" (" comment" without a name); the name is set as text and replaces `:name` through a function, so a `$&` in it is literal. A second run places nothing twice (`data-teme-edit`). Core's layer keeps `[data-teme-actions][hidden]` and `[data-teme-empty][hidden]` hidden whatever a theme's `display` says, and the link a target at least 1.5rem each way.
- **The empty line and the count (1.8c″, D8).** The default theme hooks its heading `data-teme-count="{n}"` (the approved comments as drawn) and its empty line `data-teme-empty`. After a post whose outcome is `posted` the script hides the line, adds one to the count and rewrites the heading ("1 comment", "{n} comments", en-US thousands). After `waiting` it changes neither: the heading counts approved comments as everyone sees them (I-639). The pending endpoint's comments don't move the count. A theme without the hooks is left as it is.
- **Size (D10).** Core's two scripts, compressed: 3,716 bytes before 1.8c″, 4,279 after (14,633 and 16,993 uncompressed), against the 5,120 ceiling.
- **Tested without JavaScript (D19).** The Browser suite runs the no-JavaScript paths with Playwright's `javaScriptEnabled: false`, which `visit()` passes to the browser's context.

## The Comments screen

Whoever looks after comments opens `/admin/comments` from the menu (1.8c; its calls, D1 to D26, are I-654 to I-679, the design pass's, C1 to C11, I-641 to I-653). It lists comments a page at a time, narrows them to one post or page, searches them, moves them between statuses alone or in bulk with Undo, deletes them permanently after a confirmation, and opens one comment's details and the moderator's judgement in a drawer. 1.8c′ adds Quick edit, the inline reply, Empty spam and Empty trash, and the keys (the last bullets below; its calls, D1 to D19, are I-728 to I-746).

- **Who sees what (D2, D14, D18, C1, I-270 B).** `CommentScope::forViewer()` reads a person once and restates `CommentModeration::allows()` as SQL over `contents`: whoever holds `comments.moderate` looks after every item; anyone else, for each type that takes comments, after the items of the types whose publish ability they hold, every one with the type's `edit.any` too and their own without it. Every read on the screen, the badge, Home's figure and the column's waiting count goes through it, so an author's numbers are their own items' and agree with their list; `CommentScopeTest` compares it with the policy row by row. Its one divergence: an item of a type no longer registered is looked after by `comments.moderate` holders alone. The route's gate is `look-after-comments`, a gate ability that this rule answers, never a permission (I-570). The rows and the drawer carry an IP address and a browser only for `comments.moderate` holders, null for everyone else, and a search never looks at addresses for anyone else (I-270 B); names, email addresses and websites are everyone's who looks after the item.
- **Views and counts (D3 to D5, C10).** All, Pending, Approved, Spam and Trash, in the registry's order; All is Pending and Approved, as in WordPress. A visit with no view opens Pending. Comments on items in the trash are left out of every view, count, the badge and Home's figure, by a join on `contents.deleted_at IS NULL`; they come back with their item. The counts are two statements whatever the list shows: Pending and Approved summed from `comment_stats`, Spam and Trash counted from `comments` through `comments_parked`. They follow the item the list is narrowed to, never the search. A tombstone is never listed (I-278).
- **Pages and search (D6, D7).** Keyset pages, newest first, by `comments.id`, a ULID from the clock, so every view's index ends in it and a page costs what page one costs; the page size is the person's `lists.per_page`. The search reads the words readers see: the text of every text node of the stored document, in document order and joined with nothing between them, so a phrase across bold or a link matches, and never a key or an attribute; the name, the email address, the website; and the IP address for `comments.moderate` holders. Case is ignored and `%` and `_` match as typed.
- **The indexes (D8).** `comments_waiting (id) WHERE status = 'pending'` serves the Pending view, `comments_inbox (id) WHERE status IN ('pending', 'approved')` All and Approved, `comments_parked (status, id) INCLUDE (content_id) WHERE status IN ('spam', 'trash')` Spam and Trash and their counts as index-only scans, and `comment_stats_waiting (content_id) INCLUDE (pending_count) WHERE pending_count > 0` the badge and Home's figure. An item's own views use `comments_item_status`. 1.8d′'s benchmark reads their plans at study S §3.11's scale (`docs/benchmarks/v0.1.0-beta.8.md`).
- **Moving comments (D9 to D11, D23).** Moderation is one `ModerateComment` per comment, at most 100 a request, each authorized on its own, the person read once for the batch through `Actors`; never one bulk Operation, so what learns from a moderation meets every change. `ModerateComment` returns a `ModeratedComment`: the comment's ID, its status before and after, read under the Operation's lock, and its writer's name. A comment that can't be moved (deleted meanwhile, an item that changed hands, a tombstone) is counted and named in the toast, never dropped. Undo is the toast's: the flash toast carries an optional `undo` (an address and the reverse moves, each comment back to the status the Operation found it in, never the one the browser last saw), the toast stays ten seconds, and the answer to an Undo says "Undone." and offers none. Nothing is kept on the server between the two. A move answers with a redirect to the list as it was: the view, item, search and cursor of the request's Referer and nothing else, so a comment deleted from its own drawer never answers 404.
- **Deleting for good (D12).** One `DeleteCommentPermanently` per comment, deepest first, so a comment whose replies are all in the selection is deleted outright, never made a tombstone that the next deletion removes again. The confirmation counts, from the rows on the page, the selected comments that will keep a place because a reply stays; the toast reports the tombstones the Operations made. A comment opened by its address and not among the page's rows is counted from the drawer's own reply count, so the confirmation says what will happen whichever page it opens on (B-367); when every comment selected keeps a place, it says so (B-368).
- **The drawer and its address (D13, C7).** `/admin/comments?comment={id}` opens the Comments screen with the comment's details over it, with the list's own query as it was; with no `view` it opens the comment's own status's view, so an email's link (1.8d) lands on the list it's in. Opening and closing it reload the `details` prop alone. A comment that doesn't exist or is a tombstone answers 404; one on an item the person doesn't look after is refused as the item is. `?item={id}` narrows the list to one item. The public thread's Edit link, 1.8c″'s, opens `?comment={id}` (C9), this drawer, and not the narrowed list.
- **The judgement (D16, question 3).** Core's moderator stops at the first rule that applies and records that rule alone, so the drawer shows the checks that ran, in order: each before the deciding one passed, then the deciding one; a comment approved at once by whoever looks after the item is its own single row; a plugin's judgement shows its name and its reason. The words are built on the server, by `CommentVerdict`, so tests hold them.
- **Pings (D17, C8).** An imported pingback or trackback is listed as a comment with a chip for its kind, the source site's name and its address as the website; the same moderation and Delete permanently apply.
- **Two pages besides the list (D15).** With comments switched off, `comments/off`, answered 404, as a switched-off module's route is; the POST routes answer a plain 404. A list narrowed to an item, or a drawer for a comment, that the person doesn't look after: `comments/refused`, answered 403, in v9's words.
- **The menu, Home and the column (D18 to D22, I-220, I-204, C2).** `NavEntry` gained a module and a badge provider: an entry of a module that is off is left out, and `AdminNavigation` asks each entry it keeps for its count once a request, a parent's adding its children's. `CommentsWaiting` is the first provider: the pending comments on the items the person looks after, through `comment_stats_waiting`. Home shows the same figure, "Comments waiting" for `comments.moderate` holders and "Comments waiting on your posts and pages" for everyone else who looks after comments. Posts and Pages gain a Comments column, read for the page's rows in one statement from `comment_stats`: the approved count, linked to the Approved view narrowed to the item for whoever looks after it, and a badge for the waiting count linked to the Pending view. It isn't sortable (I-680). `comments` is a reserved segment.
- **The row's actions (D26).** The built lists' Actions menu, labelled "Actions for the comment by {Name}", never small always-shown buttons, which fail WCAG 2.2's 24-pixel target size on the drawing; the Browser suite runs axe's `target-size` rule on the screen and its drawer in both schemes, which the Browser plugin's axe leaves disabled.
- **When a status last changed (1.8c′'s D2, C4).** `status_changed_at` is a required `timestamptz(6)` with no default, written from PHP's clock to the microsecond by every Operation that sets a status: `SubmitComment` as a comment arrives, `ModerateComment` on every move (never when the status asked for is the one it has), `DeleteCommentPermanently` when it leaves a tombstone, and `ReplyToComment`. The migration added it, filled it from `updated_at` (else `created_at`), then required it. Microseconds, because Empty's cut-off compares it with the moment a list was drawn; no default, so an insert that forgets it fails instead of taking the database's clock, which a test's `travel()` doesn't move; no model cast, which would drop the microseconds; no index, since Spam and the Trash are read whole through `comments_parked` and the column only filters them (1.8d′'s benchmark reads the plans).
- **Quick edit (1.8c′'s D9, D10, C3).** `EditComment` changes a comment's name, email address, website and words, for whoever looks after the item; never a ping or a tombstone, never its status, moderation, IP address or browser. The stored document is replaced only when the words changed, compared as the typed text (line endings made `\n`, trimmed) against the stored document read back as text, under the comment's lock; an edit of anything else keeps an imported comment's bold or quote. A comment is *plain* when its text, made into a document again, gives the stored document, keys compared in any order since JSONB keeps its own (`CommentText::isPlain()`); each row and the drawer carry `plain`, so the hint that says first when the words would lose formatting is right wherever Quick edit opens. The email address is lower-cased and a website typed without a scheme gains `https://`, as the form's does. An approved comment's pages are removed after commit when its name, website or words changed, never served stale, since a correction can be a takedown (`CommentPurges::changed()`).
- **The reply written in the admin (1.8c′'s D11, D12, C6).** `ReplyToComment` writes a reply as whoever looks after the item writes one through the form: their account's name and lower-cased email address, approved at once with the form's own reason, placed by the thread's one rule (`CommentPlace::under()`, shared with `SubmitComment`), and no IP address, browser or key; its `moderation.signals` are `{rule: 'looks-after', written: 'admin'}`, which the drawer reads to say "None: written in the admin". It answers a comment, never a ping, that is pending or approved, on an item that isn't in the trash, open or closed. A pending comment answered is approved through `ModerateComment`, nested, so its counts and purges are that Operation's own. No throttle and no duplicate check: a moderator's second "Thank you!" to another reader is not a form sent twice.
- **Empty spam and Empty trash (1.8c′'s D3 to D7, C4).** An Empty press covers what the list would have shown for the same person, view, item and search, on every page, items in the trash left out, and of those only the comments whose `status_changed_at` is no later than the moment the page was drawn (`openedAt`, to the microsecond, sent back as the cut-off; the server takes the earlier of it and now). Spam that arrived, or a comment restored and marked as spam again, after the list was opened stays. Only spam and the trash are ever emptied. Each comment is one `DeleteCommentPermanently`, whose input gained `notChangedAfter`, checked under the comment's lock; the comments are read deepest first, then by ID, a batch at a time by keyset on `(depth, id)`, so a comment that couldn't be deleted is never read twice. Up to 1,000 go in the request; the rest go to the queue as `EmptyComments`, 5,000 a job, carrying the person's ID and the list's facts as plain values, so it runs as that person, never elevated, and hands the rest to the next job. The confirmation's numbers (how many go, how many keep a place as tombstones, how many replies those have) come from the server with the page and hold for every page of the list; a comment keeps a place when some comment below it stays. The buttons sit at the end of the filter bar for everyone who looks after comments, authors on their own items included, while the view, as filtered, holds comments.
- **The trash purge (1.8c′'s D8).** `teme:trash:purge` also deletes comments that have been in the trash since `content.trash_days` ago or longer, as the operator (`actorId: null` under `OperatorElevation`, which `DeleteCommentPermanently` now accepts as `DeleteContentPermanently` does), deepest first, by keyset in chunks of `--chunk`, with the same cut-off under the lock; a comment moved or deleted meanwhile is passed over. Spam waits until someone empties it. Its output gains a line for the comments and the tombstones that keep replies in place.
- **The keys (1.8c′'s D14 to D16, C11).** J and K move between rows, X selects, A, U, S and T move the comment through the same request as the menu, so the toast offers Undo, and R and Q open the reply and Quick edit where those are offered. They act only while a row itself has focus, never from a control inside it or a menu or sheet it opened, never with Ctrl, Alt or Meta; one row is in the tab order at a time. Two shared list components gained opt-in props and nothing else (`DataTable`'s `rowProps` and `describedBy`, `RowActions`' `movesFocus`), so every other list draws as before. Reply and Quick edit sit in the row's menu after Approve or Unapprove, and Quick edit in the drawer's footer, never for a ping, spam or the trash; Quick edit from the drawer closes the drawer first.
- **What a role editor will label (C2).** `comments.moderate`: "Moderate comments on every post and page: approve, reply, edit, mark as spam and delete". Nothing in the admin lists permissions with labels yet; the role editor (I-131) is the first screen that will.

## One item's Discussion

Whether an item takes comments, Open, Closed or Hidden, is set by whoever may publish it, from the editor's Publish panel, from Quick edit and, for many items at once, from Bulk Edit (1.8d′; I-571, I-687, I-688).

- **`SetDiscussion` (D2, D3)** is the only writer of `contents.comment_status` after `CreateDraft` writes its start. It authorizes `ContentPolicy::publish()` on the item, an item in the trash not found; it refuses, keyed `discussion`, while comments are switched off ("Comments are switched off."), for a type that takes none ("Regions take no comments."), and for a state that isn't one ("Choose Open, Closed or Hidden."). Under the item's row lock, the state the item already has writes nothing and returns `false`; another is one `UPDATE` through the query builder, so `updated_at` stays: a discussion change isn't an edit, and the lists' "Updated" order doesn't move. For a published item the item's `content:` tag is purged after the outermost commit, which removes its page and its later comment pages; a draft's change tells the page cache nothing.
- **The editor's row (D4, D5).** After Visibility, while comments are on and the item's type takes them: a select of the three states with what each means to readers under it, and, for an Open item while `close_after_days` is more than 0, when new comments stop: "after it's published", "on {date}", or "stopped on {date}" once that day has passed, worked out in the browser from the rail's live status and date, as `CommentViews::open()` decides it. It saves at once through `POST /admin/content/{content}/discussion` (`content.discussion`), outside the revision, as the address does; the select is disabled while its request runs, and a refusal puts it back and says why under it. Its data is the page prop `discussion`, from `ItemDiscussion::of()`; who may change it is the session's `can.publish`. Someone who may not publish sees the state, its meaning, any close-after line and "Whoever publishes it sets this."
- **Quick edit (D6)** shows the same select after the Published date, disabled with the same line for someone who may not publish, and sends `discussion` only when the person may set it and changed it, so a Quick edit opened before someone else's change can't undo it. The server runs `SetDiscussion` before the details: refused, nothing is saved and the same form can be sent again.
- **Bulk Edit (D7, D8)** offers "— No change —", Open, Closed and Hidden beside Status, while the list takes comments and the person holds the type's publish ability. `BulkEditItem` runs it as a step after the status, through `SetDiscussion`, so an item the person may not publish is never written. Its line says "discussion set to Closed" or "discussion already Closed" (I-829); a refusal is "discussion not changed: {reason}" when something else on the item changed, and otherwise the item is skipped with the reason.
- **The rows (D9).** Each list row carries `discussion: {value, canSet}`, by the rule the Comments column follows: null when the type takes none or comments are off; `canSet` is `ContentAbilities::canPublish()`, and the state is read with the row, so a page costs the statements it did.
- **The words (D19)** live once on each side: `Discussion::label()` in PHP, for Bulk Edit's lines, and `resources/js/lib/discussion.ts` in the browser.
