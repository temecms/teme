# The page cache

A full-page cache for readers who aren't signed in (slice 1.7). Study R (`docs/studies/page-cache.md`) is the design; this document describes what is built. **1.7a is the core**: the lookup, the key, who passes by, what is never stored, the file store and its tag table, the headers, the `teme_auth` marker and two commands. **1.7b is dependencies and invalidation**: each page records the tags of everything it shows, every Operation that changes what the public sees purges those tags after the outermost commit, a race guard keeps a page drawn during a purge from being stored, and `teme:cache:purge` purges by hand. **1.7c is stampedes, staleness and the session endpoint**: lives from configuration, capped by changes that come by the clock; a changed list's pages set aside and served `STALE` while one request draws each afresh, and the pages that show a change removed; a lock per page; `/_teme/session`; and core's small script, which adds an "Edit post" link for a signed-in editor. **1.7d is the Redis store**: pages in Valkey, for several servers, each page's lock beside it, and a race guard that compares the order purges were noted in, never clocks. **1.7d′ is in front of Teme**: a CDN told each stored page's tags and life in headers of its own, and purged, on the queue, once Teme has drawn the changed pages again; `teme:cache:warm`; and the file store's folder out of `storage/framework`. **1.7d″ is the static-file driver**: the web server serves each stored page a reader may have as a plain file, with no PHP at all, with nginx and Caddy settings in `docker/`, `teme:cache:check-static`, and the CDN in front purged by address. **1.7e is the proof**: a listing page reads its authors' addresses and its cards' images once (#30), a container singleton holds only what boot gives it (I-087), and the benchmark measures the cache at a million articles. **Slice 1.9 (SEO) adds to it, in parts:** 1.9a the `seo` tag, the XML and text a route may mark cacheable, and `X-Robots-Tag` outside production (`docs/superpowers/plans/2026-10-07-phase1-slice09a-foundation.md`, D1 to D19 are I-1010 to I-1028); 1.9c the `not-found` tag, the redirect Operations' purges and the counting of stored 404s on a hit (`2026-10-07-phase1-slice09c-redirects-and-404-log.md`, D1 to D20 are I-1043 to I-1062); 1.9d the `feed` tag (`2026-10-07-phase1-slice09d-feeds.md`, D1 to D20 are I-1063 to I-1082); 1.9e site code's purge (`2026-10-07-phase1-slice09e-site-code.md`, D1 to D11 are I-1083 to I-1093); 1.9f `robots.txt` and the sitemaps, with the `sitemap` tag (`2026-10-08-phase1-slice09f-sitemaps-and-robots.md`, D1 to D23 are I-1097 to I-1119); 1.9h the admin's Clear button (`2026-10-08-phase1-slice09h-tools-screens.md`, D1 to D16 are I-1140 to I-1155); 1.9i the 404 log's ignore list, applied by the minute's run (`2026-10-08-phase1-slice09i-search-and-social.md`, D1 to D17 are I-1156 to I-1172); 1.9j the person or the logo a page names as the site's publisher, which record tags they already had (`2026-10-08-phase1-slice09j-who-publishes.md`, D1 to D20 are I-1173 to I-1192); and 1.9k, which adds no tag and stores nothing (`2026-10-08-phase1-slice09k-editor-search-and-social.md`, D1 to D17 are I-1193 to I-1209). Each is described where it belongs below.

**On by default, except where `APP_ENV=local`** (`config/page_cache.php`; I-460, I-478). A developer's machine sees a theme's Blade changes at once; production gets the cache with no line of configuration. `PAGE_CACHE_ENABLED` decides whatever the environment; `.env.example` names it in a comment and never sets it, so a production `.env` copied from it can't turn the cache off. **A stored page lives an hour at most by default** (`page_cache.lifetime`, `PAGE_CACHE_LIFETIME`; question 2, I-500), a search's page ten minutes and a "not found" page ten seconds (below). The test suite keeps the cache off (`phpunit.xml`); a test that wants it calls `cacheOn()`, which keeps a page's life at a minute (D14), the one 1.7a's and 1.7b's tests were written against. **The benchmark runs its uncached scenarios with it off**, whatever the configuration (`BenchmarkRunner::run()`), so they measure what 1.6h measured, and **the page cache's own scenarios with it on** (`CacheScenarios`), each in a folder and a prefix of its own (*The benchmark*, below).

## Where it sits

`CachePublicPages` (`app/Http/Site/Middleware`) is in Laravel's **global** middleware stack, **after `TrustProxies` and before `PreventRequestsDuringMaintenance`** (I-463). `bootstrap/app.php` splices it in last in `withMiddleware()`, so every middleware of Laravel's own stays, in order; `ServingTest` holds that.

- **After the proxies are trusted**, so a key has the scheme and host the reader asked for.
- **Before maintenance mode**, so readers keep stored pages during a restore (`docs/studies/deployment.md` §3.9). **Maintenance mode alone no longer takes a cached site dark: clear the page cache too.**
- **A hit skips everything after it:** routing, the `public` group, `throttle:site-search` and the controller. A stored search spends none of the reader's thirty searches a minute; only a search drawn does. A hit reads nothing from the database, the maintenance flag included (`ServingTest`). It calls `prepare()` itself, since the router never sees a global middleware's response, and that is what empties a HEAD's body.
- **Only pages a `public` route drew are stored**, found through the route's `gatherMiddleware()`. That group has no session, cookie or CSRF middleware (I-262; `ServingTest` keeps it so). The admin, preview links and `/up` carry no `X-Teme-Cache` at all.
- **Off, it does nothing**: no header, no file, no row; nothing is recorded, no footprint is read, and nothing is purged.
- **`NoindexOutsideProduction` is the next middleware inside it** (I-1022), spliced in beside it, so a response drawn outside production is stored with `X-Robots-Tag: noindex, nofollow` and a hit replays it (*The static-file driver*, below).
- **A hit on a stored "not found" page appends one line to a file and reads no database** (I-1055): `CachePublicPages` notes the address for the 404 log, given as `HIT`, `STALE` or `HIT` after a wait, when the page carries the `not-found` tag (*The folder every process shares*, below, and `docs/architecture/addresses.md`, *Redirects*). The 404 log's ignore list is applied by the minute's run (`RecordAddressCounts`), never here, so the hit still reads nothing from the database (I-1162).

## The key

`PageKey`: the scheme and host, lower-cased, and **the path exactly as asked** (I-461). 1.6a answers `/About/` with a 301 to `/about/`, so a lower-cased key would serve the page at a second address. Of the query only `s` is kept (`PageKey::QUERY`), the one parameter a public page reads, parsed as `PathResolver` parses it and written one way (`s=heron+watch` and `s=heron%20watch` are one key); tracking parameters share a page. An empty `s` is a search, apart from no `s`. A search that isn't plain text (`s[]=`) has no key. Cookies are never part of it.

Every page carries its address's tag first, `url:` and 16 hex characters of the SHA-256 of the path in stored form (lower-cased, NFC), so `/About/?s=x` and `/about/` share it: one purge of an address takes every page at it, in any case or query.

## How long a page lives

| Page | Life at most | Why |
|---|---|---|
| Any page | `page_cache.lifetime`, an hour by default (`PAGE_CACHE_LIFETIME`, `PageCache::lifetime()`) | Purges are exact (1.7b) and time caps cover the clock, so a life is a safety net: a missed purge, a change made outside Teme, or a worker on a folder of its own heals within it. The page cache is infrastructure the operator provisions, so it is configuration, not a setting (question 2, I-500) |
| A search's page | `SEARCH_LIFETIME`, ten minutes, and never longer than any page (D7) | Its key comes from the reader, so the pages kept for searches are bounded by the search limit (thirty a minute a reader, 1.6h) times their life, never by the size of the site. Payload revalidates its listings every 600 seconds |
| A "not found" page | `NOT_FOUND_LIFETIME`, ten seconds, and never longer than any page | Enough to absorb a burst of probes at one address, short enough for an article published there |

**Time caps** (D5, I-266, `ClockChanges`). No stored page outlives the next moment a page can change with no Operation to purge it. `ClockChanges::next()` returns the earliest of the next published item dated ahead and the start of the next year on the site's clock, one moment for the whole site, exact to the second, needing neither the scheduler nor a shared folder. It costs one indexed statement per stored page, through `contents_published_order`, with the index's condition written out so a generic plan can still prove it. Pages expire early only while an item is dated ahead, which is rare.

| Change | Where | Capped? |
|---|---|---|
| A published item dated ahead comes into view | Quick edit allows a date ahead (`UpdateContentDetails`, refusing it only for the chosen home and posts pages, #36) and sets it. `PublishRevision` keeps an item's date, and `RestoreContent` restores one, so either can bring back a date ahead. Lists, its address and menus show it only from then: `ListingViews::archive()`, on which `LatestViews` and `RelatedPosts` build; `PathResolver::live()`; `NavigationTree::liveContent()` | **Yes** |
| A new year on the site's clock | `SiteComposer` gives every view `site.year`; the default theme's footer prints it | **Yes** |
| An item's comments close `close_after_days` after its date | `SubmitComment` refuses from then | No: a stored page may show the form up to its life; a reader who posts meanwhile is told "Comments here are closed." and keeps their words |
| A scheduled publication | The scheduler's `RunScheduledPublication` runs `PublishRevision`, which purges after commit | No: an Operation purges it, as Statamic's minute job and Emdash's sweep do theirs |
| A scheduled unpublication | Parked (I-182); it would come as an Operation too | Nothing to cap |
| A preview link's expiry | `/preview/{token}` is never stored (`no-store, private`) | Nothing to cap |

Search doesn't filter an item dated ahead (#44, open), so a search already shows it early; when #44 is fixed, the same cap covers the search page. **The tags are taken before the clock is read**: reading the site's time zone records the `settings` tag on any page still being drawn (1.7b's D3), which every stored page would otherwise carry.

**What a shared cache is told** (D6): `s-maxage` is the life a page has left, and a minute at most (`SHARED_LIFETIME`), however long Teme keeps its own copy, for every shared cache Teme can't purge. A `STALE` answer is `s-maxage=0`. A CDN a driver purges is told the whole life left, in its own header (*The CDN in front*, below).

**Turning the cache off, then on** (D8, I-475). While the cache is off, nothing purges a page as what it shows changes, so `teme:cache:prune`, which the scheduler runs every minute, empties the store: a page kept from before is gone within a minute of the cache going off. **An operator who turns the cache on again within that minute runs `teme:cache:clear` first.** Purges don't run while the cache is off: that would add footprint reads to every Operation, and change the benchmark and the statement counts 1.7b left alone.

## What a page records

`RenderRecord`, scoped to the request, collects tags while a page the cache may store is drawn; `PageCache::keep()` stores them with the page, its address's first. Tags are built by `PageTags`, from rows and the registries, never from a quoted type name.

**Two kinds of tag** (D1, I-469): **a thing as shown** (`content:{id}`, `term:{id}`, `person:{id}`, `media:{id}`) and **a list by its query** (`list:{type}`, `term:{taxonomy}:{id}`, `author:{id}`, `date:{Y}`, `date:{Y}:{m}`). Study R §3.4 gives authors and terms list tags only, but every article and every card shows its author and its kicker: with list tags alone, every publish by an author would purge all their articles, and every post filed under News would purge each archive whose cards show "News". Drupal separates `node:5` from `node_list`, and Craft `element::{id}` from `element::{class}::*`, for the same reason. `term:{id}` and `term:{taxonomy}:{id}` differ by their number of parts.

**Recorded where the read happens, for every ID asked for, found or not** (D2): an unpublished menu item, a trashed image or a link to a trashed article draws nothing, yet the page changes when it comes back, so the ID asked for is recorded, not the row found. Recording never reads the database. `*` is never recorded: every page carries it. There is no `home` tag: the home page records what it shows, `list:{type}` or the chosen page's `content:{id}`.

**Nothing keeps a fragment between requests**, so a region's or a card's tags join the page's that draws them.

**A settings group's `cacheTags`** (D3) are both what a page reading it records (`SettingsRepository::group()`) and what a change to it purges (`SettingsWriter::write()`), so any group, a theme's or, from phase 5, a plugin's, keeps the promise with nothing more to register. Core declares `general` → `settings`, `design` and `theme.{code}` → `theme`, `addresses` → `*`, `modules` → `*` (1.8a), `discussion` → `discussion` (1.8b) and `seo` → `seo` (Search and social, I-1020); `content`, `media` and `security` declare none, since no public page reads them.

|---|---|---|---|

| `theme` | the design: the theme, its settings, the accent, the menus in its places | `SettingsRepository`, for `design` and `theme.{code}` | `PublishDesign`, `BindNavigationSlot`, `DeleteNavigation` of a menu in a place |

| `comment:{id}` | a thing: a comment as shown, a tombstone or ping too | `CommentViews`, for each comment drawn | the comment leaving the thread, a tombstone deleted |
| `discussion` | the Discussion settings a thread is drawn by | `SettingsRepository`, for `discussion` | `UpdateSettings` of `discussion`, from 1.8d's screen |
| `seo` | Search and social's settings: the robots meta, the titles, the social cards' default image, the feeds' length, `robots.txt`, the sitemaps' being on | `SettingsRepository`, for the `seo` group, so every page the shell draws, every feed, `robots.txt` and every sitemap carries it | `UpdateSettings` of `seo` (`PageTags::SEO`, I-1020) |
| `feed` | every feed, whatever its subject (I-1076) | `FeedBuilder`, first among a feed's tags | `teme:cache:purge feed`; it is a thing's tag, so removes them all |
| `sitemap` | every sitemap: the index and each child's pages (I-1114); the stylesheet carries only its address's `url:` tag and `seo` | `Sitemaps` (`Sitemaps::CACHE_TAG`), on the index and on each page | `teme:cache:purge sitemap`, and by the lists and things below; a thing's tag, so it removes them all |
| `not-found` | every "not found" page `PublicController` drew | `PublicController`, on a 404 no redirect answered | a redirect with a pattern added, changed, switched or deleted: any stored 404 might be one it now matches (`RedirectLookup::NOT_FOUND_TAG`, I-1052) |
| `*` | every page | never recorded | `ChangeAddresses` (the `addresses` group), `RebuildCounts` when it fixes a count, site code when pages draw the change (below), `ClearPageCache` and `teme:cache:clear` |

A feed also records the lists and things it shows, as the page of the same subject does (I-1076): the site's feed `list:{type}` of each type Settings › Reading ticks, a type's archive page's feed that type's; a term's `term:{taxonomy}:{id}` and `term:{id}`; an author's `author:{id}` and `person:{id}`; each item shown `content:{id}`, each author named `person:{id}`, each category named `term:{id}`, each image `media:{id}`; and `seo` and `settings` through the settings it reads. A new item in the list sets the feed aside; an edit to an item it shows removes it. **A sitemap records the lists its entries come from** (I-1114): the index and each child carry `list:{type}` for a type's items, the archive type's list for terms, authors and the site's address, or the front page's `content:{id}` when the site shows a page, and `seo` through the settings; a page of terms adds `term:{id}` for each term on it and a page of authors `person:{id}` for each person, so a renamed term or person moves. A publish therefore sets the index and its type's pages aside, served while one request draws each afresh. A sitemap does not carry the tags of the images it names (parked, I-961), so a replaced or trashed image leaves it at the next change of its type. **The page starts live in the application cache** (I-1107, I-1119): the keys each child's last index pass found are kept under `Sitemaps::KEPT`, since a page answers only for a key the index gave. With the page cache on, the index finds them afresh each time it is drawn, which is once after each change; with it off, the index reuses them for ten minutes (`Sitemaps::REUSE`), so a request runs that pass at most once in ten minutes for each child and a new item past a full last page waits at most that long for its page. `feed`, `sitemap` and `not-found` are not in `PageTags`' lists: they are recorded by the code that draws the page, and `PageTags::isList()` doesn't name them, so each is a thing's tag and a page carrying it is removed, never served stale.

## What a change does

**Removed, or set aside, by the tag's kind** (1.7c's D1, I-266, study R §3.9). `PageCache::invalidate()` notes every tag for the race guard first, removes the pages that carry a thing's tag, then sets aside the pages left that carry a list's tag, for `RENDER_WINDOW` seconds (`PageTags::isList()`). Every page that shows an article, as its own page, a card, a link or a menu item, records its `content:` tag (1.7b's D2), so it is removed; a list page that doesn't show it only joins or loses a member, so it is set aside. **The article that changed, and anything taken down, is never served stale.**

| Kind (1.7b's D1) | Tags | A page carrying it |
|---|---|---|
| A thing as shown | `content:{id}`, `term:{id}`, `person:{id}`, `media:{id}`, `menu:{handle}`, `region:{slug}`, `url:{hash}`, `settings`, `theme`, `*`, and any tag `isList()` doesn't know | is removed |
| A list by its query | `list:{type}`, `term:{taxonomy}:{id}`, `author:{id}`, `date:{Y}`, `date:{Y}:{m}` | is set aside, unless it also carries a thing's tag |

A page carrying both kinds is removed. A tag not known as a list's is a thing's, so what later parts add is removed until named, never served stale. **Operations' changes go through `invalidate()`; `purge()` removes whatever the tags, for the commands:** an operator's purge means gone.

**A set-aside copy is the page's file renamed** (D2), from `{hash}.page` to `{hash}.stale`. A hit reads only `.page`, so a hit still reads no database, and a set-aside page is never a hit. The page's tag rows stay, so a later removal by any of its tags still finds the copy; their expiry drops to five minutes (`RENDER_WINDOW`), so `teme:cache:prune` removes the copy then. A page stored again deletes its copy. A rename is whole, so a reader meets the page or the copy, never half of either. While one request draws the page afresh, the others are given the copy, `STALE` (below). MilliCache distinguishes expiring from deleting, and Drupal's cache API invalidating from deleting, but both delete what their page caches purge.

**Operations tell; `BaseOperation` purges** (D4, I-472). `perform()` hands each change to `purgeAfterCommit()` as a `CacheKeysFor`; `BaseOperation` purges them in its after-commit step, after `afterCommit()` and `invalidateCache()` (`docs/architecture/operations.md`, *The fixed sequence*, step 7). `invalidateCache($result)` alone wouldn't do: it sees the result, never the state before the change, which only `perform()` reads under its lock (the old slug, the old categories, the old author). `PublicChanges`, scoped to the request or job, keeps one list per execution, nested as Operations nest, so an Operation run twice inside one outer transaction tells both runs, and **nothing is purged until the outermost transaction commits**; a rollback purges nothing. A purge that fails is reported, never thrown: the change has committed.

**Rule 1 at run time** (D13): telling the page cache outside an Operation throws a `LogicException`. Only an Operation changes what the public sees.

**A change's tags are what the public saw before and sees after** (D5): `Footprints` reads each thing's tags under the Operation's lock, before the change and again after, and both are purged. A content item's footprint, while it is published, is its `content:`, its address's `url:`, its type's list, its terms' lists, its author's list, and its year's and month's lists; a region's is `region:{slug}`; a term's is its `term:{id}`, its list and its address; a person's is their `person:{id}`, their `author:{id}` and their address. A published item dated ahead counts: its address and lists are purged a little early, which costs a redraw, never a stale page. **Footprints are read only while the cache is on**: off, nothing is read, so the suite and the benchmark run as before.

**`CacheKeysFor`** (D6, `Teme\Contracts\Cache`) is a final readonly payload: a subject (`content`, `term`, `person`, `media`, `menu`, `settings` or `site`, as constants), an ID, and the keys core purges. Core builds one for every change, so phase 5's dispatcher changes one method (`PublicChanges::add()`). A redirect change is told as `SITE` with the ID `redirects` (I-1059), since the contract has no subject for it (a `REDIRECT` subject waits for the plugin API, I-912), and site code's and the admin's Clear as `SITE` with the ID `*`, since what they change is on every page. `SITE`'s docblock in the contracts package still speaks of repairs alone; its wording is for the maintainers to widen (rule 5).

## The race guard

A page drawn while something it shows changes must never be stored after the change's purge (D8, I-264). **`page_cache_purges`** (`id`, `tag`, `purged_at`) holds a row for each tag each purge removed, **numbered by PostgreSQL as it is written** (`id`, a sequence) and stamped from PHP's clock for the prune, before the store is touched (`PageCache::invalidate()` and `purge()`); a list set aside is noted as a removal is. It stays in PostgreSQL whichever store keeps the pages.

- **A page is refused when a tag of its own, or `*`, was purged with a higher number than the latest purge noted when its drawing began** (`PurgeTimes::latest()`, read by `PageCache::beginDrawing()` and kept in `RenderRecord`). A purge is noted only after its change commits, and a sequence numbers in the order it is asked, so a purge numbered at or below the latest the drawing saw belongs to a change the drawing could already read. One numbered higher is either seen when the page is checked, or lands after the page is written and removes it.
- **Checked before the write and again after it**: a purge that landed between the look and the write found nothing of the page's to remove, so the page is forgotten (`PageStore::forget()`).
- **A page that took longer than `RENDER_WINDOW` (300 s) to draw isn't stored**, since purges older than that are forgotten: `teme:cache:prune` removes them every minute, so the table grows with recent activity, never with pages or tags.
- **`teme:cache:clear` records `*`**, so a page drawn before it is never stored after it.
- **No clock is compared** (1.7d, D5). A purge stamped by a server whose clock lags or leads is judged by when it was noted, so any number of servers share one guard. A drawing's length is still measured by its own server's clock, against itself. `purged_at` only decides when a purge is forgotten: a clock minutes wrong shortens how long its purges are kept, never what they refuse. Rejected: NTP alone, a tolerance (it would refuse every page drawn just after a purge), PostgreSQL's clock for both stamps (a statement per miss, and `travel()` no longer moves it), and purge times in Valkey (a second implementation, and a third clock).

## One request draws a page

**A lock per page, looked at again inside it** (D3, study R §3.9), named `page-cache:` and the SHA-256 of the page's key (`PageKey::lockName()`), **from the store that keeps the pages** (`PageStore::lock()`, 1.7d): the file store's from Laravel's default cache store, `cache_locks` in the database without Valkey, where taking it is an `INSERT` taken or refused and freeing it a `DELETE`; the Redis store's in Valkey, beside its pages, one round trip to take it. Every server that shares the pages shares their locks.

- **`LOCK_SECONDS = 30`**, as Statamic and MilliCache hold theirs and as long as PHP lets a request run by default; at most `RENDER_WINDOW`, since a page drawn longer isn't stored anyway. A request that dies holding it frees it then.
- **Looked at again inside the lock**, as Statamic does: the request that held it may have just stored the page.
- **A request that finds the lock held is given a stale copy at once, or waits.** The copy is the one a changed list set aside, or the page whose life just ended and which nothing has pruned yet, answered `STALE` with `s-maxage=0`. With neither, as after a change removed the page, it waits up to `LOCK_WAIT = 5` seconds, looking in the store every `WAIT_STEP = 100` ms. **It watches the store, never the lock**: Laravel's `block()` retries the lock every 250 ms, and each retry of a database lock is an `INSERT` and an `UPDATE`, so a hundred waiting readers would make eight hundred statements a second. The wait counts its looks, not the clock.
- **Then it draws the page itself: never an error page.** Statamic answers 503 after its 30-second wait.
- **A lock that can't be reached** (the database or Valkey down) is reported, and the page drawn as if it were free (`NoLock`).

**Only a GET locks, and the router's own addresses pass by** (D4). A HEAD's page is never stored, so nothing waits for it. A path whose first segment is in `Paths::RESERVED` (`admin`, `preview`, `up`, `storage`, `build`, `_teme`) is answered by its own route, never by a stored page, and passes by as `reserved`, so a health check on `/up` or an anonymous visit to the sign-in page takes no lock and reads no file.

**The request's way through `CachePublicPages`:**

1. **Off:** handed on untouched.
2. **Passed by** (a method, a signed-in reader, another host, a design preview, a reserved address, a search with no key): drawn, never stored, and on a public page it says why.
3. **A fresh page stored:** `HIT`. Reads no database.
4. **A HEAD with no fresh page:** drawn, never stored (`BYPASS (head)`), and no lock taken.
5. **A GET with no fresh page takes the page's lock:**
   - **taken:** it looks again inside the lock and answers `HIT` if the page was stored meanwhile. Otherwise it draws the page and stores it, `MISS`, and frees the lock whatever happens.
   - **held by another request:** it answers with the copy set aside, or the page whose life just ended, `STALE`, at once. With neither, it waits up to five seconds, looking in the store every 100 ms, answers `HIT` when the page comes, or draws the page itself when it doesn't.

**What a miss costs the database** beyond drawing the page: the latest purge number (one index-only statement, 1.7d), the lock (two statements with the file store and the `database` cache store, none with the Redis store), and the next clock change when the page is stored (one). A `STALE` answer follows a refused lock attempt: with the file store that costs the lock's statements (B-332), though the copy itself is read from a file; with the Redis store it reads nothing from the database. A hit reads nothing from the database with either store; neither do a wait's looks, and the refused lock before them costs what a `STALE` answer's does. *The benchmark* (below) measures each.

## Who passes by

`PageCache::bypass()`, each with its reason in `X-Teme-Cache: BYPASS (…)`:

| Reason | When |
|---|---|
| `method` | any method but GET and HEAD |
| `signed in` | the reader carries `teme_auth` (below) |
| `host` | a host other than APP_URL's (I-462): the key holds the host, so an unchecked `Host` header would fill the disk with copies. 1.13's `trustHosts()` limits hosts anyway |
| `design preview` | the design preview's parameter, which the key drops |
| `reserved` | an address the router answers itself, its first segment in `Paths::RESERVED` (`admin`, `preview`, `up`, `storage`, `build`, `_teme`): nothing is looked up or locked (1.7c's D4). Such a route isn't the public site's, so it carries no `X-Teme-Cache` |
| `query` | a search with no key |

`feed`, `sitemap.xml` and `robots.txt` are not in that list. They are `Paths::SITE_ROUTES`, read with `RESERVED` through `Paths::taken()` so no item may take them, but the cache passes none of them by and stores what they answer (I-1025). Listing them in `RESERVED` would have stopped the cache storing them at all.

## What is never stored

`StoreRules::refusal()` (I-464), each rule's name the reason `X-Teme-Cache` gives:

| Reason | Why |
|---|---|
| `head` | Symfony empties a HEAD's body before middleware sees it; a HEAD is still answered from a stored page |
| `redirect` | an address's redirect changes when addresses change |
| `server error` | study R §3.1 |
| `status N` | any status but 200 and 404: a 403 from a bad preview link, a 429 from the search limit and a 503 are one request's answers; so is a comment feed's 410, drawn each time as `BYPASS (status 410)` (storing it briefly is parked, I-927), and a redirect's 410 or 451 |
| `streamed` | its body isn't a string to store |
| `sets a cookie` | it would hand one visitor's cookie to everyone |
| `private` | marked `private`, `no-store` or `no-cache`; Symfony's own default, sent when nothing set a `Cache-Control`, doesn't count. Every answer at a protected item's address is marked so (*Protected items*, below) |
| `vary` | varies by anything but `Accept-Encoding` or `Host` |
| `encoded` | not the HTML the key stands for |
| `not html` | a JSON 404 for a request that expects JSON would otherwise be stored under an article's key. **A route may mark itself cacheable** (`MarkCacheable`, which sets `PageCache::CACHEABLE`, I-1023), and then its `application/rss+xml`, `application/xml`, `text/xml`, `application/xslt+xml`, `text/xsl` or `text/plain` is stored too. Feeds, `robots.txt` and the sitemaps with their stylesheet are marked (I-1076, I-1114) |
| `not xml or text` | a marked route answered something else, such as JSON or an image: marking a route widens what it may store to those six types and no further. An unmarked route's anything but HTML is still `not html` |
| `degraded render` | core's plain fallback drew the page, for a missing or broken theme or a theme error view that failed (`PublicPage` tells `RenderRecord`) |
| `store failed` | the store couldn't be written; reported, and the page served as drawn |

The race guard adds two (above): `purged while drawn` and `drawn too slowly`.

A theme's own warnings (`PageWarnings`) aren't degraded renders: the same on every render, so such a page is stored. **Search's rate-limit headers are never kept** (`X-RateLimit-*`, `Retry-After`): they count one reader's searches.

**Protected items** (I-1700, I-2776). Every answer `PublicController` gives for an item protected by a password, the form and the unlocked page alike, at its address or a later page of its comments, carries `Cache-Control: no-store, private`, so it is drawn each time as `BYPASS (private)` and never stored: a reader's open page never reaches another, and the form never reaches a reader who holds the key. With nothing stored, the static-file driver writes no file and a CDN keeps nothing. A copy stored while the item was public goes with `ChangeVisibility`'s purge of its footprint, after the commit, and the race guard refuses a page drawn during the change. `POST /_teme/unlock` is a POST under `_teme`, which the cache passes by, and it marks its own answers `no-store, private` too. A private item has no address, so nothing of it is drawn to store. The sitemaps' index, `contents_sitemap`, holds public items only, so each page's start is still counted from the index alone; the author listing's and the pinned posts' partial indexes (`contents_author_published`, `contents_pinned_published`) repeat `visibility <> 'private'`, since a partial index serves only a query that repeats its condition.

## The file store

`PageStore` is the driver interface (spec §5.6). Three are built, chosen by `page_cache.driver`: `file`, the default, `static`, the file store and a plain file of each page for the web server (below), and `redis` (below). A page's stored line, the JSON before its HTML, is `PageEntry::storedLine()`, which both keep, and `PageEntry::fromStored()` reads it back.

- **One file a page**, named by the SHA-256 of its key, under two levels of folders from the hash (`ab/cd/abcd….page`), in `page_cache.stores.file.path` (`storage/page-cache` by default, kept out of git and out of `storage/framework`, which a container may keep on a tmpfs of its own, study X §3.2). Its first line is JSON: `key`, `status`, `headers`, `storedAt`, `expiresAt` and its tags; then the HTML, byte for byte. **Never PHP `serialize()`** (rule 4; I-261's exception is the `cache` table alone).
- **Written whole, then renamed into place** (`Filesystem::replace()`), so a reader meets the old page or the new one, never half of either. A file that can't be read, or holds another key, is a miss.
- **`page_cache_tags`** (`entry`, `tag`, `expires_at`; primary key `(entry, tag)`, indexes on `tag` and on `expires_at`, I-466) finds files by tag and by expiry. The file is written first and deleted if its rows can't be, so the table knows every file; a race can leave rows with no file, which is harmless. A page needs at least one tag. A tag a page no longer has is dropped when it's stored again.
- **`purge()`** removes every page carrying any of the tags given, all of each page's rows and then its file and any copy set aside, taking up to 500 pages at a time; `*` flushes. **`forget()`** removes one page, for the race guard.
- **`markStale()`** sets aside each page carrying any of the tags given, once, by keyset over `entry` (a mark leaves the rows, so it can't page through them as a purge does): every row of the page expires at the moment given, and `{hash}.page` is renamed `{hash}.stale`. **`stale()`** reads only `.stale`, as `get()` reads only `.page`. `put()` deletes the copy, and `prune()` deletes it once its rows expire. A page whose file is gone has nothing to set aside, and isn't counted. **Flush and prune take up to 500 entries at a time from the table**; prune takes only rows still expired, and deletes a file only if its own JSON line says it expired too, since a page stored again meanwhile has a new file. **Nothing in `app/` lists a folder** (`NoStorageListingTest`), and nothing grows with the number of pages in one piece.
- `page_cache_tags` and `page_cache_purges` are cache data, left out of backups and exports like `cache` (1.12).

A failure of the store never breaks a page: a read that fails is a miss, a write that fails is `BYPASS (store failed)`, and both are reported.

### The folder every process shares

**The folder must be one the web server, the queue worker and the scheduler share** (D12, I-480). Only the web server stores pages, but all three purge them: a scheduled publication, a recompute and a count repair run in the worker or the scheduler. A process on a folder of its own removes a page's rows but not its file, which the web server serves until it expires. Its default sits outside `storage/framework` (1.7d′, question 4, I-533), where 1.13 mounts one volume for the web server, the queue worker and the scheduler.

The store makes that visible. The first time a folder holds a page, the store writes a random name into `.teme-folder` there and tells the cache store, which every process shares (`FilePageStore::FOLDER_KEY`). Every process that removes pages (purge, flush, prune) reads its own folder's name and compares:

- the same name: it reaches the pages' folder;
- no name in the cache store: nothing has been stored since the cache store was cleared;
- another name, or none in its folder: its deletions miss the web server's files. It logs a warning, and sets `FilePageStore::UNSHARED_KEY` for a day, which `PageCacheFolderShared` (`app/Domain/Status/Checks`, priority 60, for `settings.general.manage`) shows administrators as a Status banner. **The banner says how late a change can show: as long as a page lives** (D9), in words from `CarbonInterval::forHumans()`, "up to an hour late" by default.

**Each stored page tells the cache store the name again if it has forgotten it**, as `php artisan cache:clear` or `optimize:clear` make it, so a deploy that clears the cache store doesn't silence the check. A marker that can't be read tells nothing, since an empty name would read as a mismatch to every process. A folder emptied by hand is named afresh by the next page stored. **The cost:** one cache read per stored page, and one small file read and one cache read per purge; never anything on a hit.

**It also holds the counts spool** (I-1054, `AddressCounts`): a `counts` folder with `counts.open`, where each redirect hit and each address nothing answered appends one line, and `counts.closed` and `counts.reading`, which the scheduler's minute run takes in turn (`RecordAddressCounts`, `docs/architecture/addresses.md`, *Redirects*). The spool is not page cache data and nothing decides anything from it: it is a telemetry sink (`docs/architecture/operations.md`). A request appends with `LOCK_EX`, one small write to a local file, no database. **The scheduler must run every minute for the counts to appear, and it reads only the folder it shares with the web server:** with several servers on the Redis page store, each server's folder is its own and only the scheduler's server is counted (counting in Valkey instead is parked, I-911).

## The Redis store

**For several servers** (1.7d, I-265, study R §3.8): pages in Valkey, which every process on every server reaches, so no folder need be shared. **Turning it on:** `PAGE_CACHE_DRIVER=redis`, the phpredis extension (question 2, I-512; `REDIS_CLIENT=phpredis`, Laravel's default), and the `page-cache` connection in `config/database.php`: a database of its own (`REDIS_PAGE_CACHE_DB`, 2), so `php artisan cache:clear` on a Redis cache store never flushes the pages with it, and a second to connect and two to read, so a Valkey that doesn't answer makes pages misses. The store connects only when first used; a Valkey that is down is a miss, reported, and a page that can't be stored is `BYPASS (store failed)`. The file store stays the default, for one server.

**The layout** (D1 to D4), every key under the store's prefix (`page_cache.stores.redis.prefix`, `page-cache:`), after the connection's own:

| Key | Holds | Life |
|---|---|---|
| `generation` | the current generation, a number; missing is 0 | none: the one key without |
| `{g}:page:{hash}` | a stored page: a hash of `meta`, its JSON line, and `body`, its HTML; `{hash}` is the SHA-256 of its key, as the file store names its file | its life, plus `RENDER_WINDOW` |
| `{g}:stale:{hash}` | the page set aside, renamed from `page:` | cut to the moment it is kept until |
| `{g}:tags:{hash}` | the page's own tags, a set | its page's, plus a day (`TAGS_KEPT`) |
| `{g}:tag:{tag}` | the hashes of the pages carrying the tag, a set | at least its longest-lived page's |
| `{g}:expiries` | each page's hash, scored by its expiry: `prune()`'s index | at least its longest-kept list of tags' |
| `page-cache:{sha}` | a page's lock (`PageKey::lockName()`), outside any generation | `LOCK_SECONDS` |

A set per tag finds pages, and each page lists its own tags, so a tag it no longer has is dropped from that tag's set when it is stored again, as MilliCache keeps a page's flags in its entry.

**Eight fixed Lua scripts** (D2), each run whole in one round trip: a hit is one `EVAL`, whose script reads the generation and the page. The eighth, for warming, reads the JSON lines of up to a limit of the pages in some tags' sets, one `SSCAN` of each set. Atomic, so a purge and a store never interleave within a page, and a prune can't delete a page stored again after its expiry was read. **A page's values are script arguments**, which phpredis passes as given, so a page is never serialized, whatever serializer the connection has (rule 4; `RedisPageStoreTest` holds it with `Redis::SERIALIZER_PHP` set); nothing a reader sends is ever script text. Each script builds its keys from `KEYS[1]`, the store's prefix, so the connection's own prefix reaches every key. No Redis Cluster: a script touches keys it builds, which a cluster refuses; Teme runs one Valkey.

**Flushing moves `generation` on** (D1): O(1) whatever the size of the cache, and everything under the old generation expires by itself, since every key but `generation` has a life. MilliCache's clean-up calls `KEYS` and its deletion by pattern walks the keyspace with `SCAN`; study R asks for neither. **Nothing lists keys:** a purge walks one tag's set with `SSCAN`, 500 members a script, as the file store walks its table 500 rows at a time, and `prune()` takes expired pages from `expiries`, 500 at a time. A tag every page carries, such as `settings`, has a set as large as the cache, and is never read whole.

**Set aside** (D3): the page's key renamed to `stale:{hash}`, whole, so a reader meets the page or the copy; its places in the tags' sets stay, so a purge of any of its tags still finds it; its life and its score in `expiries` (`ZADD … LT`) are cut to the moment it is kept until, so `prune()` removes it then.

**Expiry** (D4): Valkey keeps a page `RENDER_WINDOW` past its life, so a page whose life just ended can still be given `STALE` while one request draws it afresh, and `teme:cache:prune` removes it at its life's end through `expiries`, as the file store's prune removes an expired file. A page's list of its tags outlives it by a day, so a paused scheduler still leaves no page in a tag's set for good.

**Its lock** (D6): a `PhpRedisLock` in Valkey, beside the pages, outside every generation, so a flush frees no lock: one round trip to take it (`SET … NX EX`), its value a random owner, never serialized. Laravel's default cache store stays as it is: moving it to Valkey would put all of Laravel's serialized cache values there, which 1.13 decides.

**Sharing a Valkey with the queue:** its eviction policy must be `volatile-lru` or `volatile-ttl`, never an `allkeys-*` one: every key the page store writes has a life and the queue's keys have none, so only pages are ever evicted.

**The tests** (D10, question 3, I-513): `RedisPageStoreTest` and `RedisServingTest` run on a real Valkey, `valkey_test` in `docker-compose.yml` (`valkey/valkey:9.1-alpine`, port 6380, in memory; `docker compose up -d valkey_test`), each test under a prefix of its own. Where none answers they skip and say why; CI runs a `valkey` service and sets `TEME_REQUIRE_VALKEY`, so there they fail instead, and CI can never pass by skipping them.

## The static-file driver

**Turning it on** (1.7d″, I-086, I-536, I-551): `PAGE_CACHE_DRIVER=static`, and the web server's settings from `docker/`. For serversideup/php 4.5.1's `fpm-nginx` image, `docker/nginx/conf.d/teme-static.conf` goes in `/etc/nginx/conf.d/` and `docker/nginx/site-opts.d/http.conf.template` over the image's own; behind Traefik, `SSL_MODE` stays off, so the image reads that template and no other. The image writes `http.conf` from the template only when `http.conf` isn't there yet, so a new template takes effect in a container created afresh, never in one restarted. For Caddy, `docker/caddy/teme-static.caddy` is imported in the site's block. Then `php artisan teme:cache:check-static --url=http://127.0.0.1:8080` inside the web container. Traefik serves no files: nginx serves them inside the web container, behind it. Off by default; the file store stays the default. For one server, or several sharing one folder; not with the Redis store.

**What gets a file** (D2, I-537): a page answered 200 with nothing but HTML in UTF-8 (and Teme's own `X-Teme-…` headers), at APP_URL's scheme and host with no query, on a path the web server sees as Teme keyed it, not reserved, with more than two minutes to live. A page with any other header stays PHP's, since the web server would drop it. A page's links are built from the request's scheme and host (I-462), so until 1.13 trusts the proxy that ends TLS (`trustProxies()`), a site whose APP_URL is `https` keys its pages `http` behind it, and none gets a file: never a wrong page.

**Outside production no page gets a file** (I-1022, I-537). `NoindexOutsideProduction` gives every response `X-Robots-Tag: noindex, nofollow` when `app()->isProduction()` is false, asked for each response from the application's `env`, never `config('app.env')`, so a test may change it. It replaces any value a response had, a search's `noindex, follow` included: a copy's links lead nowhere a search engine should go. It sits inside the page cache, so a page drawn outside production is stored with the header and a hit replays it; and since a page with a header the web server would drop never gets a file, the rule above needs no case of its own. **The middleware adds nothing in production,** so a production page carries only the `X-Robots-Tag` its own route sets: a search's, a feed's and a sitemap's (`noindex, follow`, or `noindex, nofollow` for a feed while the site discourages search engines), stored with the page. **An operator who changes `APP_ENV`, in either direction, runs `teme:cache:clear`** (below) until 1.13's `teme:deploy` does: pages stored under the old environment keep, or lack, the header. What answers before the page cache, a malformed address's 400 or a CORS preflight, carries no header; neither is a page. The benchmark's static-file scenarios run as production for the same reason (*The benchmark*).

**Its name** (D3, I-538): the path decoded, as nginx's `$uri` and Caddy's `{path}` give it, and `index.html`: `/about/` is `about/index.html`, `/about` is `aboutindex.html`, `/` is `index.html`, in `page_cache.stores.static.path` (`PAGE_CACHE_STATIC_PATH`, `storage/page-cache/static`, inside the file store's folder, so one volume and one shared-folder check cover both). The name keeps the path's case and its trailing slash, since `/about` answers with a 301 to `/about/` where the address pattern has one. A path the web server would see otherwise gets no file: an empty, dot or hidden segment, a control character or backslash, text that isn't UTF-8, or a name too long. Linux only: a file system blind to case would serve `/about/`'s file at `/About/`.

**Written whole, found through a table** (D4, D5, I-539, I-540): `Filesystem::replace()` writes beside the old file and renames over it, so the web server serves the old page or the new one, never half of either. `page_cache_files` (`entry`, `path`, `expires_at`) knows every file: a row is written before its file and deleted only by the prune, after the file, so a race or a crash leaves a row with no file, never a file with no row. Storing: the file's row, the page, its tag rows, then its file. Removing, batch by batch in the file store's own loops: the tag rows, the page, then its file. Nothing lists the folder. A file that can't be written or deleted is reported and never breaks a page (D15, I-550): PHP serves the page from the store, and the prune tries the delete again when the row's time is up.

**When a file goes** (D6, D7, D12, I-541, I-542, I-547): with its page, whenever a change removes it, sets it aside (a copy set aside is never a file: PHP gives it, `STALE`), or the race guard forgets it; on a flush; and two minutes before its page's life or clock cap ends (`StaticPages::EARLY`), through the minute's prune, so neither the web server nor a CDN that fetched it serves it past the page's life. PHP serves every page's last two minutes, from the store. While the driver is off, the prune deletes every file it left, within a minute, and with a CDN purges the whole site there once. **While the scheduler is stopped, a file outlives its page**: changes made through Operations still remove files at once; a date ahead, the new year and a life's end wait for the prune. A Status banner for a prune that hasn't run is parked for 1.13 (I-552).

**Who gets a file** (D8, I-543): a GET or HEAD, with no query, from a browser with no `teme_auth` cookie (by its presence, as PHP reads it), at an address not in `Paths::RESERVED`. Anything else reaches PHP, which answers as before. nginx: three `map`s and `try_files`, never `if` or `alias`, the named location `@teme_app` keeping the image's own rule; Caddy: a named matcher in a `handle`, which Caddy runs before `php_fastcgi`. `StaticSettingsTest` holds both to the code (D14, I-549): the reserved list, the marker's name, the file's name, the folder, and, in nginx's template, only the image's own variables.

**What a file's answer says** (D9, I-544): `X-Teme-Cache: STATIC` and `Cache-Control: public, max-age=0, s-maxage=60`, with the image's security headers (`add_header_inherit merge`, nginx 1.29.3 or later; the image's Debian trixie build carries 1.30.4, and an older nginx refuses the settings at start rather than drop the headers). No `Age`, no `Cache-Tag`: the web server knows neither the page's life nor its tags.

**Other spellings** (D13, I-548): a file answers every spelling of its path that decodes to it; Teme answers those with the same page, except a spelling that encodes a letter, digit or hyphen (`/%61bout/`), which Teme redirects and the web server answers: the same page, at a spelling no link uses. The image's `server_name _;` answers any `Host` from the one folder, with the site's own page.

**What it costs:** a hit from a file runs no PHP and reads nothing; a miss that writes one adds one statement (its row) and the file's write; a purge adds one statement per 500 pages for their files' rows; the prune, one indexed statement a minute, idle.

**The self-test** (D11, I-546): `teme:cache:check-static` writes a probe page in the static folder and another under `/_teme/`, then asks the web server for them: a GET and a HEAD must get the file, marked `STATIC`, in UTF-8, with every security header PHP's answer has; a query, the marker, a POST, the address without its slash, the address in capitals and the reserved address must not. Then it deletes the probes and asks once more, which a web server that keeps what it opened would still answer. It fails when any rule is broken, and lists what only a person can check: the worker and the scheduler on the same folder, the scheduler running, a publish removing the file at once, a CDN's cookie rule, and the check still passing after each change to the image. Its tests answer with `cacheWebServer()`, a fake that follows the shipped settings: no test starts a web server.

## The headers

| Header | Says |
|---|---|
| `X-Teme-Cache` | `HIT`, `MISS` (drawn and stored), `STALE` (a copy given while another request draws the page) or `BYPASS (reason)`, including the race guard's `BYPASS (purged while drawn)` and `BYPASS (drawn too slowly)`; `STATIC` when the web server answered from a file, with the static-file driver (PHP never sees such a request) |
| `Age` | seconds since the page was stored, on a hit, a miss or a `STALE` answer |
| `Cache-Control` | on a stored page, `max-age=0, public, s-maxage=<seconds>`: the life left, and a minute at most (`SHARED_LIFETIME`, D6); `s-maxage=0` on a `STALE` answer. A shared cache never keeps a page past its life, and browsers ask again |
| `X-Teme-Cache-Key`, `X-Teme-Cache-Tags`, `X-Teme-Cache-Ttl` | outside production only, as `X-Teme-Template` is: the key, the tags, and the life left of Teme's own copy |
| `Cache-Tag` | with Cloudflare in front: the page's tags, each as 16 hex characters of its xxh3, comma-separated; left off when they pass 16 KB. Cloudflare strips it before the reader |
| `Cloudflare-CDN-Cache-Control` | with Cloudflare in front: `max-age=` the life the page has left; never on a `STALE` answer. Cloudflare reads it before `Cache-Control` and never passes it on |

**`X-Teme-Cache-Tags` lists 2,000 characters of tags at most**, then `(+N more)` (D9): an article with twenty tags, its related posts and a menu carries well over a hundred, and a proxy may refuse a response whose headers overflow its buffer. The stored page keeps them all.

`s-maxage` is the life a page has left, up to a minute, and `Age` how long it has been stored. A shared cache that subtracts `Age` (RFC 9111 §4.2.3) keeps a page a little less than it could; one that ignores `Age` keeps it exactly as long. Neither keeps it past its life (study R §3.12).

## The CDN in front

**Turning it on** (1.7d′, I-514, I-531): `PAGE_CACHE_CDN=cloudflare`, `CLOUDFLARE_ZONE_ID`, `CLOUDFLARE_API_TOKEN` (one permission: Zone › Cache Purge › Purge), and `CLOUDFLARE_PURGES_PER_MINUTE` for a plan above Free, all in the server's environment. A driver is one class behind `CdnDriver` (`App\Domain\Cache`, internal until phase 5 decides whether a plugin may add one, D13). An unknown name, or Cloudflare without its zone or token, fails every stored page with an `InvalidArgumentException`, as an unknown store does (D15): a deploy-time mistake shows at once, never as pages the CDN keeps an hour that nothing purges.

**What a stored page tells it** (D1 to D3): its tags as hashes in `Cache-Tag`, 16 hex characters of each tag's xxh3, never a tag as written, since a content ID is a ULID whose first part says when its draft was made (I-496); and the life it has left in `Cloudflare-CDN-Cache-Control`, which Cloudflare reads before `Cache-Control` and never passes on. `Cache-Control` keeps its minute for any other shared cache, which nothing purges. A page whose keys pass Cloudflare's 16 KB tells it nothing, so it keeps the page no longer than the minute: a purge of a key left out would miss it. A `STALE` answer tells it nothing, and says `s-maxage=0`. A collision of two hashes purges a page too many, never one too few.

**What it is purged of** (D4, D5, D6, D12): every tag Teme purges, Operations' and the commands', noted in `page_cache_cdn_purges` (`id`, `tag`) once Teme's own pages are gone, numbered by PostgreSQL, and sent by one `PurgeCdn` job at a time (`ShouldBeUnique`), oldest first, 100 tags to a request, within the configured rate (Free: five a minute, counted by Laravel's `RateLimiter`). A drain sends up to ten requests a run and stops after half a minute of real time, so a slow CDN never holds a worker past its timeout (a request waits five seconds to connect and fifteen for an answer at most). It waits as long as Cloudflare's `Retry-After` says; a refused purge is reported, shown on a Status banner for a day (`PageCacheCdnPurges`, priority 60), and tried again a minute later, its rows kept; the job is never failed for waiting. A tag queued again while its batch is out is sent again: its change came after the purge. `*` purges the site's host, never the whole zone, so a zone's other hosts keep their cache. `teme:cache:prune` queues the drain every minute whatever waits, and, while the cache is off, purges the whole site the first time it empties anything, since nothing purges while the cache is off and the CDN may keep a page its whole life. With the static-file driver, the address of every file a change, a list set aside, the race guard's undo or the prune removes, noted in `page_cache_cdn_addresses` and sent 100 a request as full URLs (`purgeUrls()`), on Cloudflare's budget for addresses (800 a second on Free), apart from the tags' five requests a minute; tags go first. A flush, and the first prune that retires the files once the driver is off, purge the site's host instead, and `*` covers every address queued before it (D10, D12, I-545).

**At Cloudflare** (the operator's, once): a Cache Rule "Eligible for cache" for the site's host, its Edge TTL "Use cache-control header if present, bypass cache if not"; a second, "Bypass cache", when `http.cookie contains "teme_auth"`, so signed-in people pass it by as they pass the page cache by; and Traefik trusting Cloudflare's addresses (study X §3.6). Cloudflare caches no HTML without the first rule, and serves its copy to a cookie without the second (OUTSIDE, https://developers.cloudflare.com/cache/concepts/default-cache-behavior/ and https://developers.cloudflare.com/cache/how-to/cache-rules/examples/bypass-cache-on-cookie/, read 2026-09-28).

**What it costs:** a hit hashes its page's tags (xxh3, about 0.1 µs each) and reads nothing from the database; a change's after-commit step adds one insert per 500 tags and the drain's dispatch; no reader's request waits on Cloudflare. On the `sync` queue the drain runs inside the request that made the change: a refused request costs a round trip, dropped packets the 5-second connect timeout. No test reaches Cloudflare: `TestCase` calls `Http::preventStrayRequests()`, and `cacheCdnOn()` fakes the API.

## Warming

**After a change** (D7 to D10, study R §3.11, I-532): up to `page_cache.warm.limit` (20, `PAGE_CACHE_WARM_PAGES`) of the pages it removes, then of those it sets aside, read from the store before they go (`PageStore::keys()`, which lists no folder and no keyspace); never a search's page, a list's later page (`/page/2/`), or a page that answered anything but 200; the home page first. One `WarmPages` job draws them inside Teme, through the HTTP kernel in the worker's own process, never over HTTP, where a CDN in front would answer with its own copy; each page in a fresh scope (`PageWarmer`), so a value one page read, such as the settings `Cache::memo()` keeps, never reaches the next. Then it queues the CDN's drain: Teme regenerates first, then the CDN is purged (study R §3.10). A change with nothing to warm starts the drain at once. **Correctness never depends on the order**: Teme's own copies go synchronously after the commit, before any queued job, and a page drawn while the change commits is never stored (the race guard). On by default; off with `PAGE_CACHE_WARM=false`, and **never on the `sync` queue**, where the request that made the change would draw the pages itself. A job draws for half a minute at most; the rest wait for their readers.

**`teme:cache:warm`** (D11): the home page, then each term's and each author's archive from `paths` (its first page only), then live items newest first, 500 rows a query, one page at a time, never all at once; 1,000 pages by default, `--limit=0` for every current address, since pages live an hour and a page no one reads within it was drawn for nothing. Run it after `teme:cache:clear`. Date archives aren't in `paths`, and neither feeds nor sitemaps are warmed. The page chosen as the home page has its own address in `paths`, which answers with a 301 to `/`: drawn, not stored, and counted "not stored".

**What it costs:** with warming on, two reads of the store in a change's after-commit step (the file store: two indexed statements and up to 40 small file reads; the Redis store: two `EVAL`s) and one job's row; nothing while it's off or on `sync`. With Valkey unreachable, those reads fail as every store call on that request does (B-334).

## The `teme_auth` marker

`SignedInMarker` (I-465): a session cookie, `SameSite=Lax`, encrypted by the `web` group like the admin's other cookies, set at every sign-in (Laravel's `Login` event, so a remembered sign-in too) and cleared at sign-out (`Logout`). **Only its presence is read**: it sends a reader past the page cache and the speculation rules (`Document`), and has core's script ask who is reading; nothing reads a session to know it.

**Readable by scripts** (question 1, A, from 1.7c): not `HttpOnly`, so core's script asks `/_teme/session` only in a browser that carries it, and an anonymous reader makes no second request, behind a CDN too. What that reveals: any script on a public page, a plugin's or an injected one, can see that this browser signed in to the site. Why that's safe: its value is nothing, so there is nothing to steal, and any script on the site could already ask the same-origin endpoint itself, with cookies, and learn the same.

A session that ends without a sign-out used to keep the marker until the browser closed. **`/_teme/session` now clears a marker whose session has ended**, so that browser is given stored pages again and stops asking. Someone signed in before 1.7a carries no marker until they sign in again, and gets the pages anyone gets.

## Who is reading: `/_teme/session`

The one uncached endpoint (study R §3.3, I-163): `GET /_teme/session?path=…` (route `teme.session`) answers `{"signedIn": bool, "edit": {"href", "label"} | null, "token": string | null, "name": string | null, "moderate": string | null}` with `Cache-Control: no-store, private`. The page itself stays the same for every reader, and is stored; only this answer is personal, and nothing keeps it. `_teme` is reserved (`Paths::RESERVED`), so no address pattern can reach it, and the page cache passes it by.

**The `reader` group** (D10, `bootstrap/app.php`): `AnswerAnonymousReaders` first, then `EncryptCookies`, `AddQueuedCookiesToResponse`, `StartSession` and the admin's own checks, `EnforceSessionLifetime`, `AuthenticateSession` and `EnsureAccountIsActive`. A browser with no marker is answered by the first, **before any session middleware**: no session is started and no cookie set, where the `web` group would start a session (a `database` row) and set two cookies for every reader who asked. Laravel's middleware sort moves only middleware in its priority list among themselves, so the first stays first.

| Who asks | Answer | How |
|---|---|---|
| A browser with no marker | `{"signedIn": false, "edit": null, "token": null, "name": null, "moderate": null}` | The `reader` group's first middleware, before any session: no session, no cookie (D10) |
| A marked browser whose session has ended | the same, and the marker cleared | So the browser is given stored pages again, and stops asking |
| A signed-in person who may edit the item the path shows | `signedIn: true`, `edit` its editor and "Edit post" (the type's singular), `token` as below, `name` the account's name (1.8b′), `moderate` the Comments screen's address when they look after the item's comments (1.8c″) | `EditLinks` (D11, D12); `looksAfterCommentsAt()` also counts a later page of the item's comments as the item, and `moderate` is one string for every item, never an ID |
| A signed-in person on any other page, or who may not edit it | `signedIn: true`, `edit: null`, `token` and `name` as above | |
| A suspended account, or a session past the admin's limits | the admin's own redirect | `EnsureAccountIsActive`, `EnforceSessionLifetime`. Core's script asks with `redirect: 'manual'`, so it shows nothing |

**The page is found from its path, never from an ID written in the page** (D11): a content ID is a ULID, whose first part is the moment its draft was made, so a public page would tell anyone when a story was first drafted. `EditLinks` (`app/Domain/Site/Queries`) resolves the path as `PathResolver` does, with its liveness condition, and asks the editor's own rule, `Gate::allows('update', …)` (`ContentPolicy::update()`). **The link belongs where a page shows one item by itself** (D12): the item's own address, or the site's address when the item is the chosen home page. A list, a search, a date, a term's or a person's archive, and the posts page get none: the admin edits one term or one person only in its list, so WordPress's "Edit Category" and "Edit User" wait for such screens.

**The token, only where one is needed.** Laravel 13's `PreventRequestForgery::handle()` lets a request through when `hasValidOrigin()` passes, before it compares tokens, and it passes a request whose `Sec-Fetch-Site` is `same-origin` (`same-site` doesn't). The script's own request is same-origin, so a browser that sends Fetch Metadata sends `same-origin` here, and will with a form posted from the page, which needs no token. A browser that sends none gets the session's token. A reader with no marker has no session, so gets none; nothing on a public page posts before 1.8's comments, which carry that case on. 1.8b′'s script fills a comment form's `_token` from this answer, and shows `name` in the form's "You’re signed in, so you’ll comment as …" in place of the guest fields (`docs/architecture/comments.md`, *Core's script*).

**This browser's own comments: `/_teme/comments/pending`** (1.8b′, D6). `GET /_teme/comments/pending?path=…` with the browser's key in the `X-Teme-Commenter` header answers `{"comments": [{"id", "parentId", "html"}]}`, `Cache-Control: no-store, private`, and like `/_teme/session` starts no session and sets no cookie: it is outside the page cache, which passes `_teme` by, and the pages themselves stay shared. It returns what this key wrote on the item that waits (pending, and spam, which reads as held), and what was approved since a stored page could have been drawn, which is `PageCache::lifetime()` plus its render window, at most 20 (`CommentThreads::OWN_LIMIT`), each drawn by the theme's own comment partial. The item is found by its address as a post finds it, never an ID; a key that isn't one answers `[]` before anything is read (`docs/architecture/comments.md`, *Core's script*).

**Core's small script** (D13, I-247) is inline at the end of `<body>`, from the document shell, the same for every reader, so the page stays shared. It keeps its answer as a promise under `Symbol.for('teme.reader')`, which core's comments script (1.8b′), drawn wherever a thread is, form or not (1.8c″), pushed to the `teme-core-scripts` stack and drawn right after it, reads instead of asking again. It checks the marker, asks, and inserts the link right after the skip link, never inside the theme's markup: the default theme's `.site` is a size container, and a container holds a fixed element to its own box. Its words come from the server, set as text, and it follows only a link to the site's own origin. The theme still ships no JavaScript, and its budget still allows none (I-253). Whenever public pages get a content security policy, it allows the script by its hash, never by a nonce: the page is shared, so a nonce would be the same for every reader.

**The "Edit post" link, as the design pass drew it** (I-468, `docs/prototypes/2026-09-22-theme-v1.source.html`):

| | Built | Why |
|---|---|---|
| **Who gets it** | A signed-in person who may edit the one item the page shows: an article, a page, the page chosen as the home page. A reader gets nothing: no element, no style that takes room, no request | D11, D12; the question 1's A |
| **Where** | Fixed at the bottom inline-end corner, `1rem` from each edge plus the safe areas | Floating, as Ghost's staff toolbar and Emdash's editing pill float. The landmark rule (2026-09-28) keeps no content outside a landmark, axe's `region` rule, which every public page is held to; WordPress's admin bar and Ghost's toolbar are navigation landmarks too |
| **Look** | A pill (`border-radius: 999px`), `min-block-size: 2.75rem` (44 px), `padding-inline: 1.125rem`, text `600 .9375rem/1.2 system-ui`, a light shadow for its lift, a transparent 1 px border that forced colours draw | 44 px is the touch target. ## The commands

| Command | Does |
|---|---|
| `teme:cache:purge {tags?*} {--url=*}` | removes the stored pages carrying any of the tags given, or every page at an address given, in any case or query (`--url=/about/`, with or without its host), for an operator who changed something outside Teme (D11), and, with a CDN, queues the same purge for it. Operations purge on their own |
| `teme:cache:clear` | removes every stored page, as a purge of `*`, so it records itself for the race guard, and, with a CDN, queues the same purge for it: the site's host. Run after a deploy that changes a theme's or the admin's built files, whose old addresses stored pages still name; 1.13's `teme:deploy` runs it. **An operator also runs it after changing `APP_ENV`** (stored pages keep the `X-Robots-Tag` they were drawn with, or lack it, I-1022) **and after setting or unsetting `TEME_DISALLOW_SITE_CODE`** (stored pages keep the site code they were drawn with, I-1089), until `teme:deploy` does. It isn't hooked to `optimize:clear`, which a build may run with no database |
| `teme:cache:prune` | removes expired pages and set-aside copies through the expiry index, and forgets purges older than `RENDER_WINDOW`, **every minute** (`routes/console.php`), as often as pages expire, so files of addresses nobody asks for again never pile up. **While the cache is off it removes every page** (D8), so turning it on again starts afresh, and purges the whole site at the CDN the first time it removes any. It also queues the CDN's drain whenever purges wait for it. With the static-file driver it removes the files two minutes before their pages, and, with the driver off, every file it left |
| `teme:cache:warm {--limit=1000}` | draws and stores the home page, every archive and the live items, newest first, one at a time inside Teme (*Warming*, above). Run it after `teme:cache:clear` |
| `teme:cache:check-static {--url=}` | writes a probe page, asks the web server for it as every kind of request, and says which of the static-file driver's rules it keeps (D11); `--url` is APP_URL by default, `http://127.0.0.1:8080` inside the web container |

**The admin's button is built** (1.9h; `docs/superpowers/plans/2026-10-08-phase1-slice09h-tools-screens.md`, D5 and D6 are I-1144 and I-1145). **Tools › Page cache** is for holders of `page-cache.clear`, administrators (I-1024). It shows whether the page cache is on; where pages are kept, in words for each of the three drivers; how long a page, a search's page and a "not found" page live, each capped at a page's life as `PageCache` caps it (I-500); the CDN in front, when there is one; and when the cache was last cleared here and by whom, read from the security log for display only. Its button runs `ClearPageCache` (*Every Operation*, above). It shows no count of pages (I-467, I-950): a store can't say how many pages it holds without reading every tag row or listing a keyspace, and a counter each store keeps is parked.

## Not an Operation

A stored page is cache, a sink (`docs/architecture/operations.md`, *Telemetry sinks*): deleting every one changes nothing but speed. The store and its purge times are written by the page cache alone, nothing decides from them, and the commands call the page cache as `teme:security-log:prune` calls `SecurityLog`, with no actor. **The admin's clear is an Operation** (`ClearPageCache`, I-1144), because it is a person's act, authorized by `page-cache.clear`, recorded in the security log and told to the page cache as any change is; the commands stay the operator's and record nothing.

## Request state

Code we write keeps no state between requests or jobs (I-087). `tests/Architecture/NoStaticStateTest.php` forbids a static property or a static variable in `app/` and `packages/`, and binds once for the whole process only the registries boot fills, each listed there with why (1.7e's question 1): a container singleton is shared by every request and job a process serves, and Laravel forgets only scoped instances between them, the queue worker before each job, Octane before each request. What one render learns lives in `RenderRecord`, what one request's or job's Operations tell in `PublicChanges`, the media a request has read in `CardMedia`, and the people a pass or a batch acts as in `Actors`: all scoped, `RenderRecord` started afresh for each page the cache may store.

A hit from the static-file driver's file never reaches PHP, so no scenario sees it: its cost is the web server's. **The static-file driver's scenarios run as production** (`CacheScenarios::on()` sets the application's `env` and `off()` puts it back), since outside production no page gets a file and the scenarios measure what that driver does where it writes them; the others stay in the environment the benchmark runs in, since the CDN scenario reads `X-Teme-Cache-Tags`, which only a response outside production carries.

**The rules.** `public-hit` is 10 ms at p95 on either store (1.7e's question 2, I-567), and a scenario marked `readsNothing`, every hit, fails on any statement whatever its time (D8), since one stray statement fits inside 10 ms. The `STALE` answer and the wait share the group. **Queries** are SELECTs, as before; **Writes** every other statement sent, a failed one too, counted through `Connection::beforeExecuting()` as it is sent, since Laravel's query log records a statement only once it has run and never a refused lock's `INSERT` (D6, `Tally`); **Valkey** the commands sent to the page store's connection. Work that belongs to another request, such as the page a wait is waiting for being stored, is counted by neither (`Tally::aside()`, D9), though it falls inside the timing. **Every public request starts in a fresh scope** (D5), cached or not, as a production request, a queue job and `PageWarmer`'s pages do, so nothing an earlier run read, the settings or an image, is kept.

**Nothing left behind** (D7): the scenarios keep to a folder of their own inside the file store's (`storage/page-cache/benchmark`, git-ignored) and the Redis prefix `page-cache-bench:`, at APP_URL's scheme and host, with pages living an hour; they run only with the database cache store, which the benchmark points at `teme_bench`, or the array store the tests use, and are left out, with a note, with any other. Each scenario's `finish` flushes the store and deletes the rows it wrote: purges, the CDN's queues, files' rows, queued jobs, and the CDN drain's unique lock. The CDN's zone and token are made up, and its drain is queued and deleted, never run. **The Redis store's scenarios run where a Valkey answers** the page store's connection through phpredis, and are left out, with a note saying where none answered, otherwise (D10).

**v0.1.0-beta.7** (`docs/benchmarks/v0.1.0-beta.7.md`, a million articles, provisional under I-154): a hit read nothing on either store, 1.5 to 4.2 ms on the file store and 3.6 ms, one `EVAL`, on Redis. A miss costs, over the same page drawn uncached, 5 SELECTs and 4 writes on the file store, 5 and 5 with the static-file driver, and 4 SELECTs, no write and 5 commands on Redis; an article itself runs 23, 24 or 26 statements by what it shows, since issue 30 (B-343). A `STALE` answer took 13.9 ms on the file store (its refused lock, two writes) and 4.9 on Redis; a wait 96.2 ms on the file store, whose timing includes the other request's store (B-345), and 6.7 on Redis. A quick edit with the cache on adds 9 SELECTs and 4 writes to the uncached one; with a CDN 1 and 3 more, with warming 2 and 1, with the static-file driver 2 SELECTs. The twenty-tag article carries 56 tags, 1,790 characters, all of them in `X-Teme-Cache-Tags`.
