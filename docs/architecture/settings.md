# Settings

Site-wide choices an administrator makes — the site title, the time zone, security limits, module switches — live in **the settings registry**. The design and its evidence are in `docs/studies/settings-registry.md` (study H); this document describes the system as built and is what the code is checked against.

## What is a setting

Ask in order, and stop at the first *yes*:

1. Can a wrong value lock people out, or does it describe infrastructure the operator provisions? → **Configuration** (`.env`, `config/`). Never in the database, never edited in a browser. The site address (`APP_URL`) is configuration.
2. Is it temporary, hiding unfinished code? → **Feature flag** (Laravel Pennant, I-079).
3. Is it words or media readers see, or does it grow with the site? → **Content.**
4. Did nobody choose it — counters, installed versions? → **Module state**, in the module's own table.
5. Does it affect only the person who set it? → **Preference** (I-110; arrives in slice 1.5).
6. Otherwise → **a setting.**

A change that adds a setting names the question it answered *no* to.

## Declaring settings

Settings are declared once, in code, through `Teme\Contracts\Settings\SettingsRegistrar`. One declaration gives the type, the validation, the default, the form control, the generated reference entry, and — through its group — the permission.

```php
$registrar->group(new SettingsGroup(
    key: 'general',
    label: 'General',
    description: 'The site\'s name, tagline, contact address and time zone.',
    section: 'general',
    ability: 'settings.general.manage',
    since: '0.1.0',
    settings: [
        Setting::text('site_title', 'Site title', 'The name of the site…', '0.1.0')
            ->default('My Teme site')->required()->maxLength(120),
    ],
));
```

- **Types:** text, textarea, number, boolean, select, multiselect (from slice 1.2d), url, email, secret, timezone, color (1.6f: `#rrggbb`, stored lower case, or `''`), media and pairs (1.9i, below), and urls, person and hours (1.9j, below). There is no free-form JSON type.
- **`media`** (I-1158) holds one image from the library, stored as its ID or `''` when none, so an address is made when it is drawn (rule 9). A value must be a live image, not a file of another kind and not one in the trash ("Choose an image from the library."). Its control is the featured image's: a preview with *Replace* and *Remove*, or *Choose an image*, which opens the library's picker, and the form sends the ID in a hidden input. `SettingsForm::find()` sends a `media` map beside the values, each media setting's chosen image in the shape the editor's cards get, or null when none is chosen or it is gone.
- **`pairs`** (I-1159) holds rows of a name and a value, stored as `[{"name": "…", "value": "…"}]` and empty by default. Its two column labels are its `options` (`name` and `value`); `max()` bounds the rows (50 when unset), `maxLength()` each value (2,000 when unset), and a name is at most 100 characters. Each part is trimmed and a row with both parts empty is dropped when stored; a half-filled row is for the section's own check to refuse. The rule gives one message for the whole field, and a part that is too long names its row ("Row 2: the content is longer than 500 characters."). Its control is a row of two inputs with *Remove*, then *Add a row*; with no rows it keeps one hidden empty input, so that clearing the list saves.
- **`urls`** (I-1176) holds addresses on other sites, stored as a list of strings and empty by default. The form sends one a line in a textarea (`Setting::urls()`); each line is trimmed and blank lines and repeats are dropped. Each address must be `http` or `https` with a host, at most 2,048 characters, and **never on the site's own host**, since Teme makes those at render so they follow the site when it moves (rule 9); `max()` bounds how many (20 when unset). The rule gives one message for the field, naming the first line that fails as the person counts it ("Line 3 is on this site. …", "At most 20 addresses.").
- **`person`** (I-1176) holds someone with an account, stored as their ID in digits, or `''` for none. A value must be a user that exists ("Choose someone with an account here."). `SettingsForm::find()` gives each person field `people`, a list of `{value, label}`: everyone who may write (`AuthorOptions`, at most 500, by name), then the chosen person while they have an account but aren't among them. It is a list, not a map, because a JSON object with numeric keys comes out in ID order. A person whose account is gone shows as nobody chosen.
- **`hours`** (I-1176, I-877) holds a week of opening hours (`Setting::hours()`, `Setting::DAYS`). The form sends days keyed `monday` to `sunday`, each `closed` or with `hours`, one or two openings of `opens` and `closes` in 24-hour `HH:MM`. It is stored as the days that say something, Monday first, each `{day, hours, closed}`: `[{"day": "monday", "hours": [{"opens": "09:00", "closes": "17:00"}], "closed": false}]`, and empty by default. **Closed wins over any times,** an opening with both times empty is ignored, an opening may run past midnight but never closes the minute it opens, a day has at most two openings, and a second one starts once the first has closed (so the first can't run past midnight). One message, naming the day ("Tuesday: give each opening both its times."). **The stored keys are written in the order PostgreSQL's `jsonb` reads them back,** shortest first (`day`, `hours`, `closed`; `opens`, `closes`), because `SettingsWriter` compares a stored value with `===` (`app/Domain/Settings/SettingsWriter.php`): a week written in any other order would read back unequal to the same week saved again, and every save of the screen, which sends the whole week, would bump the group's version and purge every stored page.
- **The site's accent** (`design.accent`, a color setting) is checked against the light background only, and the dark scheme takes a lighter version of it, `Contrast::darkVariant()` (I-457; `docs/architecture/themes.md`, **Settings**).
- **`->fieldset()` and `->visibleWhen()`** (1.6f) group a setting under a screen's section (`Setting::FIELDSETS`) and hide it unless other settings of its group have these values. Hiding isn't clearing. `SettingsForm::find()` sends every field's `visibleWhen`, so a screen reads the rule from the settings and doesn't repeat it (I-1189); a field that is hidden keeps its stored value, isn't sent and isn't checked.
- **Module switches** (I-077): the `modules` group, one key per module, its value `on` or `off`, a select the module declares rather than a bare boolean (study H). Its `cacheTags` are `*`, since a switch changes every page. Each switch is shown at the top of its own feature's settings page, never on a Modules page (I-485). The first is `comments` (1.8a), read through `Modules::on()`, and shown at the top of Settings › Discussion (1.8d), where `SwitchComments` changes it for holders of `settings.modules.manage`, administrators (`docs/architecture/comments.md`).
- **Every setting documents itself:** a label, a description and a `since` version are required. The registry refuses a setting without them, and an architecture test checks every registered setting.
- The contracts carry **no Laravel types** (rule 5). Constraints are Teme's own — `required`, `min`, `max`, `maxLength`, `options` — translated into Laravel validation inside `app/Domain/Settings/`.

## Groups that follow the content types

Some groups are made from the type registry: a setting for each public type or taxonomy, such as `addresses` (a pattern and an archive page for each type), `discussion` (how a code type's new items start), `seo` (the title and hide rows) and `reading`. Types made on the site (slice 2.1, `docs/architecture/content-types.md`) change while the process runs, so these groups are **derived**: `SettingsRegistry::derive($key, $build, $stamp)` holds the group's place in the order, builds it when first read, and builds it again whenever the stamp, `ContentTypeRegistry::stamp()`, answers differently. `group()` and `all()` do this for every caller, and a derived group is checked as any group is. Nothing is built at boot, so a request that reads no such group pays nothing. A second group under a derived group's key is refused.

A type made a moment ago therefore has its address, archive page, title, hide and discussion settings at once, in every process, with no restart. `AddressSettings::current()` reads the keys the group declares as it stands now. The preference definitions for a list's columns are not derived: a worker started before a type was made lacks that type's `lists.{type}.columns` until it restarts.

**Settings › Reading** (the `reading` group, `ReadingSettingsGroup`, `settings.general.manage`) holds `posts_per_page`, the number of items on a listing page (0 uses the theme's own), and `home_types`, "Types on the home page and in the main feed" (I-3298): a multiselect of the public types that have an archive, posts ticked by default. The home page (or the posts page, when the home page is a page) and the main feed list the newest items of the ticked types, and a type that stops being public or loses its archive drops out of the answer at once and from the stored value at the next save. A term's, an author's and a date's archive do not read it (`docs/architecture/addresses.md`). Its page also draws the addresses group's Home page, below the number of items.

## Storage

```
settings          group_key   varchar(191) PRIMARY KEY
                  overrides   jsonb NOT NULL DEFAULT '{}'   -- CHECK object, CHECK size <= 64 KiB
                  secrets     text NULL                     -- encrypted under APP_KEY; never cached
                  version     bigint NOT NULL DEFAULT 0     -- optimistic concurrency
                  updated_by  bigint NULL → users.id
                  updated_at  timestamptz
                  draft_values      jsonb NULL             -- Settings › Design's unpublished keys; CHECK object, size
                  draft_updated_by  bigint NULL → users.id
                  draft_updated_at  timestamptz NULL

settings_changes  id ulid, group_key, changed_keys jsonb, before jsonb, after jsonb,
                  actor_id → users.id, origin (human|ai|import|system), created_at
                  -- append-only; the last 100 changes per group are kept
```

**One row per group, with a typed JSONB body** — rule 2's own shape, "one row per thing, typed values in a single JSONB column governed by a registry". It is not `wp_options`: rows are bounded by registered groups, there is no autoload, values are typed, unregistered keys are refused, each group is capped at 64 KiB, and defaults are never stored.

The column names differ from study H's sketch on purpose: `group` and `values` are reserved words in SQL.

## Reading

`Teme\Contracts\Settings\SettingsReader` — `group()`, `get()`, `string()`, `int()`, `bool()`. A group's overrides are read through `Cache::memo()`, then the cache store, then one primary-key lookup, and merged over the registry's defaults. **The cost depends on the groups a request touches, never on how many settings exist.**

- Defaults resolve at read time. A group row stores only what an administrator changed.
- Typed accessors throw when the value is not of the type asked for.
- **Secrets are never returned by the reader and never cached.** They are read only through `Teme\Contracts\Settings\SecretReader`, which is never handed to themes or views.
- Settings never feed `config()`. Loading them into config at boot would read every group on every request — autoload again.
- **During a design preview** (`DesignPreview`, one request's), the `design` and `theme.*` groups read their drafts over their live values, key by key. The repository asks for `DesignPreview` at each read, since it outlives a request.

## Writing

Only through Operations. A group edited on the generic screen is written by `UpdateSettings`. **A group with its own screen** (`SettingsGroup::$screen`) **is written only by that screen's Operations**, and `UpdateSettings` refuses it: `addresses` by `ChangeAddresses`; `discussion` by `ChangeDiscussionSettings` and `modules` by `SwitchComments`, both on Settings › Discussion (1.8d); `design` and every `theme.{code}` by Settings › Design's `SaveDesignDraft`, `PublishDesign` and `DiscardDesignDraft`, and a theme's slots also by Content › Navigation's `BindNavigationSlot`, and cleared by `DeleteNavigation`. All write live values through `SettingsWriter`, the shared write step below, so every change lands in the same history.

**`SettingRules`** holds a setting's validation rules (`for()`) and its stored form (`normalise()`), so `UpdateSettings`, `SettingsWriter` and `SaveDesignDraft` agree: a draft holds each value exactly as publishing it would store it. **`SettingsWriter` keeps a row that holds a draft**: a write that changes nothing deletes a version-0 row only when it holds none.

1. **Authorize** — the actor holds the group's ability (for example `settings.general.manage`).
2. **Validate** — unknown keys, secrets sent as values, and secrets supplied by the server's environment are refused; every value is checked against its declaration.
3. **Perform**, in `SettingsWriter` — lock the group row, check `version` (a stale form throws `StaleSettingsException`), write only keys whose value actually changed, **never write a default** (a value equal to the default removes the override), bump `version`, append a `settings_changes` row.
4. **After commit** — `SettingsWriter` forgets the group's cache entry (rule 6), and the Operation writing the group purges every stored page carrying the group's declared `cacheTags`: `settings` for `general`, `theme` for `design` and `theme.{code}`, `*` for `addresses`, `seo` for `seo`. A page that reads a group records them.

**A part's own check of a group** (`SettingsCheck`, I-1101) is asked at step 2. It is an interface with `group()` and `problems(array $values)`, registered under the container tag `SettingsCheck::TAG` (`teme.settings.checks`) from its part's own provider. `UpdateSettings::validate()` asks every check for the group it is saving and reports their problems with the types' own, keyed `values.{key}`, before anything is read or written. A value that isn't of its setting's type is left to the type's rule. A section is often its own check: robots.txt's extra lines are held to the file's grammar, a title template may name only Teme's tokens, a verification tag may not use a name core writes, and the publisher's business, person and owner are held to what the chosen kind shows (*Search and social*).

**Secrets** are write-only. Forms receive `{isSet, source}`, never a value. An empty submission means *unchanged*; clearing is explicit. A secret may name an environment variable; when that variable is set in the server's environment it wins, and the form shows the field as provided by the server.

## Screens

One Inertia page, `settings/group`, renders any group from its schema, using the **shared field components** in `resources/js/components/fields/` — the same set the content field registry grows from in slice 1.3. The sidebar's Settings entry lists only groups the user may manage. A group with its own screen draws the same tab strip on its own page: Settings › Addresses is `settings/addresses` (`docs/architecture/addresses.md`), Settings › Design is `settings/design` (`docs/architecture/themes.md`, **Settings**), and Settings › Discussion is `settings/discussion`, which also shows the `modules` group's comments switch (`docs/architecture/comments.md`). Settings › Search and social is `settings/search-and-social` (*Search and social*, below).

**A group is a Settings tab of its own when it has no screen, or when its screen is the Settings route named for it**, `'settings.'.$key`: Addresses, Design, Discussion and Search and social are; a theme's `theme.{code}` group, edited on Design's screen, isn't, nor is `modules`, edited on Discussion's. `/admin/settings/{group}` redirects a group with a screen to it. `screen` is read both ways, as that marker and as a route name: for `discussion` and `modules`, `settings.discussion` is both, and a test holds every group's `screen` to a route that exists (1.8d's D2). `addresses` names `settings.addresses` while its route is `settings.addresses.show`, issue #55, still open.

**A group keeps `screen` for an Operation of its own, and not for a screen of its own** (I-1163). A group with `screen` set is refused by `UpdateSettings` ("Change these settings on their own screen.") and written only by that screen's Operations, as `ChangeDiscussionSettings` writes `discussion`, which needs one because its save depends on the comments switch. Search and social has a screen of its own and no such dependency: its checks already live in `UpdateSettings`, through `SettingsCheck`, so its `screen` is null, the screen answers the group's own address, and it saves through `UpdateSettings` like the generic form.

**A Settings page that isn't a group** (`SettingsPage`, `App\Domain\Settings`, I-1090) gets its tab through an interface, `key()`, `label()` and `ability()`, that a part registers from its provider's `register()` under the container tag `SettingsPage::TAG`. `SettingsNavigation` lists these after the groups, for whoever holds the ability, so the sidebar's Settings entry, the tab strip and `SettingsHub` all see them. Its key is also its address under `/admin/settings/`, and it can never be a group's: a group key's first part allows no hyphen (`SettingsRegistry`), and the page's routes sit before `settings/{group}`. The first is Site code (`docs/architecture/security.md`, *Site code*).

## Search and social (the `seo` group)

Slice 1.9 built it in parts: 1.9a the group and its shell (`docs/superpowers/plans/2026-10-07-phase1-slice09a-foundation.md`, D1 to D19 are I-1010 to I-1028), 1.9b the titles section (`2026-10-07-phase1-slice09b-head.md`, D1 to D14 are I-1029 to I-1042), 1.9d the Feeds section (`2026-10-07-phase1-slice09d-feeds.md`, D1 to D20 are I-1063 to I-1082), 1.9f robots.txt's section and `SettingsCheck` (`2026-10-08-phase1-slice09f-sitemaps-and-robots.md`, D1 to D23 are I-1097 to I-1119), 1.9i the other sections and the screen (`2026-10-08-phase1-slice09i-search-and-social.md`, D1 to D17 are I-1156 to I-1172), 1.9j who publishes the site, at order 300, and each type's page and article type, at order 350, both sections drawn on the screen by kind (`2026-10-08-phase1-slice09j-who-publishes.md`, D1 to D20 are I-1173 to I-1192), and 1.9k the editor's section, which reads this group's title rows, separator, hide rows and default social image to show an item's result as its page will make it (`2026-10-08-phase1-slice09k-editor-search-and-social.md`, D1 to D17 are I-1193 to I-1209; `docs/architecture/admin-design.md`).

One group, one row and one ability, `settings.seo.manage` (administrators; I-1024), built by `SearchAndSocial::group()` from **sections** (I-1020). A section is a class implementing `SearchAndSocialSection`: an `order()` (a number its class answers with), a `key()` (lower-case words joined by hyphens), a `label()` and its `settings()`. A part registers its section from its own provider's `register()` under the container tag `SearchAndSocial::SECTIONS`; `SeoServiceProvider::boot()` builds the group once every provider has registered, so a section's place in `bootstrap/providers.php` doesn't matter. The group is refused at boot when two sections share an order or a key, and the registry refuses a setting two sections both declare, as for any group. Core's orders go up in hundreds, so a plugin's section fits between two.

It is **not sensitive** (changing it asks for no password), and its `cacheTags` are `seo` (`PageTags::SEO`), so every page that resolves a title, a robots value, a social card or a feed, and every stored `robots.txt` and sitemap, carries `seo` and a change removes them. Its tab follows Discussion's, since `SeoServiceProvider` sits after `CommentServiceProvider`. Each setting is read through `SettingsReader`, never the table, so a page that reads one carries the tag.

- **The title rows are made from the registries** (I-1032, I-853): a type or taxonomy registered in code gets its rows when the group is built at boot, and the prefixes (`title_type_`, `title_taxonomy_`) keep a type called `author` from meeting the author row. A template is text with tokens (`docs/architecture/themes.md`, *The title*); a blank one reads as its default, and one that names a token Teme hasn't got is refused when saved (I-1166). The home page and "page not found" have a template and no hide box (I-1036), and search results a template and no hide box because they are always hidden (I-1034). A hide box marks every page of its kind `noindex, follow` (`docs/architecture/themes.md`, *The head*) and leaves it out of the sitemaps. Each row's accessors are on `TitlesAndListing` (`template()`, `hidesType()`, `hidesTaxonomy()`, `hidesAuthors()`, `hidesDates()`, `separator()`), and `rows()` gives the screen each row's template key, default and hide box.
- ***Discourage search engines*** (I-1021) is read first by `RobotsMeta` on every page the shell draws, so it wins over any page's own value and every page carries `seo`. Its description is fixed (I-883): "Every page is marked noindex and the sitemap is switched off, so search engines drop the site. For a site that isn’t ready to be found." `WholeSite::discouraged()` is how every other part asks. Feeds ask it for their own `X-Robots-Tag` (`noindex, follow`, or `noindex, nofollow` while discouraged; I-1078). While it is on, `robots.txt` keeps its usual rules and loses its `Sitemap:` line, and every sitemap address answers the site's 404 (I-883, I-1115).
- **Who publishes the site** (I-1175, I-1184) says who search engines are told publishes the site, from a closed list. `publisher_type` is one select, stored as the schema.org type's name, or `''` for **nobody in particular, the default**: no publisher is output until one is set. `PublisherKinds::options()` lists them: nobody; six organizations (`Organization`, `NewsMediaOrganization`, `Corporation`, `NGO`, `EducationalOrganization`, `GovernmentOrganization`); six local businesses (`LocalBusiness`, `Store`, `Restaurant`, `LegalService`, `AccountingService`, `MedicalBusiness`); and `Person` (I-876). "Professional service" isn't offered: schema.org's release marks the general type deprecated, so a legal or accounting firm picks its own and any other professional firm picks `LocalBusiness` (I-889). The other eighteen settings are shown only where they apply, each declaring `visibleWhen` on `publisher_type` (I-874): an organization's or business's name (the site's title when empty), other name, logo and the owner's three; a person's `publisher_person`; any publisher's profile links; and a business's ten (address in five parts, phone, latitude, longitude, price range, week). A field the kind hides keeps its value, isn't sent and isn't checked, so switching back finds it. The graph this makes is in `docs/architecture/themes.md`, *The head*.
- **Who publishes the site checks its own values on save** (`WhoPublishes` is a `SettingsCheck`, I-1185). It reads the stored values under those sent, since a hidden field isn't sent, and checks only what the kind shows. A person kind needs a person chosen; saving it with nobody is refused, but deleting an account never is (I-878). The logo must be at least 112 by 112 pixels (`WhoPublishes::LOGO_SMALLEST`); that it is clear on white is in its description, since no check can see it (I-1179). The owner's name and website go together, and the website is a full address that isn't this site's. A business needs its street address and its town, since the gate leaves a `LocalBusiness` without an address out of the graph; its phone is digits, spaces and `+ - ( )` with at least five digits; its country is the two-letter code `addressCountry` recommends, since Teme holds no list of countries (choosing it by name is I-992); latitude and longitude come together, within -90 to 90 and -180 to 180. Each message names its field. A value of the wrong type is left to its type's rule.
- **Page and article types** (`PageAndArticleTypes`, I-1186) are a section of its own after Who publishes the site (I-888), made from the type registry as the title rows are: for each public type, `schema_page_type_{type}` ("Page type for posts": Web page, About page, Contact page or Collection page) and, when the type's items may choose a main entity, `schema_article_type_{type}` ("Article type for posts": those main entities, then `none`, "Not an article", or "Nothing" for a type whose main entities aren't all articles). Each is set to what the type declares, so a site that never changes one follows the registry if a later Teme changes the type's. `TypeSchemas::for()` puts the site's choice before the type's own entry, and a stored value the type doesn't offer, as an import could leave, falls back to the type's; an item's own choice still comes first (`docs/architecture/content-types.md`).
- **The default social image** (I-1161) is a `media` setting, read by `PageHead` after a page's social image, its featured image and the first image in its body, on every page that draws social tags, archives and the home page included (I-293). Saving a new one queues its share images as the person who saved it (`DefaultImageCard`, on `SettingsChanged`); `docs/architecture/media.md` has the rest.
- **The verification tags** (I-1160) are checked on save through `SettingsCheck`: each name must be a meta tag's name (`MetaTag::KEY_PATTERN`) and never one core writes (`description`, `robots`, `twitter:card` or `viewport`, in any case), since the site's entry wins over core's; each row needs its content, which may not hold a `<`, as it would if the whole tag were pasted; and a name appears once, since the head keeps the first entry of a name. They are written on the home page only (`docs/architecture/plugins.md`, channel 1).
- **The feeds' two settings** (I-1075) are read once a feed through `FeedsSection::items()` and `fullText()`. Their hint, which says the feeds are at WordPress's addresses, is the screen's, keyed by section, since `SearchAndSocialSection` has nowhere to carry one.
- **robots.txt's two settings** (I-1102) are read through `SettingsReader`, so `/robots.txt` as the page cache stores it carries `seo`. The extra lines are checked on save by `RobotsRules`: User-agent, Allow, Disallow and Sitemap lines, `#` notes and blank lines, nothing else, and the first bad line is reported with its number.
- **The 404 log's two settings** (I-1162) are applied by the minute's run, `teme:redirects:count`, which passes them to `RecordAddressCounts`, and never on a reader's request: the page cache's hit path keeps reading nothing from the database (`docs/architecture/page-cache.md`). The patterns are read in the stored form of the paths they are matched against. The 404 log's screen reads its size from `NotFoundLogSection::size()` and links "Change the log’s size and what it ignores" to this screen's section for whoever holds `settings.seo.manage`; the section links "Open the 404 log" for whoever holds `redirects.manage` (I-970).

**The screen** (I-1163 to I-1170) is `GET /admin/settings/seo` (`settings.seo`), saving at `PUT /admin/settings/seo` (`settings.seo.update`), both before `settings/{group}` and behind `settings.seo.manage`. `SearchAndSocialScreen` builds its data from `SearchAndSocial::ordered()`, so a section a plugin registers appears in its place, with its fields on the generic controls; core's sections are drawn by key, with core's words for each (the query's `NOTES`). **Who publishes the site has a component of its own** (`resources/js/components/seo/who-publishes.tsx`, I-1189), chosen by key. It draws the kind select with its options in two groups, "An organization" and "A local business", and then each field only while its `visibleWhen` holds against the kind as it is chosen; nothing is saved until *Save*, and a field that is hidden is not drawn, so keeps its stored value. "The business" and "Owned by" are fieldsets of their own, the business's inputs set to `autoComplete="off"` since they are the business's and never the person's. Under *Person*, a note says when the chosen person's account is gone. *Opening hours* is the weekly table (`hours-setting.tsx`, also the generic form's `hours` control): a row for each day with *Opens* and *Closes*, a *Closed* box that disables that day's times, and *Add a second opening* and *Remove*. The screen's extras are the `publisher` prop of `SearchAndSocialScreen::data()`, from `PublisherScreen::data()`: the kinds with their groups, the site's title an empty *Name* falls back to (its placeholder), and whether the person is gone. *Page and article types* is drawn on the generic controls, a select for each setting in the order the types are registered. Each title row shows what its template gives as it is typed, "Shows as: …", filled by `resources/js/lib/title-template.ts`, which twins `TitleTemplate::fill()`, from tokens the server gives each row (the newest live item of a type, a term, the viewer's name, this month, a sample search, the site's name and tagline); the home row also shows its second page (I-904). robots.txt's section shows "What robots.txt says now", from `RobotsTxt::text()`, the function the route calls. The first panel says "This copy isn’t the live site." whenever the application is not in production. The save's toasts say what changed when *Discourage search engines* turns on or off. `UpdateSettings` does the writing; the controller exists for those toasts and its redirect. Home shows administrators a warning, "Search engines are asked to stay away from this site.", with a link to the switch, while it is on (`SearchEnginesNotice`, I-873, I-1167).

The generated reference, `docs/reference/settings.md`, is regenerated once at the end of slice 1.9, not by each part (I-1028), so until then it doesn't list this group.
