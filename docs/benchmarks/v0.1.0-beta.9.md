# Scale benchmark — v0.1.0-beta.9

> **Provisional (I-154).** Slice 1.9's release run, in a cloud container (4 vCPU, 15.7 GiB), never a quiet machine: freshly seeded with a million items, 40,000 comments, 100,000 redirects and a 404 log of 100,000 addresses (`teme:bench:seed --items=1000000 --comments=40000 --redirects=100000 --not-found=100000`, 1,744 s, the database 13 GB on disk), vacuumed, then run with the load average at 0.09, 1.18, 1.94 and the CPU 94.0% idle. It may be run again locally before the tag. This is the fourth run on that seed: the first stopped at the posts sitemap's page 2, since the seeded IDs start with a capital and a page's address takes only lower-case keys (B-501, draft); the second and third found what *What was fixed* lists.
>
> **What changed since beta.8.** Every public page now carries slice 1.9's head and structured data. Against beta.8, the public pages' statements: the front page 16 → 18; an article 29 → 29; the twenty-tag article 27 → 29; a category 17 → 19; an author's page one and page 400 17 → 19; the year archive 15 → 17; the four searches 14, 15, 15, 15 → 16, 17, 17, 17; `public.item` 20 → 19; `cache: miss, article` 32 → 33. Each listing gains two statements, what slice 1.9's head and graph read; an article's count moves with the random article picked, as beta.8 found (B-344), by what its featured image and its neighbours read; the publisher is nobody in particular in every one of them, so the graph reads nothing more.
>
> **Redirects among 100,000.** A lookup: 0.7 ms an exact redirect and 0.8 ms an address none answers with all 100 patterns tried, each from `redirects_source_unique`. A reader's request answered by a redirect: 3.3 ms to an address, 2 statements; 7.2 ms to an item, 5 statements, reading the item and its address too. Tools › Redirects: page one 5.3 ms, 4 statements; halfway down 12.1 ms, 7 statements; the tabs' counts 26.9 ms; a search for a word every source holds 14.7 ms, and for one source 22.9 ms, through the trigram indexes F2 added.
>
> **A flood of addresses nothing answers.** Each request for a new address: 17.1 ms, 9 statements a request (900 for the run's 100), and 0 writes. The minute's run: 52.7 ms a thousand addresses, so 100,000 take 5.3 s of the 30 allowed; the log held 100,000 addresses after; the process used at most 114 MB. With the page cache on, each new address is stored for ten seconds (I-262): 4 writes a request, a finding to review. The log's screen: page one 6.8 ms and halfway down 7.8 ms, 2 statements each, from `not_found_log_most_asked_index`.
>
> **Sitemaps.** 632,200 live posts make 317 pages of 2,000; page 317 is the deepest asked for. The index with every page found afresh: 613.2 ms, so about 970 ms at a million live posts, one pass over `contents_sitemap` (I-296); its plan: Index Only Scan using `contents_sitemap`, a WindowAgg and no Sort, Heap Fetches 6,454 of 632,200. Page 2 and page 317: 146.8 ms and 72.7 ms, 3 statements each; page 317 from `contents_sitemap` by key, page 2 from `contents_pkey`, which the planner prefers where the range runs to the table's end and posts are nine rows in ten (232 rows filtered for 2,000). Page 317 is the last, 200 entries, so its time is not page 2's; and both are drawn by the posts sitemap and its XML without the HTTP kernel (B-501, draft).
>
> **The head with every fallback.** 56.1 ms, 31 statements against `public: article`'s 29: the canonical's item, looked for at its address and found with none; the default social image's row; and the publisher's logo's row; less the one read of its neighbours' images a plain article makes.
>
> **What was fixed.** (F1) *404 log: halfway down*: the cursor's bound was only a filter, so the index was read from its first row, 50,001 rows removed (120 ms in `EXPLAIN ANALYZE`); the bound now comes first, the index's range starts at the cursor, 1 row removed (0.7 ms); the scenario 36.6 → 7.8 ms. (F2) *redirects: search, one source*: a sequential scan of all 100,000 redirects (149 ms); trigram indexes on the source as shown, the target and the note (`2026_11_05_100000_add_redirects_search_indexes`) make it three bitmap index scans (24 ms). (F3) Tools › Redirects joined each item to its address as `paths.target_id = contents.id`, a `varchar` against a `char`, which no index of `paths` can serve: a sequential scan of 802,202 addresses each page; the join is now on `contents.id::text`, as `ListedItems` writes it (136 → 0.15 ms). (F4) The redirects' states asked which of the shown sources the site answers with a raw clause `A OR B` written without its parentheses, so `path IN (…) AND A OR B` read every old address on the site; in parentheses it reads the shown sources from `paths_path_unique`. Together: halfway down 752.9 → 12.1 ms; a word every source holds 729.3 → 14.7 ms; one source 716.4 → 22.9 ms.
>
> **What failed and wasn't fixed.** (1) *redirects: halfway down* runs 7 statements to page one's 4: page one is the 100 patterns, the newest, which have no item, file or exact source to check, so it skips three reads by its data, not its code (B-502, draft). (2) *redirects: the tabs' counts*: a count of every redirect reads the table (D14 2). (3) The sitemap index and page one: the "sequential scans" on `contents` and `terms` are `EXISTS` probes that stop at the first live row (0.08 and 0.28 ms); the index's 613.2 ms is I-296's one pass, over its budget of 150 at this size, for review (D14 4); page one 161.8 ms and page 2 146.8 ms read `contents_pkey` rather than `contents_sitemap`, the planner's choice for a range that runs to the table's end (D14 2, 3). (4) As in beta.8, with clean plans or the planner's choice: the four admin searches, `scheduler.claim`, *What Empty spam covers*, one deletion inside Empty spam and the erasure's daily run (B-346); and by time alone, the container's: *public: article, long thread* 148.0 ms and *cache: miss, article, static driver* 100.0 ms (I-153, I-154).
