## Result

33 of 38 scenarios pass their time budget, against a million content items and a million media items together. **Every query-plan rule passed**: no sequential scan on a table over 10,000 rows, no sort of more than a page in a statement that pages, and — new in 1.4d (check 4) — no scenario whose deep page runs more queries than its page one. B-081's four content tab-and-sort scenarios (`all tab, by title`, both pages; `published tab, by published date`; `trash tab`) all pass their index-order check, confirming what content-management.md promises.

## Accepted misses (I-153)

Five scenarios missed their time budget. None comes from a real defect (a plan whose cost grows with the table, or a forbidden scan) — each was checked by hand — so under I-153 none blocks the tag. Budgets and the run count are unchanged (I-148).

| Scenario | p95 vs budget | Cause | Backlog |
|---|---|---|---|
| Mine tab, by updated, page one | 233.5 ms vs 150 | The query itself runs in 0.167 ms (an index-only scan); the measured p95 reflects host load, not the query | B-101 |
| Category filter, with children | 422.5 ms vs 200 | Same cause as B-079 (1.3d): the dense plan is correct and does not grow with the table | B-102 |
| Media search: harbour | 553.7 ms vs 300 | A correct trigram GIN bitmap scan, but "harbour" is one of the seeder's 50 words and matches 40,122 of the million media rows — a data-set artifact | B-103 |
| Picker search: river | 637.2 ms vs 300 | Same cause as the row above; "river" matches 31,600 rows | B-103 |
| Quick edit, draft waiting | 203.1 ms vs 150 | Same class of scenario as B-078 (1.3d): a fixed set of small key lookups and writes | B-104 |

The timings above are provisional (I-154). A clean run on a quiet host will replace them.
