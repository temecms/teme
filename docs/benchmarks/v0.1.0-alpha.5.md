## Result

52 of 56 scenarios pass their time budget, against a million content items and a million media items together. **Every query-plan rule passed**: no sequential scan on a table over 10,000 rows, no sort of more than a page in a statement that pages, and no scenario whose deep page runs more queries than its page one (`editor.history_deep`, `list.sort_author_deep`, the lists' deep pages).

This is the second run on the same data. The first, earlier the same morning, found a real defect: `palette.mixed` took 2,214 ms with a sequential scan of all of `contents`, ranking every matching title and text by `similarity()`. It was fixed before this run (B-199), as below. In the first run `editor.checkpoint` also missed, at 151.7 ms against 150; here it takes 70.2 ms.

Three of alpha.4's five accepted misses now pass: *mine tab, by updated, page one* (233.5 → 72.5 ms, B-101), *quick edit, draft waiting* (203.1 → 126.6 ms, B-104) and *picker search: river* (637.2 → 266.0 ms, B-103).

## The palette's title search (B-199)

Titles are filtered by `title ILIKE` and ordered by word-similarity distance, `'query' <<-> title`, which PostgreSQL runs as `title <->> 'query'` on the trigram GiST index `contents_title_trgm_gist`. One index scan gives both, so the first page costs the same however many titles match. `EXPLAIN (ANALYZE, BUFFERS)` at a million items:

A common string, "har" (about 126,000 matching titles):

```

  Buffers: shared hit=13404 read=2039 written=1568
  ->  Index Scan using contents_title_trgm_gist on contents  (cost=0.41..354530.61 rows=126082 width=74) (actual time=170.890..171.019 rows=20.00 loops=1)
```

**The published text could not be bounded**, so the palette no longer searches it. The best bounded form walks `contents_pkey` in ID order and stops at the first page of matches: 2 ms for a common word ("harbour"), but 2,912 ms for a word no article holds ("har"), which walks all million rows; the GIN index on `search_tsv` gives no order. The palette offers **Search in text →** instead, which opens the main type's list with its In text search (`search.body_one_word`, `search.body_phrase` above). Its budget at a million rows, for a common and a rare word, is for 1.6h's search budgets (I-153).

## Accepted misses (I-153)

Four scenarios missed their time budget. None comes from a real defect (a plan whose cost grows with the table, or a forbidden scan) — each was checked by hand — so under I-153 none blocks the tag. Budgets and the run count are unchanged (I-148).

| Scenario | p95 vs budget | Cause | Backlog |
|---|---|---|---|
| Category filter, with children | 213.7 ms vs 200 | Same cause as B-079 (1.3d): the dense plan is correct and does not grow with the table. Down from 422.5 ms in alpha.4 | B-102 |
| Media search: harbour | 427.6 ms vs 300 | A correct trigram GIN bitmap scan; "harbour" is one of the seeder's 50 words and matches about 40,000 of the million media rows, a data-set artifact. Down from 553.7 ms | B-103 |
| scheduler.claim | 14,340.4 ms vs 500 per pass of 50 | About 44 statements per publication, each around 4 ms on this host, none slow; 100 of a pass's are each row's scheduler's roles and permissions, reloaded per row | B-200 |
| bulk.edit, per item (batch of 25) | 384.2 ms vs 150 | 33 statements per item (one `UpdateContentDetails`, its projections and counts), none slow; 165 ms an item when profiled alone | B-201 |
