# Install on Dokploy as one Application

Branch `deploy/all-in-one`. Teme installs on Dokploy as a single Application from any of its sources (the image `ghcr.io/temecms/teme`, a Git provider building the repository's `Dockerfile`, or a ZIP): one container runs web, both queue workers, the scheduler, the installer and the updater, against Dokploy's own PostgreSQL service. The template and Compose routes are built beside this on `deploy/dokploy-template`; they own the Compose files and the Compose sections of `docs/guides/operators/platforms/dokploy.md`. This plan owns the image's start-up, the Application updater and the guide's section "Install as one Application".

## Decisions as built

1. **One switch, `TEME_ROLE=all`, explicit.** The image never defaults to it: `docker/compose.dokploy.yml` and `docker/compose.yml` start `web` with no role named (the image's own command), so a default of `all` would make that service run workers and a scheduler a second time. Any other value than empty or `all` refuses to start, with one sentence.
2. **The image starts as root and drops, role by role.** One container can only keep the installer (uid 9990) apart from the site (uid 33) if its supervisor can start processes as either, and only root can; Dokploy has no setting for an Application's user. `docker/teme/bin/teme-entrypoint` is the image's entrypoint: as root with no role it drops to `www-data` and runs the base image's entrypoint exactly as before; started as another user (the installer in Compose) it changes nothing; with `TEME_ROLE=all` it stays root and starts s6-overlay, which the base image already contains and maintains. No new dependency. Because a terminal in the container now starts as root, `php` run as root hands itself to `www-data` (`docker/teme/bin/php-as-site`, after every build step that runs PHP as root). nginx's master runs as root and its workers as `nginx`, which joins `www-data`'s group to read what PHP writes.
3. **Start-up order, by s6 dependencies:** `teme-deploy` (a oneshot as `www-data`: `teme:database:prepare`, the caches, then `php artisan teme:deploy`, which holds `DeployLock`) → `teme-installer-prepare` (a oneshot as uid 9990: `teme:installer --prepare-only`, which never stops the site) → nginx and php-fpm (web), `teme-worker`, `teme-worker-long`, `teme-scheduler`, `teme-installer` and `teme-updater`. A failed deploy ends stage 2 (`S6_BEHAVIOUR_IF_STAGE2_FAILS=2`, already set), so web never answers on a half-migrated site. The image's `STOPSIGNAL` is now `SIGTERM`: the base image's `SIGQUIT` is ignored by s6's init, so a container was always killed at the end of its grace period. `S6_SERVICES_GRACETIME` lets a job finish.
4. **The installer's environment is an allow-list**, built from the container's own: `PATH`, the `APP_*` and `DB_*` settings it needs, `PHP_*`, `LOG_*`, `TEME_EXTENSIONS_*` and `TEME_COMPOSER_BINARY`. Nothing else: no `TEME_DOKPLOY_*`, no media bucket keys, no `TEME_GITHUB_TOKEN`. The configuration cache, which holds every value, is written `0600` (`umask 077` in the start step), since a shared file system would otherwise hand the installer what its environment withholds. `ComposerRunner` already scrubs its own child to nothing. The container's root cannot read other users' environments either (no `CAP_SYS_PTRACE` by default).
5. **Database.** The person makes Dokploy's PostgreSQL service and sets `DATABASE_URL`, or `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME` and `DB_PASSWORD`, from what it shows. `StartRules` refuses a `DB_HOST` that holds an address and a `DATABASE_URL` it can't read, in sentences that never carry the value (`DatabaseAddress`). The login given is moved out of the environment into a file only root reads (`/run/teme/admin.env`); the deploy step uses it once, for `teme:database:prepare`. When it is a superuser, that makes a login of Teme's own (no superuser, no create rights) that owns the database and a spare `<database>_verify`, with a password that is an HMAC of `APP_KEY`, so every start agrees on it and nothing is stored; the login Teme runs as goes to `/run/teme/service.env` (root only), which only the installer reads, and into the configuration cache, which every other process reads. The login is named for the database, `teme_app_<database>`, not `teme_app` as the recipe's is: two sites on one PostgreSQL service would otherwise share one role and reset each other's password on every start. When the login given is no superuser, Teme runs as it and `teme:doctor`'s `DatabaseRole` says what it has beyond what Teme needs.
6. **One mount.** The person mounts one volume at `/var/teme`. The start step creates `media`, `page-cache` (`www-data`) and `extensions` (uid 9990) in it and links `storage/app` and `storage/page-cache` to the first two, keeping what the image had there; it says in the log when nothing is mounted. It also fills in `TEME_EXTENSIONS_PATH`, `TEME_IMAGE_REPOSITORY` (`ghcr.io/temecms/teme`), `PAGE_CACHE_DRIVER` (`static`) and `PGCONNECT_TIMEOUT`. `APP_URL` can't be filled in: Dokploy tells a container nothing of the domain that routes to it.
7. **Health, one check for the container.** `teme-healthcheck` (the image's `HEALTHCHECK`; start period 15 minutes, because the deploy step runs before the first check can pass): without a role it is the base image's own `curl /up`; with `TEME_ROLE=all` it also fails when nginx, php-fpm, the two workers, the scheduler or the installer is not up under s6. The updater is left out: a crashed updater must not make Dokploy replace a working site.
8. **Updates from the admin: `DokployApplicationPlatform`**, chosen when `TEME_UPDATER_PLATFORM=dokploy-application`, or with `TEME_ROLE=all` and `TEME_DOKPLOY_URL` set. It finds the Application with `application.search` by `TEME_DOKPLOY_APP_NAME` (the name Dokploy shows as App Name; the search matches part of a name, so only the exact one counts), changes the image with `application.update` (the one field, `dockerImage`; `application.saveDockerProvider` would have needed the registry login sent back), redeploys with `application.redeploy`, reads deployments with `deployment.all` and containers with `docker.getContainersByAppNameMatch`. One container is every part, so `health()` reports it for all four, `TEME_UPDATER_IMAGE` is the same setting as `TEME_IMAGE`, and `Platform::hasUpdaterOfItsOwn()` is false, which ends the update at the Updater step with nothing to restart. The updater runs inside the container being replaced: the new container's updater carries on from the request's row, as the updater always has; Dokploy's own defaults (start-first, rollback on failure) put the old image back when the new one never becomes healthy, and the old updater then finishes the row. An Application built from Git or a ZIP has a `sourceType` other than `docker`: the request ends at once, writing nothing to Dokploy, with the sentence that says Dokploy rebuilds it from its source and how. Dokploy's API has no per-key scope: a key can do what its user can, so the guide has the person make a user with access to this Application alone (`service: create` and `deployment: create` are what `application.update` and `application.redeploy` check).
9. **Agreed with the template and Compose part (the other session):** `updates.dokploy_api_key` is a secret in the `updates` settings group, read with `SecretReader::secret('updates', 'dokploy_api_key')` (`DokployToken`); the environment `TEME_DOKPLOY_TOKEN` still wins when set. `TEME_DOKPLOY_URL` is the panel's address; `TEME_DOKPLOY_APP_NAME` names the Compose service's or the Application's Dokploy App Name; `TEME_DOKPLOY_COMPOSE_ID` stays for Compose. `DokployPlatform` (Compose) is untouched except for `hasUpdaterOfItsOwn()` (true), so the two parts join without a conflict; it can adopt `DokployToken` and `DokployApi`. Until the settings group is declared, the key is read from `TEME_DOKPLOY_TOKEN` alone.

## Tests

The supervisor starts every process and stops them on `SIGTERM`; the installer process has none of the site's secrets; two concurrent starts run the deploy once (`DeployProcessesTest`, already in main: two processes, one migrates); a missing `APP_KEY` refuses with the sentence (`StartRulesTest`, already in main); `DATABASE_URL` works and a bad one fails without the password; the updater's Application path against a fake Dokploy (success, refusal writes nothing, switch back). The container tests build the base image with Teme's start files as the Dockerfile places them and a stand-in `artisan` (`tests/Fixtures/Image`); they run in CI and where `TEME_CONTAINER_TESTS=1`.
