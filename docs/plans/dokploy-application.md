# Install on Dokploy as one Application

Branch `deploy/all-in-one`. Teme installs on Dokploy as a single Application from any of its sources (the image `ghcr.io/temecms/teme`, a Git provider building the repository's `Dockerfile`, or a ZIP): one container runs web, both queue workers, the scheduler, the installer and the updater, against Dokploy's own PostgreSQL service. The template and Compose routes are built beside this on `deploy/dokploy-template`; they own the Compose files and the Compose sections of `docs/guides/operators/platforms/dokploy.md`. This plan owns the image's start-up, the Application updater and the guide's section "Install as one Application".

## Decisions as built

1. **One switch, `TEME_ROLE=all`, explicit.** The image never defaults to it: `docker/compose.dokploy.yml` and `docker/compose.yml` start `web` with no role named (the image's own command), so a default of `all` would make that service run workers and a scheduler a second time. Any other value than empty or `all` refuses to start, with one sentence.
2. **The image starts as root and drops, role by role.** One container can only keep the installer (uid 9990) apart from the site (uid 33) if its supervisor can start processes as either, and only root can. The image's entrypoint is now `teme-entrypoint`: as root and with no role it drops to `www-data` and runs the base image's entrypoint exactly as before; started as another user (the installer in Compose, `user: '9990:9990'`) it changes nothing; with `TEME_ROLE=all` it stays root and starts s6-overlay, which the base image already contains and maintains. No new dependency. nginx's master runs as root and its workers as `nginx`, which joins `www-data`'s group to read the files PHP writes.
3. **Start-up order, by s6 dependencies:** `teme-deploy` (a oneshot as `www-data`: the database step, then `php artisan teme:deploy`, which holds `DeployLock`) → `teme-installer-prepare` (a oneshot as uid 9990: `teme:installer --prepare-only`) → nginx and php-fpm (web), `teme-worker`, `teme-worker-long`, `teme-scheduler`, `teme-installer` and `teme-updater`. A failed deploy stops the container (`S6_BEHAVIOUR_IF_STAGE2_FAILS=2`, already set), so web never answers on a half-migrated site. `SIGTERM` stops every service; `S6_SERVICES_GRACETIME` lets a job finish.
4. **The installer's environment is an allow-list**, built from the container's own: `PATH`, the `APP_*` and `DB_*` settings it needs, `LOG_*`, `TEME_EXTENSIONS_*` and `TEME_COMPOSER_BINARY`. Nothing else: no `TEME_DOKPLOY_*`, no media bucket keys, no `TEME_GITHUB_TOKEN`. The configuration cache, which holds every value, is written to a `0700` folder only `www-data` can open (`APP_CONFIG_CACHE=/run/teme/private/config.php`), since a shared file system would otherwise hand the installer what its environment withholds. `ComposerRunner` already scrubs its own child to nothing.
5. **Database.** The person makes Dokploy's PostgreSQL service and sets `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME` and `DB_PASSWORD` from what it shows, or `DATABASE_URL`. `StartRules` refuses a `DB_HOST` that holds an address and a `DATABASE_URL` it can't read, in a sentence that never carries the value. The deploy step runs `teme:database:prepare`: when the given user may create roles it makes `teme_app` (the recipe's role: no superuser, no create rights), gives it the database and a `teme_verify` database, and sets its password to an HMAC of `APP_KEY`, so every start and every container agrees on it with nothing stored. Every service then runs as `teme_app`, and the given user's password stays with root. When the given user may not create roles, Teme runs as it, and Settings › Status says so in the sentence `DatabaseRole` already gives for a role with more rights than Teme needs.
6. **Health, one check for the container.** `teme-healthcheck` (the image's `HEALTHCHECK`; start period 15 minutes, because the deploy step runs before the container's first check can pass): without a role it is the base image's own `curl /up`; with `TEME_ROLE=all` it also fails when nginx, php-fpm, the two workers, the scheduler or the installer is not up under s6.
7. **Updates from the admin: `DokployApplicationPlatform`**, chosen when `TEME_UPDATER_PLATFORM=dokploy-application`, or with `TEME_ROLE=all` and `TEME_DOKPLOY_URL` set. It finds the Application with `application.search` by `TEME_DOKPLOY_APP_NAME` (the name Dokploy shows as App Name), changes the image with `application.update` (the one field, `dockerImage`), redeploys with `application.redeploy`, reads deployments with `deployment.all` and containers with `docker.getContainersByAppNameMatch` (`appType=stack`). One container is every part, so `health()` reports it for all four, and the setting `TEME_UPDATER_IMAGE` and the Updater step are the same as the site's. The updater runs inside the container being replaced: the new container's updater carries on from the request's row, as the updater always has, and Dokploy's own default (start-first with automatic rollback) puts the old image back when the new one never becomes healthy; the old updater then finishes the row. An Application built from Git or a ZIP has `sourceType` other than `docker`: the updater ends the request at once, writing nothing to Dokploy, with the sentence that says Dokploy rebuilds it from its source and how.
8. **Agreed with the template and Compose part (the other session):** `updates.dokploy_api_key` is a secret in the `updates` settings group, read with `SecretReader::secret('updates', 'dokploy_api_key')`; the environment `TEME_DOKPLOY_TOKEN` still wins when set. `TEME_DOKPLOY_URL` is the panel's address; `TEME_DOKPLOY_APP_NAME` names the Compose service's or the Application's Dokploy App Name; `TEME_DOKPLOY_COMPOSE_ID` stays for Compose. Until the group is declared, the key is read from `TEME_DOKPLOY_TOKEN` alone.

## Tests
